## 1. 项目概述

### 1.1 背景与目标

WBME 是企业内部自用的统一管理平台，通过统一入口承载多个业务子系统（资产、人事、财务等，后续还会扩展），各子系统共享同一套登录认证、功能授权和运维能力。

### 1.2 目标形态

- 每个员工只对应一个平台账号，账号与一个钉钉账号一对一绑定；支持**钉钉扫码登录**与**手机号 + 密码登录**，登录后统一进入门户。
- 每个业务系统可独立开放或标记为"即将上线"；员工**只有在该系统拥有至少一项已授予功能时才可看见该系统入口**，系统已开放且服务就绪时才可进入。
- 全站所有业务与管理能力拆分为可授予的**功能权限**，功能是唯一的授权单位；岗位只表示组织身份，不直接带来业务权限。
- 管理能力分为**业务前台**与**管理后台**两个区域：业务前台只承载日常业务操作；平台级管理配置集中到管理后台，各业务系统的配置留在业务系统内。
- 所有关键操作可追溯（审计）、数据可恢复（备份）；全站所有增删改与导出操作统一记录操作日志。

### 1.3 模块与服务

平台按**逻辑模块**划分、按**部署单元**运行。为适应少量开发维护人员，`base` 与 `backstage` 不再分别部署后端容器，而是共同运行在一个 NestJS 后端容器 **`platform-core`** 中；两者仍保留独立的路由命名空间、应用模块、按领域拆分的 Prisma 模型文件与数据库 schema，不合并业务概念或前端区域。为保证跨两个 schema 的本地原子事务，`platform-core` 统一生成一个覆盖 base/backstage 的 Prisma Client 并使用一套迁移序列，不生成两个彼此隔离的 Client。`asset`、`hr`、`fin` 仍分别部署为可独立启停的服务容器；“独立”表示容器可分别开放、停止和恢复，不表示生产环境允许各部署单元运行不同代码版本。每次生产发布以一个 Git commit 作为整个平台版本，前端、全部后端、Worker、恢复执行器和 Migration Runner 均从该 commit 构建；当时处于停止状态的业务服务不被强制启动，但其镜像也更新到同一 commit，之后启动时不得使用旧版本。

全部部署单元共享一个 PostgreSQL 实例并按逻辑模块 schema 隔离数据。`platform-core` 声明拥有 `base` 与 `backstage` 两个 schema；同一进程内的两个模块只通过明确导出的应用服务/命令接口协作，需要原子变更时由编排层创建一个事务客户端并显式传给参与模块，事务中不得执行 hr 等外部网络调用，也不得直接导入对方私有 Repository 或绕过对方业务规则。不同部署单元之间的业务动作通过内部 REST 接口通信，不得绕过目标服务直接写入其 schema；经评审的稳定公共数据可通过明确授权的只读视图共享，视图字段变更按接口契约管理。

数据库**恢复执行器**是本期独立基础设施部署单元，不属于业务模块，也不承载普通业务页面或 API。它常驻但空闲时不执行恢复，只通过受限内部控制路由接收 backstage PRD §10 已由超级管理员确认的恢复请求；按 §9.9 使用项目统一 PostgreSQL 账号，并通过部署机密取得恢复专用 OSS 权限及 ECS 恢复状态目录读写权限，不依赖即将被替换的 PostgreSQL 任务行或 Redis 会话维持恢复状态。它不得挂载 Docker Socket 或开放任意命令、任意 OSS 路径和普通数据库查询能力，部署、健康检查、日志轮转与版本更新均纳入统一 Compose 和发布入口。

| 逻辑模块 | 后端部署单元 | 定位 | 内容 |
| --- | --- | --- | --- |
| base | platform-core | 基础模块，全员可用（无授权门槛） | 注册与登录、会话管理、登录保护、统一门户、个人中心 |
| backstage | platform-core | 管理后台，平台级管理 | 用户管理（含资料修改审批）、功能权限管理（目录/人员权限）、系统设置（含系统开放状态）、系统日志、更新日志与系统公告、数据备份、操作日志、健康状态 |
| asset | asset | 资产系统 | 固定资产、消耗品、库存、申领、代交申领、借还与核销、审批、二维码、资产配置 |
| hr | hr | 人事系统 | 加班申请、代交加班、加班审批、加班历史记录、审批（加班/岗位申请）、组织架构、部门管理、岗位管理、职称管理、人事配置 |
| fin | fin | 财务系统 | 工程合同管理、利润分析汇总、项目操作记录、财务配置（含地区字典） |
| ai | ai（本期不启动） | 智能能力（服务，本期预留） | 本期无业务场景，模块划分与接口架构预留 |
| agent | — | 智能对话 Agent | 本期不实现，仅预留 |

> 各模块的详细功能需求见对应子系统 PRD（见本文档头部索引）。

### 1.4 参数配置原则

- **管理员可调业务参数**（会话超时、登录保护次数与时长、导出业务行数上限、备份保留天数等）不得散落硬编码在业务逻辑或普通配置文件中，统一存储在数据库，并通过对应设置页面维护。
- **版本化工程与安全常量**不进入设置页面：接口版本、Excel 模板版本、上传/解压安全上限、请求固定总超时、健康统计固定窗口、Worker 池上限、BullMQ 记录保留上限等由本 PRD 或技术基线明确为固定值的参数，在代码中的集中常量模块或部署资源限制中维护并纳入版本控制，不能被普通请求或管理员界面提高。这样既避免魔法数字散落，也避免安全边界被运行时配置意外放宽。
- 数据库参数变更发布后，各服务应通过 Redis 广播或下一次读取及时获取新值；“即时生效”表示无需重新部署，不表示追溯改写已按旧值形成的会话、额度周期等业务快照，具体是否影响既有记录由对应业务章节声明。Redis 暂时不可用时遵循 §9.8，不以各实例永久保留不同旧值继续运行。
- 可由业务管理员维护的敏感业务参数（如后续的模型连接密钥）必须使用部署级主密钥加密存储，不明文展示、不写入普通日志。数据库连接串、钉钉应用密钥、OSS 凭证、Cookie 签名密钥等部署级机密不进入该参数表，由环境或专用机密管理能力注入。

## 2. 总体架构需求

### 2.1 统一入口与系统组织

- 登录后统一进入门户，门户展示 WBME 品牌、系统公告入口、可用业务系统入口和个人中心入口（门户详情见 base PRD §5）。
- **全站访问原则**：除登录/注册页、钉钉授权回调与健康状态探针接口外，所有页面与业务接口均要求登录访问；钉钉回调仅处理官方授权结果，健康探针仅返回存活/就绪状态，两者均不承载业务数据。
- 业务系统与管理后台的入口不单独设置授权项：当前用户拥有该系统至少一项功能时入口可见；系统已开放时可进入，"即将上线"或运行不可用时保留入口并显示对应状态，但不能进入。
- 个人中心作为全员可用的门户入口始终展示，不属于业务系统授权项。
- 系统状态规则：**base 与 backstage 共同依赖核心部署单元 `platform-core`，不提供彼此独立的主动下线操作**；`platform-core` 是登录、会话和平台管理的必需核心，停机时整个平台进入不可用状态。asset、hr、fin 支持"开放 / 即将上线"产品状态，并可由运维独立停止对应服务容器。系统未开放、服务已停止或健康检查失败时，其页面和业务接口不可用；依赖它的跨系统功能必须停止当次操作并给出明确提示，不得产生部分写入。ai 不提供门户形态，随依赖它的业务模块可用；agent 本期不实现。
- 每个可进入的系统本期仅必须提供「首页」，作为默认落地页展示欢迎信息与按权限过滤的常用功能快捷入口。仪表盘及其编辑能力本期均不实现，不展示空仪表盘或"开发中"占位入口。
- 系统内导航默认按业务域组织为「业务分组 → 二级分组 → 页面」三级结构（如"消耗品 → 消耗品申领 → 我的申领/代领申请"）；"申请"类入口归入对应业务分组内，不按"申请/历史"横切单列分组；审批中心、系统设置等作为顶层独立入口。默认层级由代码定义，「菜单管理」可突破（见下条）。
- **菜单管理**：每个系统的「系统设置」提供「菜单管理」页签，可调整本系统侧边导航的菜单顺序、分组层级与显示名（中文名），并可一键恢复默认。排序通过拖拽或每行右侧的上移/下移按钮完成；顶层独立入口与分组在同一顺序轴上混排；菜单项可挂在顶层或任意分组下，分组可新建、重命名、移动、嵌套到任意深度（唯一限制：分组不能落入自身或其后代），空分组可删除。菜单项本身由代码定义，页面上不支持新增或删除，仅调整既有项的展示配置；菜单项的路径与权限要求不受展示配置影响。配置按系统独立保存在数据库，修改后无需重新部署即生效。
- 不把任何一个业务系统伪装成全平台首页。

### 2.2 业务前台与管理后台边界

- **业务前台**（资产、人事、财务）：只承载日常业务操作导航（系统首页、业务办理、审批中心、记录查询等），不提供平台级管理页面入口。
- **业务配置**（资产配置、人事配置、财务配置）：留在各自业务系统内，作为系统内的配置页面。
- **管理后台**（backstage）：承载平台级管理能力——用户管理、功能权限管理、系统设置（含系统开放状态）、系统日志、更新日志与系统公告、数据备份、操作日志、健康状态。
- **组织信息**：用户管理位于管理后台；组织架构、部门管理、岗位管理、职称管理位于人事系统。
- 配置与组织功能按各自所属系统的功能授予与委派。

### 2.3 用户类型

| 用户 | 职责 |
| --- | --- |
| 超级管理员 | 平台根管理员，不受任何业务权限约束；可维护超级管理员账号和任意员工的功能授权。 |
| 普通员工 | 仅使用被直接授予的业务或管理功能；被授予"权限管理"功能时，可管理全部系统内任意普通员工的普通功能授权与权限组。 |

站点角色仅此两种；除超级管理员外，任何用户不因角色获得隐式功能。

### 2.4 多端形态

- 桌面端与移动端（响应式 Web，非独立客户端）均须能完成登录、门户选择、个人中心、审批及被授予的核心管理操作；同一功能授权不能仅因使用移动端而失去业务能力。具体呈现形态由开发阶段设计，不在本 PRD 限定；表格在移动端的展示形态按 §10.2 执行。

### 2.5 功能权限机制说明

> 各系统的功能权限清单见对应子系统 PRD §1（管理后台：backstage PRD §1；资产系统：asset PRD §1；人事系统：hr PRD §1；财务系统：fin PRD §1）。本节只保留清单的组织方式与通用规则。

- 功能权限目录按「系统 → 业务板块 → 功能」三层组织；功能是唯一的授权单位（授权机制详见 §3.1）。
- **拆分原则（以业务理解为准，不套公式）**：
  - 使用者不同的操作拆分为不同功能；
  - 同一使用者的业务操作保持闭环，不能因权限拆分卡住业务；
  - "管理"类功能隐含包含其"查看"能力（无需额外授予查看权限）；"查看"类功能独立存在，供只读人员单独获得；
  - 数据被多个功能引用的管理项（如部门、岗位）独立授权更有意义；脱离业务场景无意义的能力不独立。
- **申请类功能通用规则**：
  - 所有"申请"类功能在同一页面内以 tab 形式提供"xx申请"与"历史记录"两个视图（tab 状态可直链、刷新与前进回退后保持）；"历史记录"tab 用于查看本人/部门/公司在该业务下的申请记录；
  - 拥有"xx申请"权限即拥有**查看本人 xx 历史记录**的权限（隐含，无需单独授权）；
  - 另设"xx历史记录"独立权限，数据范围分 **部门 / 公司** 两档，赋予后可查看对应数据范围内的历史记录；所有数据范围均包含下级，"部门"范围隐含"本人"范围；
  - 审批类功能数据范围分 **部门 / 公司** 两档：部门档可审批提交时部门快照位于本部门（含下级）的申请对象，公司档可审批全部；多对象批次按 §3.2 要求覆盖全部申请对象。

### 2.6 全局软删除与批量删除原则

- 除字典、分类、库位、部门、岗位、品种等本节明确的配置类数据例外，或业务章节另行声明为物理清理/不可删除外，本文中的"删除、批量删除、注销"统一表示**软删除**：记录保留在原表，写入删除时间和删除操作人，不提供面向前端或普通业务服务的硬删除方法。
- 所有正常列表、详情、搜索、下拉选择、统计和权限判断默认自动排除软删除记录；需要保留历史引用的审批、库存流水、操作日志等仍通过原标识展示必要的历史快照，不因关联对象被软删除而丢失。
- 软删除过滤针对"被查询的主实体"和"新建业务可选目标"，不能错误传播为关联业务记录消失。用户注销后不再出现在新增申请、代交名单、责任人分配和权限授予等选择器中，但固定资产、借还、库存、加班、审批、操作日志等既有业务记录仍必须返回并展示该用户的原用户 ID、姓名等最小必要快照及"已注销"标记；查询实现不得因关联用户已注销而使用内连接或默认关联过滤丢掉整条业务记录。部门、岗位、字典等停用或删除后的历史引用遵循同一原则，以提交/发生时快照展示且不能重新选用。
- 独立列表中的删除默认使用"勾选 + 批量删除/批量注销"，不提供逐行单个删除入口，也不提供单条删除 API；确有单对象交互时，前端仍调用同一个批量接口并只传入一个标识。批量删除采用**全有或全无**语义：服务端先校验全部目标的存在性、权限、引用和业务状态，任一目标失败则返回全部失败明细并且整批不产生任何删除；全部通过后在单个数据库事务中一次完成。接口幂等并受平台批量数量上限约束。
- 软删除不自动等于可恢复；只有业务章节明确提供恢复能力时才显示恢复入口。软删除记录是否继续占用业务唯一键由各业务章节确定，未明确时必须在数据设计阶段给出规则，不能因默认过滤而产生不可区分的重复历史记录。
- **配置类数据硬删除例外**：业务字典项、资产/消耗品分类、库位、部门、岗位和消耗品品种等配置类数据不使用软删除，删除成功即物理移除；删除入口仍只使用批量接口并遵循整批回滚（存在性、权限与业务状态校验任一失败则整批不变更）。
- **引用存值快照**：上述配置类数据被具体业务引用时不保存外键关联，而是直接保存当时的名称/路径文字快照（例如消耗品批次保存入库时的库位名称快照，而不是库位 ID）；配置项被删除后，既有业务与历史记录仍按快照原样展示，不需要也不允许回溯改写。
- **删除前引用确认**：批量删除配置类数据前，服务端返回每个目标仍被引用的情况（现存库存、未结清借还、在职员工、资产归属、待审批申请、职称规则等当前业务引用的数量），前端明确展示（如"xx消耗品xx批次仍存在该库位，你确定要删除吗？"）并要求操作者确认后才执行；引用本身不再导致整批拒绝。其中部门、岗位被删除时，其**当前业务引用**（员工所属部门/岗位、资产所属部门、部门负责人等）在同一事务中直接置空——这些字段原本就允许为空；审批快照、操作记录等历史记录类引用不受影响，仍按快照展示原值。有未删除下级部门的部门仍禁止删除（须先处理下级），以维护部门树完整。配置项可继续通过"停用"阻止后续新选择而不删除。硬删除后同名值可以重新创建并获得新的记录 ID（如品种允许同名再建）。品种的额外限制见 asset PRD §5。
- **财务金额明细单条硬删除例外**：开票金额、已收回款和已付分包款的已持久化明细允许在所属项目内逐行删除，删除成功即物理移除，不提供恢复功能，也不要求使用批量入口。服务端必须先校验"财务数据维护"权限、项目与明细归属和当前记录状态，并在同一个数据库事务中写入包含被删明细完整删除前快照的项目操作记录后再删除；审计写入失败时删除同步回滚。Excel 完整覆盖引发的原明细替换遵循 fin PRD §4 的同类物理删除与审计规则。
- 其它不属于普通软删除的场景：未关联业务图片清理、备份保留策略清理、缓存/会话过期，以及法律或安全要求下经专项流程执行的数据物理清理；系统日志（错误日志与安全日志）、操作日志、库存流水、审批处理记录和 PostgreSQL 后台任务事实记录等声明为不可删除的数据不提供删除能力。BullMQ 中仅用于投递排障的已完成/失败队列记录按 §9.1 清理，不等同于删除 PostgreSQL 任务事实。利润分析 Excel 导入原文件和导出结果按 fin PRD §4、§9.2 不持久化，因此不产生待清理的 OSS 文件。
- 表单中移除尚未保存的临时行、取消待审批申请、撤回已发布公告等属于业务状态操作，不视为单条硬删除；已经持久化且允许删除的明细默认遵循所属业务的软删除和审计要求，但本节明确列出的财务金额明细按单条硬删除例外执行。

## 3. 平台级机制

> 以下三个机制被全平台各系统（base/backstage/asset/hr/fin）共同引用，属平台级通用机制。各模块的具体业务规则见对应子系统 PRD。

### 3.1 功能权限机制（核心）

**授权目录**

- 功能权限目录按「系统 → 业务板块 → 功能」三层组织；功能是唯一授权单位（清单见 §2.5 及对应子系统 PRD §1）。
- 授权以功能为原子单位，整体授予、整体撤销，不存在部分生效。
- 功能由开发注册：全平台功能目录的权威定义保存在各部署单元共同引用的**共享代码包**中，随全平台同一 Git commit 版本化；asset、hr、fin 的守卫与 backstage 的启动对账读取同一份目录定义，不存在各服务各自注册导致的目录漂移。功能归属、板块划分、排序、可选数据范围均在开发时确定，界面不可调整；管理员仅可维护功能的业务说明文字（悬停展示该功能开放的业务操作）。
- 每次启动/发布由 backstage 以稳定功能编码把代码目录与数据库注册表幂等对账；新增、移除、系统/板块归属或可选数据范围变化时，在同一事务更新目录并递增全局权限目录版本，随后由 base PRD §3 的版本校验使旧授权缓存失效。移除的功能不再参与入口、菜单或守卫判断，其历史授权行可保留为审计数据但不得继续生效；普通业务说明文字和纯展示排序变化不改变授权语义，可不递增该版本。
- 功能无启停状态，存在即启用；base 功能全员可用，不进入授权目录。

**数据范围**

- 每项功能授权可附带数据范围：**本人 / 部门 / 公司**；"部门"包含部门及全部下级部门，多部门员工按其所归属部门（含下级）的并集计算；"本人"的语义按业务定义（如固定资产指责任人或使用者为本人，申领/借还为本人提交的记录）。
- 每项功能声明可选的数据范围档位，授权界面只展示可选档位（清单见 §2.5 及对应子系统 PRD §1）。
- 同一权限点被多个不同范围授权时按最宽范围生效（公司 > 部门 > 本人）。
- 业务读取接口（列表、详情、导出、审批待办）必须按授权范围过滤数据；范围外的记录视为不存在。
- **申请类功能**：授权范围为本人的功能隐含本人历史记录的查看权限；"xx历史记录"独立功能（部门/公司两档）授予后可查看对应范围内的历史记录；"部门"档隐含"本人"档。
- **审批类功能**：授权范围分部门/公司两档，数据范围根据提交时保留的申请对象部门快照，决定审批人可见与可处理的待办/记录；多对象批次的审批人范围必须覆盖全部申请对象。
- **读取上下文**：功能执行所需的关联数据读取属于该功能自身能力，不额外要求其它功能授权——审批类功能可读取待办、申请详情及其关联业务数据（如品种、库存条目）；组织架构可引用部门树与岗位档案。

**角色与委派**

- 站点角色仅「超级管理员」与「员工」两种。
- **超级管理员不受任何功能授权和数据范围约束**，无需被授予功能即可访问平台能力；该豁免只针对访问控制，不绕过字段校验、状态机、库存一致性、岗位适用范围、危险操作确认或其它业务规则。超级管理员之间可互相任免，超级管理员可把普通员工任命为超级管理员，没有额外任命门槛；唯一限制：当系统中仅剩 1 名超级管理员时，该超级管理员不可主动卸任（卸任或降级将导致平台失去根管理员）。任命、卸任或降级提交前必须明确展示目标账号与权限影响并二次确认，接口在事务内复核操作人当前仍是超级管理员、目标账号状态和最后超管约束并记录变更前后值；按 base PRD §3 不再要求操作人重新输入密码或扫码。
- 平台的第一个超级管理员由部署初始化直接创建为已激活账号，部署参数至少提供其姓名、手机号、性别和初始密码（密码策略同 base PRD §2）。初始化幂等：已存在已激活超级管理员时跳过，不重复创建、不回改密码。种子超管的钉钉绑定不由初始化流程代办，由本人登录后在个人中心自助扫码绑定（base PRD §2）。
- **"权限管理"是唯一的授权管理功能**，不再按系统拆分：持有者可进入管理后台的权限管理页，管理**全部系统**内任意普通员工的普通功能授权与权限组。
- **仅超级管理员可以授予或撤销"权限管理"功能**；委派链条固定为两级（超级管理员 → 权限管理 → 普通功能授权），不存在继续向下转授的入口。权限管理员不能授予或撤销他人的"权限管理"功能，也不能修改自己的授权或其它权限管理员的"权限管理"功能（防止自我提权与权限管理员互相倾轧）；超级管理员可按信任关系只向少数员工开放该功能。
- 普通员工只在被授予的范围内工作或管理。

**权限组（授权预设）与批量授权**

- **权限组**：命名的一组功能授权（每个功能含数据范围），**可跨系统**（一个组可包含多个系统的功能），作为授权时的快捷模板。权限组本身不是授权单位——功能仍是唯一授权单位，权限组只是批量展开的预设，不新增授权项。
- **与员工不产生关联**：将权限组授予员工时，把组内功能**展开**为员工的功能授权快照；此后修改或删除权限组不影响已按该组授权的员工。员工始终持有展开后的功能授权，不引用权限组。
- **维护边界**：持有"权限管理"功能者（含超级管理员）可创建、编辑和删除全部权限组；权限组变更按 §3.3 记录操作日志。
- **功能目录变化的影响**：权限组内功能被移除或数据范围失效时，该功能不再可从组内展开；已按旧目录展开的员工授权遵循本节撤权规则处理。
- **批量授权**：管理后台权限管理支持选定多名员工后批量授权（**增量**）：一次操作为所选员工追加功能授权或权限组展开授权，不改动其已有授权；按本节的授权版本校验与 §3.3 的幂等规则执行，任一目标失败整批回滚并逐人返回原因，不出现部分成功。

**入口推导**

- 员工在某系统拥有任一已授予功能时才可见该系统入口；只有系统已开放且服务就绪时才可进入。撤销该系统最后一项功能后，入口、菜单和直接访问同时失效。
- 管理后台向持有任一 backstage 功能授权的员工开放。
- 用户界面只展示可进入的页面和可执行的操作；服务端始终做最终校验，直接地址或接口访问同样受限。

**变更审计**

- 权限变更、批量授权/撤销和"权限管理"功能的授予/撤销操作必须记录操作者、目标员工、变更前后内容和时间。

### 3.2 统一审批机制

**统一原则**

- 平台建立轻量级的统一审批内核，复用状态、字段、权限校验、并发控制、操作日志和接口语义；本期不引入 BPMN 或可视化通用流程引擎。
- "统一"不等于建立一个所有模块必须依赖的中央审批服务：资产、人事、管理后台等服务分别拥有本模块的审批记录与业务明细，但必须实现同一审批契约，使用共享的审批内核代码。目标模块停止时，其审批也随之不可用，不影响其他模块。
- 每条审批至少保留：申请编号、申请类型、所属系统、业务记录标识、申请人/代交人、申请对象列表、每个申请对象在提交时的部门快照、状态、版本号、提交时间、处理人、处理时间与处理意见。

**状态与流转**

- 统一状态为：**草稿、待审批、已批准、已驳回、已取消**；不支持草稿的申请类型可在创建时直接进入待审批。
- 只允许"草稿 → 待审批""待审批 → 已批准/已驳回/已取消"。已批准、已驳回和已取消均为终态，不得直接改回待审批；需要重新申请时建立新记录并关联原记录。
- 提交人或代交人只能取消待审批记录；驳回必须填写原因，批准意见可选；业务另有要求时可将批准意见声明为必填。
- 本期不实行申请与审批强制分离：申请人、代交人或申请对象只要确实拥有对应审批功能、数据范围覆盖整张申请且满足当前状态和业务规则，就允许审批与自己相关或由自己发起的批次，不因身份重合额外拒绝，也不为超管设置不同规则。审批记录仍必须如实保存申请人与处理人；权限授予继续受 §3.1 的委派规则控制，不能由申请人在流程内临时取得审批权。
- 审批记录不保存 `expiresAt`。待审批超过系统设置"审批超时自动取消天数"（默认 30 天）后，由每日后台扫描自动取消；不因等待时间过长自动批准或驳回。待审批记录保持待办，直到合格审批人批准或驳回、提交人/代交人主动取消，或超时自动取消。
- 待审批期间已经形成的库存、额度、待处理数量或其它业务占用持续有效；批准时按业务规则转换为正式结果，驳回、人工取消或超时自动取消时在同一数据库事务内释放，并记录取消来源。页面展示提交时间和已等待时长，并提示超时自动取消规则。
- 账号注销属于审批生命周期事件，按 backstage PRD §3 区分申请类型处理：公司业务型申请继续流转，账号资料型申请自动取消。自动取消（账号注销、超时）仍必须执行该申请原有的终态释放逻辑并记录取消来源，不得只隐藏待办或直接删除审批记录。

**权限与数据范围**

- 审批人必须同时拥有对应审批功能，且其数据范围覆盖当批次的**全部申请对象**；批次没有独立申请对象时，默认按申请人提交时的部门快照计算。跨越多个部门且无任一部门范围审批人能完整覆盖的批次，只能由公司范围审批人处理。资产系统的库存入库和库存变更会直接影响全公司库存，属于明确例外：两类申请只能由持有"消耗品审批（公司）"者查看和处理，部门范围不能审批，即使申请人属于其部门也不例外。
- 列表、详情与处理接口均执行相同的权限与范围校验；范围外记录对调用者表现为不存在。
- 本期所有审批均为单级审批：任一合格审批人首次有效处理后即进入终态，不要求多人会签或按固定顺序审批。

**并发、幂等与业务原子性**

- 提交、批准、驳回和取消接口均支持幂等键；同一幂等键的重试返回原结果，不得重复生成批次、库存流水或其它业务副作用。
- 处理审批时必须使用"当前状态 + 版本号"条件更新并在数据库事务内完成状态变更、业务副作用和审计记录；并发请求仅允许一个成功，其余返回明确的状态冲突。Redis 分布式锁可减少冲突，但不是数据正确性的唯一保障。
- 批准前必须在事务内重新校验权限、申请数据和业务前置条件；校验失败时保持待审批并返回可理解的失败原因，不产生部分业务结果。

**各业务待审批数量规则**

- 统一审批内核只提供"按业务键限制待审批数量"的可选能力，不默认限制同一申请人只能有一条申请；每种申请必须在本业务服务中声明限制键、提交校验和终态释放规则，不能为了形式统一覆盖真实业务差异。
- 声明"同一业务键最多一条待审批"的类型必须同时使用事务内校验和 PostgreSQL 条件唯一索引（例如对待审批状态下的员工标识唯一）保证并发正确性；两个并发提交最多一个成功，另一个返回明确 `CONFLICT`。允许多条的申请类型不得错误复用该索引，而应依赖本业务的时间重叠、库存占用或待处理数量约束。
- 资料修改：同一员工同时最多一条待审批资料修改申请；进入批准、驳回或取消终态后方可再次提交（类型定义见 backstage PRD §5）。
- 岗位变更：同一员工同时最多一条待审批岗位申请；进入批准、驳回或取消终态后方可再次提交（类型定义见 hr PRD §5）。该限制不是"一生只能申请一次"。
- 加班申请：允许同一员工存在多条待审批申请，但同一天的时间段必须按 hr PRD §3 校验不得重叠。
- 库存入库、库存变更和普通/代交消耗品申领：允许存在多张待审批申请；库存与额度分别以 asset PRD §5 的原子占用规则限制，不以申请条数限制。
- 个人归还与核销：允许存在多张待审批申请，但同一借还记录的待处理数量之和不得超过可处理数量；代领结清按"代领清单"限制同时最多一条待审批结清申请，见 asset PRD §7～§8。

**页面交互**

- 审批中心点击待办后，在当前页面以抽屉或侧栏展示申请详情（申请信息、申请对象列表、处理记录时间线、当前状态），支持"上一条 / 下一条"切换待办，无需返回列表。
- 提供快捷批准/驳回操作（驳回仍须填写原因）；处理记录时间线按时间展示提交、取消及各处理人的处理操作。

### 3.3 操作日志

- 权限：backstage 功能"操作日志"，数据范围仅 **部门 / 公司** 两档（"本人"档无意义：个人中心已向全员提供本人日志查看）；持有部门或公司任一档授权的员工才可见并进入管理后台的"操作日志"页面。
- **存储与汇总**：base、backstage、asset、hr、fin 分别在自己的 schema 中维护结构完全一致的只追加操作日志表，只写本模块产生的日志，不跨 schema 写入集中日志表。管理后台通过经评审的只读 `UNION ALL` 联合视图统一查询所有模块日志；因此查询不要求各业务服务容器在线。新增模块时必须同时注册日志来源并通过联合视图脚本（见 §9.9）扩展联合视图。
- **记录范围**：全站所有功能的**新增、修改、删除与导出**操作统一记录；普通列表查询不记录。
- **字段**：操作者、操作时所属部门（员工多部门时记录其全部归属部门）、系统、功能、操作性质（增/删/改/导出）、操作内容摘要（按功能定义模板生成，如"用户A在资产系统的固定资产维护中新增了固定资产XXX"；每个功能可有不同的摘要模板）；重要写操作另保存幂等作用域、幂等键、规范化请求指纹和最小结果引用。
- 新增、修改和软删除日志由业务服务在对应业务事务内写入本模块日志表，业务回滚时日志同步回滚；请求内导出只有在服务端完成文件生成并正常结束下载响应后才写入成功操作日志，生成或传输失败只记录失败访问结果及必要的系统日志，不伪装为成功导出。各模块复用同一字段定义与摘要模板接口，但日志写入失败不得被静默忽略。
- **幂等记录复用**：本期不另建 PostgreSQL 通用幂等表。重要写操作在业务事务内写入上述操作日志，并对"操作者/调用服务 + 幂等作用域 + 幂等键"建立唯一约束；请求指纹由校验后的规范化 DTO 计算，不保存密码、凭证或完整敏感请求体，结果引用只保留重放响应所需的业务记录标识、任务标识和稳定状态。并发重复请求中只有一个事务能成功写入并执行业务副作用；同一键且指纹相同的后续请求返回原业务结果，同一键对应不同指纹时返回 `409 IDEMPOTENCY_KEY_REUSED`。校验失败或事务回滚不留下成功操作日志，修正后仍可重试。
- Redis 只缓存近期幂等响应以减少数据库查询，缓存丢失不影响操作日志中的唯一约束和原结果定位；不得把 Redis 中的一次性中间数据当作防止重复审批、重复扣库存或重复创建任务的唯一依据。幂等键、请求指纹和内部结果引用不在普通操作日志列表、详情或导出中展示。
- 需要发送队列任务、调用下游服务或产生其它数据库外副作用的幂等写操作，必须先提交本地业务事务和操作日志，再基于已提交的业务/任务标识触发；不得在幂等唯一约束落库前执行不可撤销的外部动作。属于 §9.1 后台任务的场景统一在该事务内创建 `PENDING_ENQUEUE` 任务记录，由任务表兼任的轻量 Outbox 提交后投递，不允许业务代码直接双写 PostgreSQL 与 BullMQ。下游接口仍使用同一业务幂等键或派生子键自行去重。
- **筛选**：系统、功能、操作者、部门、操作性质、时间；除数据范围必需的约束外，筛选项均可不限，功能选项随已选系统联动。初始查询使用系统设置中的默认时间窗口，用户可调整或清除时间条件；后端通过分页、索引和导出上限控制资源消耗。
- **导出**：支持"导出所有 / 导出已筛选"两种范围，不提供"导出当前页"。"导出所有"忽略页面筛选与分页，导出当前用户权限范围内全部日志；"导出已筛选"导出符合当前筛选条件的全部日志，同样不受当前页分页影响。
- **只追加**：操作日志后端不提供修改或删除接口，用户无法自主调用增删改接口修改或删除日志。
- 个人中心提供"我的操作日志"入口（全员可用，无需授权，见 base PRD §6），仅查看本人日志。

## 9. 公共基础设施需求

### 9.1 非阻塞异步 I/O 与后台任务

- 本文所称"尽可能采用异步架构"首先指**请求内的非阻塞异步 I/O**：HTTP、PostgreSQL、Redis、OSS、内部服务调用及文件流均使用异步 API，并正确处理流背压，不在 Node.js 主事件循环中执行同步网络、同步文件或长时间 CPU 阻塞操作。它不表示所有操作都要创建 BullMQ 任务，也不表示接口可以在业务尚未完成时提前返回成功。
- 利润分析 Excel 导入在预览或确认的当前 HTTP 请求中接收、校验和处理上传流；导出在当前下载请求中读取一致性快照并把工作簿流直接响应给浏览器。两者属于请求内异步 I/O，不进入 BullMQ，不把文件写入 OSS、PostgreSQL、Redis 或服务器磁盘，也不提供稍后下载的任务记录；请求失败、服务重启或连接中断后由用户重新发起。
- Excel 解析、ZIP/压缩、工作簿序列化等可能长时间占用 CPU 的步骤不得直接阻塞 NestJS 主事件循环，应转移到**有界的 Node.js Worker Threads 工作池**执行；工作池只承载当前请求的计算，不构成可恢复后台任务，不持久化文件或中间工作簿。请求取消或超时必须传播到工作线程，排队中的工作要取消，正在执行的工作要尽快终止并释放内存。
- 审批、库存、借还、权限、单元格即时保存、导入确认及其它产生正式业务结果的写接口，必须等待数据库事务和同事务内操作日志/领域审计成功提交后才返回成功，禁止以 fire-and-forget 方式把核心写入留在请求返回后执行。确需跨请求持续执行、可查询状态和失败恢复的长任务，才进入下述持久化后台任务体系。
- 本期使用 BullMQ 的后台任务限定为：每日定时数据库备份、用户发起的立即备份及备份保留清理、数据库恢复请求的可靠投递、账号注销后的账号生命周期处理、未关联业务图片清理、待审批超时自动取消扫描。此类任务可脱离原 HTTP 请求继续运行，任务状态可查询；定时备份与立即备份复用同一处理器和备份格式，只以任务类型/发起来源区分。恢复前紧急备份是 backstage PRD §10 恢复执行器接管后的受控恢复阶段，不再另投递一个可能与恢复状态失去关联的普通 BullMQ 作业。数据库恢复执行器接管请求后的特殊状态边界遵循 backstage PRD §10，未在业务章节和本节明确列入的操作不得仅以"异步"为由擅自改造成后台任务。节假日 API 查询属于当前加班表单或提交请求中的异步 HTTP 调用，成功后直接保存，不创建后台同步任务。
- **统一任务事实表**：`backstage` schema 维护一张全平台后台任务表，其 Prisma 模型、迁移和索引由 `platform-core` 内的 backstage 逻辑模块拥有；`platform-core` 内其它逻辑模块及独立业务服务都只能通过共享任务模块执行预定义的创建、投递状态和执行状态条件更新，不得借此读取或修改其它 backstage 业务表。任务表记录任务标识、任务类型、所属模块、发起人/调度器、最小业务引用、状态、进度、开始/结束时间、尝试次数、下次投递/重试时间、超时时间、执行租约和脱敏后错误；支持超时控制、卡死任务发现与 Worker 优雅停机。至少为"状态 + 下次投递/重试时间""状态 + 执行租约到期时间"建立扫描索引，并为失败终态建立"结束时间倒序"的条件索引，使到期领取、租约异常发现和 backstage PRD §11 最近 24 小时失败汇总都不依赖全表扫描。除 backstage PRD §10 中会主动替换该数据库的恢复执行阶段改以数据库外恢复控制清单为事实来源外，其它后台任务均以本表为唯一状态事实来源。该集中写入是 §9.4 明确列出的平台基础设施跨 schema 例外，不允许被业务模块当作通用跨服务数据表。
- **任务表兼作轻量 Outbox**：PostgreSQL 任务记录是任务存在性和最终状态的唯一事实来源，也是该任务的待投递记录，不另建第二张 Outbox 表。创建任务的业务事务只负责写入状态为 `PENDING_ENQUEUE` 的任务记录及相应操作日志，不在事务提交前向 Redis 投递；事务回滚时任务记录一并消失，接口只有在任务记录提交成功后才返回已受理。
- **可靠投递与恢复**：独立调度循环以跳过已锁行的方式分批领取到期的 `PENDING_ENQUEUE`、投递租约已过期记录，以及执行租约已过期且任务策略明确允许安全重放的 `QUEUED/RUNNING` 非终态记录，使用数据库任务 UUID 作为稳定的 BullMQ `jobId` 投递，成功后条件更新为 `QUEUED`；投递失败保留数据库记录并按有上限退避再次尝试。若进程在 BullMQ 已接收后、数据库状态更新前崩溃，重复投递优先由稳定 `jobId` 去重；即使对应 BullMQ 记录已被清理、Worker 在执行中崩溃或 Redis 数据丢失，调度器也可根据 PostgreSQL 状态、过期租约和任务重放策略恢复。数据库恢复在写入 backstage PRD §10 外部控制清单前可以按上述投递规则重新交付；清单写入后不再由通用任务扫描器重放，执行异常或租约过期必须保持维护状态并要求人工核查。
- **至少一次执行语义**：BullMQ 只负责唤醒执行，不作为完成事实来源。Worker 收到任务后必须先读取 PostgreSQL 任务记录，以条件状态更新和执行租约领取；终态任务直接幂等结束，同一任务可能被重复投递或重复唤醒，处理器必须依靠任务 ID、业务唯一约束和事务保证副作用至多生效一次。成功、失败、取消和进度通常以数据库记录为准；数据库恢复在执行器接管后改按 backstage PRD §10 外部控制清单记录阶段，完成后再把结果写回新数据库。任务结束后丢失 BullMQ completed/failed 记录不影响页面查询与恢复。该轻量 Outbox 只解决本节后台任务投递，不自动解决跨服务业务写入或任意外部消息一致性，后者仍按 §9.4 单独设计。
- **失败排障关联**：后台任务因处理异常进入最终失败状态时，Worker 至少通过 backstage PRD §8 共享日志模块新增或聚合一条脱敏系统日志，服务字段使用所属模块，来源固定为 `BACKGROUND_TASK:<任务类型>`，并保留可关联任务事实记录的内部最小标识；任务参数和业务内容不得进入来源、指纹或公开摘要。自动重试过程中的同类异常可以按 backstage PRD §8 指纹聚合，但健康状态的"最近 24 小时失败数"只统计最终失败任务数，不把一次任务的多次尝试重复计算。系统日志写入失败不能把已经失败的任务标记为成功。
- **BullMQ 记录保留**：所有队列统一配置 `removeOnComplete: { age: 604800, count: 1000 }`，成功记录的策略上限为 7 天且每个队列最多 1,000 条；统一配置 `removeOnFail: { age: 2592000, count: 5000 }`，失败记录的策略上限为 30 天且每个队列最多 5,000 条，两者均同时受年龄和数量约束。这些固定值作为有名称、受版本控制的基础设施常量集中定义，不放入系统设置，也不得由单个任务提高。BullMQ 的年龄清理是惰性触发，过龄记录不会仅因时钟到点自行消失，因此 Worker 启动时和每小时维护循环还必须调用受限清理流程；正常运行时物理删除最多滞后一个维护周期，Worker 停止期间不承诺按时删除但也不会继续消费产生新记录，恢复后立即清理。清理失败记录系统日志，但不影响 PostgreSQL 任务状态。
- **任务历史与去重边界**：PostgreSQL 统一任务事实记录在 MVP 不自动清理、不提供删除接口，业务页面和健康状态汇总均以它为准。BullMQ 记录被清理后，相同 `jobId` 不再依靠 Redis 阻止重新加入，因此任务表终态检查、执行租约和业务幂等约束始终是最后防线；不能把 `removeOnComplete/removeOnFail` 的保留窗口误当作任务去重期限。
- 只有设计为幂等且失败后可安全重放的任务才允许自动重试，重试采用有上限的退避策略；每日备份按调度周期去重，数据库恢复不自动重试。
- 队列任务数据中不得存放钉钉凭证、密码、模型密钥等敏感值；任务只保留查找业务数据所需的最小标识。
- 实现：采用 BullMQ（基于 Redis 的队列，Node.js 社区主流方案）承载任务队列与调度。

### 9.2 文件存储

- 提供统一文件存储能力，用于资产主图、消耗品图片和数据库备份文件。利润分析 Excel 导入原文件与导出结果明确不使用 OSS 或其它持久文件存储，按 fin PRD §4 在请求内处理。
- 图片类文件上传前压缩至 1MB 以下（前端压缩，后端校验兜底，超限拒绝）；MVP 只接受 JPEG、PNG、WebP 静态位图，拒绝 SVG、GIF/动画、脚本化内容和无法完整解码的文件。后端不信任文件名、扩展名或客户端 MIME，必须校验实际文件特征、像素尺寸/总像素安全上限与上传者权限，并在正式关联前使用成熟图像库完整解码、纠正方向、移除 EXIF/定位等元数据后重新编码为允许格式。预签名直传的临时原对象不得直接作为页面图片响应；只有后端处理后的私有正式对象可被业务记录引用和限时下载，下载授权以业务引用为准（已正式关联的对象供引用方共享查看，不校验下载者与上传者一致；未正式关联的临时对象一律拒绝），解码或重编码失败时拒绝关联并交由临时对象清理机制处理。
- OSS 使用私有存储空间和限时、限大小、限路径的预签名上传/下载凭证；Bucket 与对象禁止公共 ACL，生产环境统一启用由 OSS 托管密钥的服务端加密（MVP 使用 `SSE-OSS/AES256`，不新增自管密钥或 KMS 运维），传输只允许 HTTPS。对象键由服务端生成，不接受用户提供的任意路径；应用凭证按图片与备份所需前缀限制权限。数据库备份不通过普通业务文件下载通道暴露，写入对象时必须携带并在恢复预检时验证服务端加密元数据；生产 OSS 场景下加密元数据缺失或读取失败均视为预检失败并禁止恢复，本地存储替身可跳过该校验。
- 图片上传先进入临时状态，只有后端校验并确认业务保存后才与正式记录关联；上传或业务保存失败不破坏主业务数据。对象键必须使用平台固定图片前缀和服务端生成的随机标识，不与备份前缀混用。未关联业务记录且超过提交时保留时长快照的图片由 Worker 定期从 OSS 物理删除，默认保留 24 小时并可在系统设置中调整；清理不能只扫描 PostgreSQL 中仍存在的"待清理记录"，还必须分页列举固定图片前缀下超过保留期的对象并与当前数据库全部正式/历史图片引用做差集，从而清理由请求中断、数据库整库恢复或临时记录丢失形成的 OSS 孤儿对象。每个候选对象删除前再次确认仍无任何正式或历史引用；删除任务幂等，OSS 列举/删除失败时保留或重建待清理记录并有上限重试，不把失败伪装成清理成功，也不得扫描或删除备份前缀及平台外对象。
- 已与正式业务记录关联、被历史记录引用或所属业务记录仅被软删除的图片不属于临时文件，不得被上述任务删除；更换主图时，旧图作为变更历史引用继续保留。只有从未完成正式关联的上传对象适用 24 小时自动清理。
- Excel 导入端点同时检查请求声明大小并在接收过程中限制累计字节数，固定执行 fin PRD §4 的单文件 20 MiB、10,000 个项目数据行、累计解压 200 MiB 和 1,000 个 ZIP 条目上限；网关与应用层采用一致的有效上传上限并统一返回 §9.5 错误结构，不能只依赖可伪造或缺失的 `Content-Length`。读取后校验文件特征、Open XML 工作簿结构和数据上限，拒绝加密、嵌套或非法路径条目；超限或格式非法立即终止、取消 Worker Threads 工作并释放内存。预览与确认各自执行固定 120 秒总超时。Excel 导出使用流式附件响应或受控内存缓冲直接返回浏览器，响应设置禁止缓存敏感文件的响应头，任何路径均不得先把工作簿写到 OSS 或容器持久卷。

### 9.3 系统日志与审计

- 重要运行异常由后端按 backstage PRD §8 自动写入或聚合到 `backstage` schema 的集中系统日志表；原始脱敏异常样本不可人工新增、编辑或删除，仅允许更新聚合计数/最近发生信息和处理状态/备注。共享日志模块必须为写入设置独立的短超时；如果数据库本身不可用、日志表不可写或日志写入超时，异常处理器立即退回到容器标准错误输出写一条脱敏结构化日志并携带 `requestId/traceId`，供 Docker 日志排查，不能静默丢弃、阻塞原响应或为了写日志无限重试。本期不额外引入外部日志平台。
- 认证与账号安全事件（登录、锁定/解锁、激活、密码重置、手机号同步、内部令牌校验失败等）按 backstage PRD §8 写入安全日志表，同样经共享日志模块的受限预定义语句写入，不承载业务数据；安全日志写入失败的处理与系统日志相同（退回容器标准错误输出），不阻断原认证流程的响应。
- 业务审计：权限变更、审批、资产调度、库存流水、财务操作记录等均保留操作者、时间与变更前后内容，不可覆盖或删除。
- **操作日志**：全站所有功能的增删改与导出操作按统一结构记录（字段、模板与查询要求见 §3.3）；每个模块在自己的 schema 内随业务事务写入，管理后台只通过联合只读视图汇总查询，后端不提供修改或删除接口。
- 运行日志与跨服务调用统一携带 `requestId/traceId`，并记录服务、路由模板、结果类别、HTTP 状态、耗时和下游服务；不记录密码、Cookie、钉钉凭证、完整手机号、文件预签名地址或其它敏感数据。
- 全局异常日志与面向用户的错误响应分离：日志可保留排障所需的受控内部信息，用户响应不得包含堆栈、SQL、文件路径、密钥或第三方原始错误。

### 9.4 模块边界与优雅降级

- 各逻辑模块共享 PostgreSQL 实例，生产镜像版本按 §1.3 始终统一到同一 Git commit。schema 仍按逻辑模块归属：`platform-core` 同时承载并拥有 `base` 与 `backstage` schema，asset、hr、fin 服务分别拥有同名 schema。任何业务表只能由其归属模块的 Repository 写入；同一 `platform-core` 进程内的 base/backstage 协作必须调用对方公开的应用服务/命令接口，不能直接导入对方私有 Repository，但需要账号、权限、资料审批等原子变更时可以由明确的编排服务让两个模块参与同一个 PostgreSQL 事务。不同部署单元之间的新增、修改、审批、扣库存等业务动作必须调用目标服务接口，禁止跨 schema 直接写入。
- 平台基础设施仅有两项集中写入例外：backstage PRD §8 集中错误日志与安全日志允许共享日志模块执行受限新增/聚合，§9.1 统一后台任务表允许共享任务模块执行受限创建与状态条件更新；两张表均位于 `backstage` schema 并由 `platform-core` 内的 backstage 模块迁移拥有，能力均不开放任意 SQL，也不授予其它跨 schema 业务写入语义。**审批超时自动取消扫描（主 PRD §3.2）为第三项书面豁免**：worker 的 APPROVAL_TIMEOUT_SCAN 处理器经 `@wbme/approval` 共享超时模块对 backstage/hr/asset 三 schema 同构的 `approval_requests` 执行受限条件更新（仅 PENDING 且超时、按 status+version 条件置 CANCELLED + 写 AUTO_CANCEL 动作），并允许同事务挂接业务占用释放 hook（如 asset 申领/库存变更释放）；该豁免仅限审批超时取消这一基础设施行为本身，schema 与操作均受共享模块白名单约束、不开放任意 SQL，asset/hr 自身业务写入仍必须调用各自服务接口。**图片孤儿清理的注册表同步删除为第四项书面豁免**：worker 的 IMAGE_CLEANUP 处理器按 §9.1 删除未关联过期图片对象后，同步删除 `backstage.image_objects` 中对应注册表行（防注册表无界增长、已删对象继续签发预签名 URL）；该操作仅限「对象已物理删除的注册表行」这一清理语义本身，不开放任意 SQL。
- **组织数据归属**：部门、岗位、职称规则和用户组织关系属于 hr schema，由 hr 服务唯一负责业务写入；`platform-core`、asset、fin 可通过经评审的只读视图读取权限计算、身份展示和历史关联所需的最小字段，因此 hr 容器停止不会让既有组织快照或数据范围读取失效。当前职称由 hr 拥有的只读视图根据 hr 组织/规则数据与 backstage 提供的最小站点角色只读视图实时派生，不在两个模块间复制当前职称；两端视图字段与迁移依赖按接口契约管理。组织编排、岗位审批和用户恢复兼容性处理仍必须调用 hr 内部接口，不能因共享数据库或拥有只读视图而直接修改 hr schema。用户批量恢复按 backstage PRD §3 采用"hr 整批处理成功后，`platform-core` 再在本地事务内处理账号与仍有效权限"的安全顺序；hr 不就绪时整个恢复请求停止，不产生部分恢复。
- 内部 REST 只用于**不同部署单元**之间的调用，统一使用 `/internal/v1` 前缀，只在 Docker Compose 私有网络中监听或路由，Nginx 不得把该前缀暴露到公网；base 与 backstage 在 `platform-core` 内通过类型明确的进程内接口调用，不为形式上的"服务化"绕一圈 HTTP。跨部署单元调用使用一个全平台共享的高熵内部令牌：令牌由部署环境注入，不写入代码、数据库、前端或日志；请求通过 `Authorization: Bearer <token>` 携带，并同时传递固定枚举的调用方服务名与 `requestId/traceId`。目标服务使用恒定时间方式校验令牌，并按"内部路由 → 允许调用方服务"白名单授权；令牌错误返回 `401`，调用方无权访问该路由返回 `403`，两者只记录脱敏安全事件。
- 由于所有服务共享同一令牌，调用方服务名白名单主要用于限制正常调用路径和防止误用，不能抵御某个已泄露令牌的服务伪装成另一服务；本期在"同一 ECS、同一受控 Docker 私网、无第三方服务接入"的边界内接受这一风险。
- 共享内部令牌只证明请求来自平台可信服务范围，不等于用户权限。用户触发的跨服务动作必须携带实际操作者用户标识和业务幂等键，目标服务仍按该内部场景的权限、数据范围和业务规则校验，不能因持有内部令牌获得任意业务能力。
- 内部 REST 调用必须设置明确连接/响应超时；只有幂等读取或携幂等键的写入才允许有上限重试，不得无限重试。令牌轮换通过更新统一部署机密并重启已启用服务完成；本期不引入内部 JWT、mTLS、逐服务密钥或独立服务认证中心。当服务迁移到不同主机、接入非本项目服务或共享令牌的信任边界不再可接受时，再升级为逐服务身份方案。
- 调用前可使用系统产品状态和健康状态作为快速判断，但调用方仍必须正确处理实际超时、连接失败和 `503 Service Unavailable`，不得假设预检成功后目标服务一定可用。
- 目标服务不可用时，调用方统一返回可识别的 `DEPENDENCY_UNAVAILABLE` 错误与目标系统名称，前端提示"目标系统当前不可用，本次操作未提交"；当次操作不得留下对用户不可见的半完成业务数据。
- 目标服务已正常响应 §9.5 约定的 `BUSINESS/VALIDATION/AUTHORIZATION/CONFLICT` 错误时，调用方应保留其业务域、错误码和安全文案，不得笼统改写为"依赖不可用"；只有连接失败、超时、无效响应或目标服务 `5xx` 才归为 `DEPENDENCY`。调用方必须校验下游错误响应结构，不能把未验证的第三方或旧服务错误正文直接透传给前端。
- 例如后续的工程养护系统向资产系统提交申请时，如 asset 服务已停止、未就绪或调用超时，工程养护系统不得将本地记录标记为"已提交资产系统"，必须保留用户已填数据并明确提示目标系统不可用，由用户稍后重试。
- 确需在多个服务中持久化结果的跨模块动作，必须在开发前明确主服务、执行顺序、幂等键、失败补偿或对账方案，不以 Redis 锁替代失败恢复设计。

### 9.5 REST API 契约与输入校验

- 业务接口使用统一版本前缀（本期为 `/api/v1`）；每个接口定义明确的输入 DTO、输出 DTO、权限要求、数据范围、可能错误码和幂等语义，并同步生成 OpenAPI 文档。
- 所有 HTTP 路径、查询、请求体、文件上传、钉钉回调和第三方返回数据均在系统边界按白名单校验；未声明字段直接拒绝，字符串长度、数值范围、枚举、日期时区、排序字段和批量数量必须有明确约束。
- 除业务章节已经声明其它上限的导入等专用端点外，批量删除、批量注销/恢复、批量撤权及其它通用批量写接口每次最多接受 **100 个互不重复的目标标识**；这是受版本控制的固定资源上限，不放入系统设置，也不允许请求自行提高。超出上限、数组为空或包含重复标识时在进入业务事务前返回统一 `VALIDATION` 错误；该限制不改变 §2.6 的整批成功或整批回滚语义。
- 列表接口从首版开始强制服务端分页与稳定排序，统一返回 `data` 与 `pagination { page, pageSize, totalItems, totalPages }`；全站默认每页 20 条，用户可切换 10、20、50、100 条，服务端最大接受 100 条，不接受无上限列表查询。业务确有不同上限时必须在对应章节明确声明，不能由页面任意传入更大值。导出接口不复用列表页 `page/pageSize`，而按明确的"所有/已筛选"范围和独立导出上限处理。
- 错误响应统一为 `error { type, domain?, code, message, details?, requestId }`。`type` 是稳定错误大类，固定为 `BUSINESS / VALIDATION / AUTHENTICATION / AUTHORIZATION / CONFLICT / RATE_LIMIT / TIMEOUT / DEPENDENCY / SYSTEM` 之一；仅 `BUSINESS` 必须返回业务域 `domain`。`TIMEOUT` 表示服务器已接受请求，但该操作超过自身定义的处理时限；连接或响应下游服务超时仍归入 `DEPENDENCY`，不能混用。`code` 是该类型或业务域内稳定的机器可读编码，`message` 是经过服务端控制、可向当前用户展示的文案，`details` 只承载字段校验、冲突对象等经过白名单定义的结构化信息。响应不得包含异常类名、堆栈、SQL、数据库约束名、文件路径、密钥、第三方原始响应或其它内部细节。
- HTTP 语义统一：`400` 请求格式错误，`401` 未登录/会话失效，`403` 已登录但不允许操作，`404` 资源不存在或超出数据范围，`409` 版本/状态/唯一性冲突，`413` 上传请求体超过端点固定上限，`422` 业务校验失败，`429` 超出频率或同用户并发额度，`503` 本服务/依赖服务不可用或服务端处理超过预定义时限。
- 新建、提交申请、审批、扣库存、批量操作、手动备份等重要写入接口支持幂等键；使用同一幂等键和同一规范化请求重试时返回原结果，不得重复产生业务结果，复用同一键却改变请求时按 §3.3 返回冲突。部分更新使用 `PATCH`。除 §2.6 明确允许的财务金额明细单条硬删除外，独立实体删除统一使用批量接口，即使只删除一个对象也提交单元素标识数组；普通实体执行软删除，字典/分类/库位/部门/岗位等配置类数据执行按 §2.6 的确认式硬删除。**删除幂等不通过忽略错误目标实现**：同一幂等键的网络重试可返回第一次的成功结果；但新的删除意图若包含不存在、已软删除、已被物理删除、状态不允许或无权操作的目标，必须返回逐项目标原因并按 §2.6 整批不变更，不能把随机错误 ID 当作成功。金额明细使用所属项目下的单条删除接口，成功后返回最新项目汇总与版本号；同一幂等键重试原删除可返回原结果，使用新幂等键删除不存在的明细则返回资源不存在，不得改变汇总或重复写入删除审计。
- 重要写入的幂等键由客户端为一次用户意图生成并在网络重试时保持不变，具体持久化与冲突规则复用 §3.3 的操作日志，不建立独立 PostgreSQL 中间表；Redis 仅缓存近期返回结果。业务申请、库存占用、额度占用、任务状态等本身属于正式业务事实，仍按各章节持久化，不视为可只存 Redis 的请求中间数据。

### 9.6 统一请求处理链路

- **请求上下文中间件**：在请求进入时生成或校验 `requestId/traceId`，建立当前用户、来源、服务与请求起始时间上下文；不信任客户端提供的任意追踪值。
- **全局校验管道**：NestJS 统一启用 DTO 转换、白名单和非白名单字段拒绝；转换失败不得进入业务服务。
- **认证与授权守卫**：默认所有面向用户的路由需要登录，仅手机号 + 密码登录、登录/注册/邀请激活所需的钉钉授权发起与回调、持限时一次性注册/激活/恢复会话的资料完善与密码重置、健康探针显式标记为公开；内部路由改为执行 §9.4 的服务令牌与调用方白名单校验。用户路由依次校验系统可用性、功能权限和粗粒度数据范围，业务查询/事务再校验具体资源归属，防止越权访问。
- **全局拦截器**：统一记录访问结果和耗时、采集指标并执行请求超时；流式下载、SSE 和备份/恢复等长任务使用单独超时策略，不被普通 HTTP 超时误中止。
- **业务异常体系**：共享基础包提供与 HTTP 传输解耦的 `BusinessException` 基类；异常对象只携带业务域、错误码和经过定义的详情参数，不继承 `HttpException`，也不允许调用处任意指定 HTTP 状态。各业务模块维护自己的错误码目录和薄封装，例如 `ApprovalBusinessException`、`InventoryBusinessException`、`HrBusinessException`、`FinanceBusinessException`。MVP 业务域至少包括 `ACCOUNT / PERMISSION / APPROVAL / ASSET / INVENTORY / HR / FINANCE / EXPORT / BACKUP / INTEGRATION`。每个目录项集中定义唯一 `code`、默认安全文案、由全局过滤器使用的 HTTP 状态和允许公开的 `details` 结构；业务代码只抛出目录中已注册的错误，不能临时拼接错误码，也不需要为每个错误再创建一个空壳异常类。典型示例为 `BUSINESS + INVENTORY + INSUFFICIENT_STOCK`。
- **单一全局异常过滤器**：每个 NestJS 服务通过依赖注入令牌 `APP_FILTER` 注册一个 catch-all 过滤器，并按确定顺序识别和映射异常：`BusinessException`；DTO/管道校验异常；认证与授权异常；已知状态或唯一性冲突；限流异常；本服务已定义的操作超时；Redis、OSS、数据库连接和下游服务等依赖异常；最后才是未知异常。不要串联多个都可能捕获同一异常的全局过滤器，也不要在控制器中重复拼装错误响应。
- **业务异常处理**：`BusinessException` 表示请求合法但不满足明确业务规则，可按目录映射为 `404/409/422` 等状态，返回具体安全文案和受控详情；它属于预期业务结果，写请求访问日志和必要的业务审计，但默认不追加"系统日志"，避免把库存不足、状态已变化等正常拒绝当成 BUG。业务异常不得包裹数据库断连、空指针、未知第三方响应或其它程序/基础设施故障。
- **其它异常处理**：字段格式和 DTO 校验返回 `VALIDATION`；未登录与无权访问分别返回 `AUTHENTICATION/AUTHORIZATION`；明确可识别的唯一约束、审批版本或状态竞争返回 `CONFLICT`；限流或同用户并发额度占用返回 `RATE_LIMIT`；本服务已定义的处理时限到期返回 `TIMEOUT`；Redis、OSS、数据库连接或下游服务不可用/超时返回 `DEPENDENCY`；无法可靠分类的异常一律返回 `SYSTEM`、HTTP `500` 和通用文案"系统处理失败，请稍后重试"，并携带 `requestId`。除预期的业务/校验/认证授权拒绝外，重要依赖异常和所有未知异常必须由过滤器自动追加 backstage PRD §8 系统日志，保存脱敏后的异常类型、堆栈、cause 链、服务和追踪标识；日志写入失败不能覆盖原始响应或递归触发异常处理。由用户取消或触发预定义资源上限产生的 `TIMEOUT` 默认只记录访问结果；若超时源于数据库语句异常、Worker 无法终止或其它非预期故障，再追加系统日志。
- **错误目录治理**：错误类型、业务域、错误码和默认文案属于接口契约，统一定义、自动生成 OpenAPI 枚举并用测试校验"域内错误码唯一、状态映射存在、公开详情符合白名单"。修改展示文案不改变错误码；删除或复用已发布错误码属于破坏性变更，必须按接口版本流程处理。前端只依据 `type/domain/code` 决定交互，不解析 `message` 文案猜测错误类型。
- 通用拦截器只能记录请求级访问结果，不能代替操作日志或领域审计；新增、修改、软删除等操作日志按 §3.3 写入当前模块 schema，权限变更、审批、库存、财务等需要前后值的领域审计记录也必须由业务服务在同一数据库事务中显式写入。

### 9.7 Web 安全基线

- 平台仅通过 HTTPS 对外提供服务；统一设置 CSP、HSTS、`X-Content-Type-Options`、防点击劫持、`Referrer-Policy` 等安全响应头，CORS 仅允许明确配置的平台域名且不使用通配来源。
- 服务端会话 Cookie 必须启用 `httpOnly`、`secure` 与适合登录回调的 `sameSite` 策略；所有使用 Cookie 认证的状态变更请求必须校验 CSRF 防护凭证，钉钉回调同时校验一次性 `state/nonce`。
- 平台密码按 base PRD §2 只校验 8～32 个字符，并使用 Argon2id 或等价的成熟自适应算法加盐哈希、不可逆存储；密码、钉钉凭证和会话标识不进入前端持久存储或普通日志。
- 登录、钉钉授权发起/回调、邀请校验与激活、密码重置、文件上传、导出、批量操作和跨服务接口分别设置可配置限流；超限返回 `429` 与可理解的重试提示。
- 数据库连接串、钉钉应用密钥、OSS 凭证、Cookie 签名密钥、内部服务令牌等属于部署级机密，从环境或专用机密管理能力注入，不存入可由业务管理员修改的普通设置表，不提供前端明文回显。

### 9.8 Redis 单实例与故障降级

- 本期在开发环境和生产环境均只部署 **1 个 Redis 容器**，由 `platform-core`、asset、hr、fin 与 BullMQ Worker 共享；不建设 Redis Cluster、哨兵或读写副本。各用途使用固定命名空间和最小权限连接，避免会话、限流、队列、配置广播与分布式锁键相互覆盖。
- Redis 使用持久化数据卷并启用 AOF（`appendonly yes`，`appendfsync everysec`）与周期 RDB 快照；内存淘汰策略使用 `noeviction`，不得为了继续写入而静默淘汰会话或 BullMQ 键。Redis 数据不是 PostgreSQL 业务事实来源，极端情况下 Redis 数据无法恢复时允许全部会话失效，用户重新登录；§9.1 调度器依靠 PostgreSQL 统一任务事实表重新投递允许安全重放的非终态后台任务，配合业务幂等规则保证不因队列重建造成业务数据重复或丢失。已经生成 backstage PRD §10 外部恢复控制清单的数据库恢复不属于可自动重投任务，Redis 丢失后仍保持维护状态并等待超级管理员处理。
- Redis 容器提供健康检查。所有启用的后端服务和 Worker 在开发、测试、生产环境启动时均执行 Redis 启动前置检查：在限定时间内完成连接、`PING` 以及带短 TTL 的读写删除探测；检查未通过则进程以非零状态退出，不监听业务端口，也不得退化为进程内会话、进程内限流或进程内队列。Docker Compose 可按重启策略在 Redis 恢复后重新拉起服务。
- backstage PRD §10 的独立恢复执行器是上述 Redis 启动强依赖的唯一基础设施例外：它在普通状态下不接受面向用户的业务请求，恢复接管后的状态和受限控制会话刻意不存 Redis，因此 ECS 重启或 Redis 已被清空时仍必须能够启动、读取数据库外清单并持续保持维护状态。该例外不得扩展到 `platform-core`、asset、hr、fin 或普通 Worker，也不得被用来提供任何绕过 Redis 会话校验的业务接口。
- 服务正常运行期间 Redis 连接失效时，服务保持存活探针可用但立即将就绪探针标记为失败，停止接受新的 Redis 依赖操作：登录、会话校验与续期、密码重置流程、权限授权变更、依赖 Redis 的限流写入、异步任务提交、任务消费、配置广播以及使用分布式锁的操作统一返回 `503` 与 `DEPENDENCY_UNAVAILABLE`。由于受保护接口需要从 Redis 读取服务端会话，Redis 故障期间除健康探针等明确公开接口外，平台业务整体表现为暂时不可用；不得绕过会话校验继续提供业务接口。
- Redis 失效前已经完成认证并进入数据库事务的请求，可在不再依赖 Redis 且数据库约束足以保证正确性的前提下完成；不得仅因 Redis 锁消失而放宽数据库并发校验。Worker 停止领取新任务，正在执行的普通任务按其幂等和事务边界安全结束或失败，恢复后由卡死任务检查和数据库任务状态重新调度；数据库恢复执行阶段继续遵循 backstage PRD §10 的外部控制清单和禁止自动重试规则。
- Redis 连接恢复后，服务必须重新执行完整健康探测、从数据库刷新运行参数与必要缓存，再恢复就绪状态和相关功能；恢复过程自动完成，不要求维护者逐个服务手工启用。记录 Redis 失联、降级、恢复时间和受影响服务，但不记录会话内容或键值。
- backstage PRD §10 的 PostgreSQL 整库恢复是本节普通 Redis 故障恢复之外的特殊情况：即使 Redis 本身健康，也必须在维护状态下清空本平台 Redis 数据集并从恢复后的数据库重建，不能继续使用跨越数据库恢复点的会话、缓存、锁或队列状态。

### 9.9 数据库结构迁移与低维护发布

- Prisma 的迁移与 Client 以**部署单元**为边界。`platform-core` 使用一份按领域拆成多个 `.prisma` 文件的 multi-file Schema，在同一 datasource 中声明 `base`、`backstage` 两个 PostgreSQL schema，并用每个模型的 `@@schema` 明确归属；它统一生成一个 Prisma Client、一个迁移目录和一套迁移历史，从而让两个逻辑模块可使用同一个事务客户端完成原子操作。模型文件、NestJS 模块与 Repository 仍按 base/backstage 隔离，不因 Client 合并而开放互相任意访问。asset、hr、fin 各自维护本部署单元的 Prisma Schema、Client 与迁移历史。跨 schema 只读视图（§3.3 操作日志联合视图、hr 职称视图、backstage 站点角色只读视图等）**不纳入任何部署单元的 Prisma 迁移序列**：它们之间存在跨部署单元循环依赖（联合日志视图依赖 asset/hr/fin 的日志表，而 hr 职称视图依赖 backstage 的角色视图），单一线性迁移顺序无法同时满足。视图定义由明确的拥有模块维护为受版本控制的幂等 SQL 脚本（`CREATE OR REPLACE VIEW`），由 Migration Runner 在全部部署单元的表结构迁移完成后统一执行；backstage PRD §10 恢复流程的正向迁移步骤同样包含该视图脚本执行；视图字段变更按接口契约管理，随正常版本发布生效。backstage PRD §8 集中错误日志表与安全日志表、§9.1 统一后台任务表及其索引在 `platform-core` 迁移中仍归 backstage 领域模型维护，其它模块复用共享日志/任务模块，不各自声明或迁移这些表。生产环境禁止使用 `prisma db push` 直接改变结构，已提交和已执行的迁移文件不得改写。
- **迁移历史隔离**：虽然四个部署单元连接同一 PostgreSQL 数据库，但它们的迁移目录不是同一条 Prisma 迁移历史，因而不得共用一张 `_prisma_migrations` 表。各 datasource/Prisma Config 使用不同的 PostgreSQL 默认 schema 保存迁移元数据：`platform-core → base`、`asset → asset`、`hr → hr`、`fin → fin`；`platform-core` 的这一张表同时代表 base/backstage 的唯一合并迁移序列。Migration Runner 必须按上述配置顺序执行并校验各自历史，不能把四个迁移目录交替对照同一迁移表，也不能因迁移文件恰好同名而判定其它部署单元已经执行。整库备份和恢复必须包含这四张迁移历史表。
- 本期应用侧只配置**一个 PostgreSQL 连接账号**，所有后端服务、Worker、Migration Runner 和备份任务复用该账号，不按服务拆分数据库角色或密码。该账号具备各模块 schema、迁移和经评审只读视图所需权限；"业务写入只通过拥有模块，并仅通过共享模块写集中系统日志与统一后台任务表"的边界由代码模块、接口约定、迁移归属和评审约束保证，不依赖数据库账号隔离。连接凭证统一由部署环境注入；每个后端部署容器使用一个独立连接池，`platform-core` 内 base/backstage 共享该容器连接池而不重复各建一池，并按 PostgreSQL 总连接上限统一配置池大小，避免多个服务合计耗尽连接。
- 为减少维护负担，项目提供唯一的自动化部署入口：开发环境的启动脚本与生产环境的单条发布命令都先运行一次性 Migration Runner，再启动或更新后端服务。Runner 按部署单元及其声明的依赖顺序执行 `prisma migrate deploy`，其中 `platform-core` 只执行一次而不是分别迁移 base/backstage；维护者不需要逐个进入容器执行迁移，无待执行迁移时该步骤直接成功退出。
- 数据迁移不由每个业务服务在启动时自行执行，避免多个容器并发迁移或某个独立服务启动时意外修改共享数据库。每个部署单元启动时只校验自己声明拥有和依赖的 schema 版本；`platform-core` 必须同时校验 base 与 backstage，任一迁移未完成、失败或版本不兼容时都不得进入就绪状态。
- 发布入口在检测到待执行迁移时自动创建并校验一次"立即备份"，随后执行迁移；迁移失败即停止本次新版本启动并输出明确的失败模块和迁移编号，不自动回滚未知的 DDL。需要跨版本共存或影响共享视图的变更采用"先新增兼容结构 → 迁移数据 → 后续版本删除旧结构"，普通的模块内部兼容变更无需人为拆成额外发布步骤。
- Migration Runner 使用上述统一应用数据库账号，不另设专用账号；它不承载 HTTP 接口，执行完成即退出。同一数据库同一时刻只允许一个发布迁移任务；迁移结果、耗时和失败原因写入发布日志，便于少量维护人员用一条命令完成部署并定位问题。
- **生产版本只前进、不回滚**：生产发布命令只接受当前成功部署 commit 的后继 commit，并统一更新全平台组件；禁止把任一生产容器切换到旧 commit、旧镜像或与其它组件不同的版本。生产缺陷通过开发环境验证后的新修复 commit 向前发布，不设计应用版本回滚按钮、回滚命令或数据库降级迁移。数据库备份恢复仅用于数据损坏、误操作等灾难恢复，不属于应用版本回滚，也不得借恢复旧数据库来运行旧代码。

### 9.10 日期、时间与时区

- 本平台使用者均在中国，本期业务时区固定为 `Asia/Shanghai`，不提供个人时区切换，也不设计跨时区展示规则。会话期限、创建/修改/处理时间、系统日志和任务执行时间等"时间点"在 PostgreSQL 使用带时区时间类型并规范化为 UTC 存储；API 使用带 `Z` 或明确偏移量的 RFC 3339/ISO 8601 字符串，前端统一转换为北京时间展示。
- 加班日期、合同开始/完工日期等不表示具体瞬间的"自然日"使用 PostgreSQL `date`，项目年度使用 `1000～9999` 的四位整数，不经 UTC 换算。加班起止时间按北京时间的业务日期与分钟值保存；当日结束值 `24:00` 只作为该业务日期的结束边界，不被错误显示成次日申请。
- 自然月/季/年额度周期、加班补交窗口边界和每日备份等业务调度均以 `Asia/Shanghai` 计算边界；节假日 API 的日期请求和响应也必须按北京时间自然日解释。数据库比较时间点时仍使用 UTC。Excel 中的纯日期按北京时间日历值导入导出，不因服务器、容器或浏览器时区发生前后一天偏移。

### 9.11 金额与十进制精度

- 财务合同金额、开票、收款、分包付款、费用、资产金额、消耗品单价等人民币金额统一使用 PostgreSQL `numeric(18,2)`，单位为元；数据库约束小数位不超过两位。所有声明为手工输入的金额与单价必须大于等于 0，允许为 0；服务端 DTO 和数据库检查约束均拒绝负数，不能只依赖前端控件。自动计算字段可以按业务公式得到负数，尤其是剩余未开票、剩余未收款和暂定保通权益，不得统一截断为 0。金额输入、业务计算、汇总、比较和 Excel 导入导出全程使用 Prisma `Decimal` 或等价成熟十进制定点类型，禁止使用 JavaScript `number` 承担金额计算或把金额先转成二进制浮点数再入库。
- REST DTO 中金额使用规范化十进制字符串传输，例如 `"1234.50"`；前端金额输入统一使用 Ant Design `InputNumber<string>` 的 `stringMode`，从 `onChange` 取得字符串或空值，不从 DOM `event.target.value` 读取格式化后的显示文本，也不得在校验、编辑缓存或提交前转换为 JavaScript `number`。仅在展示层格式化千分位；服务端统一校验格式、范围和小数位，计算结果需要落到分时使用十进制四舍五入，不得由不同页面各自实现舍入规则。
- 毛利率等比率不按金额精度截断：使用十进制数至少保留 8 位内部小数参与计算和汇总，内部以 `0.25` 表示 25%，API 按十进制比率字符串传输；最终 Web 使用百分比格式、Excel 使用数值单元格与 `0.00%` 数字格式，均把 `0.25` 展示为 `25.00%`。累计收款为 0 时继续按业务规则显示"—"，不执行除零。自动金额从明细按十进制实时计算，不保存或信任前端上传的浮点计算结果。

### 9.12 Docker 容器日志轮转

- 开发与生产 Docker Compose 中的 Nginx、各后端服务、Worker、Migration Runner、PostgreSQL、Redis 及其它全部容器统一显式使用 Docker `local` 日志驱动，不依赖 ECS 主机可能仍为无轮转 `json-file` 的默认配置。通过 Compose 扩展字段/YAML 锚点复用同一配置，避免新增服务时漏配。
- 每个服务的 `logging` 固定为 `driver: local`，选项固定为字符串 `max-size: "20m"`、`max-file: "5"`、`compress: "true"`；单个容器最多保留 5 个、每个约 20MB 的轮转文件，即轮转前名义上限约 100MB，旧文件自动删除且轮转文件启用压缩。该上限按容器分别计算，不是全平台合计 100MB。
- 应用和基础设施运行日志输出到 stdout/stderr，由 Docker 日志驱动统一接管；除 PostgreSQL/Redis 正式数据卷和本 PRD 明确要求的持久文件外，不允许服务在容器文件系统或挂载目录另建无轮转运行日志文件。不得直接读取或修改 Docker `local` 驱动的内部日志文件，排查统一使用 `docker compose logs`。
- 修改日志驱动或选项后必须重新创建容器才会生效；部署入口在启动后使用 `docker inspect` 校验每个应运行容器的日志驱动、`max-size`、`max-file` 和压缩配置，任一容器缺失或不一致则发布检查失败。Compose 配置提交前同时执行 `docker compose config` 校验展开结果。
- Docker 轮转日志只承担近期运行排障和 §9.3 数据库不可写时的兜底，不替代 PostgreSQL 集中系统日志、操作日志或领域审计；容器被删除后其本地轮转日志可能一并消失，本期不承诺跨容器重建长期保留，也不因此引入外部日志平台。

### 9.13 容器持久化、资源边界与优雅停机

- PostgreSQL 与 Redis 必须分别使用显式命名、固定挂载位置的 ECS 持久化数据卷，不得把正式数据写在容器可写层或匿名卷中；数据库恢复维护标记、恢复控制清单和生产发布状态同样使用权限隔离的固定 ECS 持久化目录。普通发布、容器重建和单个服务上下线不得删除或重新初始化这些目录，生产部署入口禁止执行会删除数据卷的命令；首次初始化与既有数据启动必须使用不同的显式检查分支，发现非空数据目录时不得再次执行初始化脚本覆盖数据。
- Compose 为 PostgreSQL、Redis、Nginx、启用的后端、Worker 和恢复执行器配置健康检查、合理的重启策略及依赖就绪顺序；`depends_on` 只用于启动编排，服务自身仍必须执行适用于自身的 Redis 探测、数据库/schema 版本检查和其它必要依赖检查，不能把"容器已启动"当作"服务已就绪"。恢复执行器的就绪检查重点覆盖恢复状态目录的读写能力、受限控制通道及数据库/OSS 配置是否完整，不要求空闲时实际执行恢复；目标 PostgreSQL 或 OSS 当前不可连接时应在恢复状态中报告依赖失败，但不能因此让已存在未完成清单的恢复控制路由也无法访问，因为恢复本来就可能用于处理数据库损坏。ECS 或 Docker 重启后，原本配置为启用的服务和恢复执行器应自动恢复，产品状态为"即将上线"不要求启动对应业务容器。
- 每个容器设置与 ECS 规格相符的内存/CPU 边界和进程内并发上限；Node.js 堆上限、Worker Threads 池、HTTP 并发、数据库连接池和 BullMQ Worker 并发必须按同一资源预算配置，不能分别取满主机资源。PostgreSQL 总连接上限须为数据库自身和恢复/迁移保留余量；达到应用资源上限时排队或返回统一的限流/暂时不可用错误，不允许继续无界创建线程、连接、缓冲区或任务。
- 后端或 Worker 收到 `SIGTERM` 时先立即把就绪探针置为失败并停止接收新 HTTP 请求、新队列任务和新调度，再在固定有界时间内等待已进入请求或任务到达安全事务边界，最后关闭 HTTP、PostgreSQL、Redis 和 OSS 客户端后退出。超过宽限期的请求必须取消并回滚未提交事务；可安全重放的后台任务依靠 §9.1 执行租约恢复，不可重放的数据库恢复继续按 backstage PRD §10 保持维护状态并要求人工确认。生产发布和运维停止统一使用该优雅停机流程，不直接强制杀死仍在写事务中的进程。
- 健康状态页增加 PostgreSQL/Redis 数据卷与 ECS 持久化目录的磁盘剩余空间状态，只展示正常、预警、严重及使用率，不暴露主机路径；固定预警阈值属于部署安全常量，不放入业务设置。达到严重阈值时停止接受新的文件上传、Excel 导入及备份任务并明确提示空间不足，已有普通数据库写入是否继续由 PostgreSQL 实际可写状态决定，不能通过自动删除业务数据、审计日志或未过保留期备份腾挪空间。

### 9.14 单 ECS 部署安全边界

- ECS 安全组与主机防火墙只向公网开放 Nginx 的 HTTP/HTTPS 入口；HTTP 仅用于跳转 HTTPS。SSH 仅允许维护者固定来源或受控运维通道并使用密钥认证，不开放密码登录。PostgreSQL、Redis、业务容器端口、`/internal/v1` 和恢复执行器控制端口只存在于 Compose 私有网络，不发布到公网或主机全网卡；免登录健康探针也只经 Nginx 返回 backstage PRD §11 的最小状态，不直通容器管理端口。
- 任何 Web 后端、Worker、Nginx 或数据库容器都不得挂载 Docker Socket、使用 `privileged`、`host` 网络或无关主机目录；恢复执行器通过维护标记、受限内部控制通道和数据库连接排空协议协调恢复，不能因需要停写就把宿主机 Docker 根权限交给可被 HTTP 触达的容器。容器尽可能使用非 root 用户、删除不需要的 Linux capabilities、只读根文件系统与有界 `tmpfs` 临时目录；确需写入的 PostgreSQL/Redis 数据卷及 backstage PRD §10/§9.13 持久目录单独按最小 UID/GID 和读写权限挂载。
- 数据库、Redis、钉钉、OSS、Cookie、内部服务与配置加密密钥通过生产部署的权限受限环境文件或等价机密注入，文件不进入 Git、镜像层、Compose 展开输出、更新日志或普通备份清单，宿主机权限仅允许运行账号读取。不同环境使用不同密钥和 OSS 前缀；开发环境不得复用生产凭证或直接连接生产数据库。
- ECS 与所有容器统一使用可靠时钟同步，应用仍按 §9.10 处理业务时区；时钟明显未同步时涉及 OAuth `state/nonce`、会话到期、预签名 URL、任务租约和备份调度的服务不得进入就绪状态。生产部署检查同时验证公网端口、容器特权/Socket 挂载、数据卷、日志轮转和时钟状态，失败时阻止本次发布完成，不依赖维护者逐项手工核对。

## 10. 前端总体需求

> 本节只保留技术选型与前端功能规则；页面布局、组件、视觉与交互细节由开发阶段设计，不在本 PRD 限定。
> **表格通用交互模式**（见 10.2）为产品既定设计，全站表格页面必须遵循。

### 10.1 技术约定

- 前端统一使用 **Ant Design v6**（组件库、风格、色彩），不引入其它 UI 体系；React 版本必须满足 Ant Design v6 的官方兼容要求且不得低于 React 18，若显式安装 `@ant-design/icons` 则使用与 antd v6 兼容的 v6 主版本。应用根节点的 `ConfigProvider` 直接使用 `docs/for-frontend/ant-design/theme.json` 作为项目唯一主题种子配置；组件选择、状态语义、间距与 Token 使用遵循 `docs/for-frontend/ant-design/design.md`，其中默认示例值与 `theme.json` 冲突时以项目主题配置为准。业务页面不得另写一套全局颜色、圆角、字体或间距常量，也不得硬编码主题色替代 Ant Design Token；主题变更只修改集中配置。
- 利润分析桌面端明确使用 Ant Design `Table` 的 Editable Cells 范式实现（不引入 AG Grid、RevoGrid、react-data-grid 或其它表格 UI 体系）；全部金额输入按 §9.11 使用 `InputNumber<string>` 的 `stringMode`。移动端复用同一数据与保存接口；编辑确认与即时保存遵循 fin PRD §4。
- 本期"类 Excel"只表示二维表格内直接编辑与连续录入，不实现公式栏、多区域选择、填充柄、任意多单元格粘贴或浏览器内 Excel 文件编辑；Excel 导入导出仍由 fin PRD §4 的独立功能和后端模板完成。若后续明确需要这些高级交互，再单独评估开源表格引擎并经需求确认。

### 10.2 表格通用交互

> 本节为表格通用交互设计，适用于全站所有表格型列表（资产台账、库存、审批中心、操作日志、用户管理、项目列表等）。

- 表格上方不放置散落的筛选选择器、搜索框或排序控件，统一只提供 **"筛选"** 与 **"排序"** 两个操作入口。业务章节中"可按 XX 筛选/搜索"的表述表示该表格支持的**可选筛选字段清单**，呈现形式一律通过筛选面板实现；"关键字"作为筛选面板中的一种特殊字段提供（对多个文本字段执行模糊匹配），不单独放置搜索框。

**高级筛选器**

- 点击"筛选"后打开**高级筛选**面板（桌面端为居中弹窗，移动端为抽屉），承载全部筛选编辑；可动态添加、移除筛选项，每个筛选项由三部分组成：**字段、符号、值**。编辑过程不触发查询，点击"确定"后统一提交生效；底部提供"重置 / 取消 / 确定"，"重置"清空所有条件并恢复为 1 条空条件行。
- **字段**：可搜索选择该表格适合筛选的字段，按字段类型分组展示；字段清单由开发阶段按业务定义，业务章节"可按 XX 筛选"即候选字段。
- **符号**：符号集按字段类型适配，选中字段后自动刷新可选符号——
  - 文本：等于、不等于、包含、不包含、开头是、结尾是、为空、不为空；
  - 数字/金额：等于、不等于、大于、小于、大于等于、小于等于、介于、为空、不为空；
  - 日期：等于、不等于、早于、晚于、区间、今天、本周、本月、过去 7 天、过去 30 天、为空、不为空（相对日期符号由服务端按 Asia/Shanghai 当天动态求值）；
  - 字典/枚举/远程引用：等于、不等于、为空、不为空；
  - 其它类型由开发阶段按业务定义。
- **值**：值控件随字段类型与符号变化——文本输入、数字输入（"介于"为双输入）、日期选择（"区间"为日期区间选择）等；**字典字段使用可搜索的下拉选择**（如选择"资产分类"时下拉字典项并支持搜索）；远程引用字段使用按名称可搜索的远程下拉；"为空/不为空"与相对日期符号无需填写值。
- **条件组合**：条件按**条件组**组织，同一组内统一使用"且（AND）"或"或（OR）"一种逻辑；支持添加一层嵌套子组（条件组最多 2 层），可表达如"A 且 B 且（C 或 D）"的组合逻辑；组内只剩 1 条条件时删除该条件保留空行，不删除条件组本身。
- 当前生效的筛选条件以**条件标签栏**显示在表格上方：每个条件一个标签，可单个删除；点击标签重新打开高级筛选面板编辑；并提供一键清除全部条件；入口按钮同时显示已启用条件数。
- 筛选在服务端执行：服务端列表接口接受结构化的树形筛选条件（字段/符号/值 + 条件组逻辑，见 §9.5），与分页、权限、数据范围共同生效。

**排序面板**

- 点击"排序"后出现排序面板（呈现形式不限），可动态添加、移除排序项；每个排序项由**字段 + 方向（升序/降序）**组成。
- 支持**多级排序**：多个排序项按添加顺序依次作为排序优先级（第一项为主排序字段）。
- 排序在服务端执行，遵循 §9.5 的稳定排序要求；无自定义排序时使用业务默认排序。

**预设**

- 可将当前使用的全部筛选条件（或排序组合）保存为**预设**：可命名、可保存多个、使用时可选择预设直接应用；支持重命名与删除。
- 预设为个人所有，按功能页区分并持久化保存（服务端账号维度，跨设备可用）。
- 预设只是查询条件的复用载体，不改变服务端接口语义。

**列设置**

- 每张表格提供"列设置"入口，支持列显隐、列宽拖拽与固定列；首列（主标识）与操作列默认固定，横向滚动时保持可见。
- 默认只展示核心列（名称、状态、时间等），其余列按需开启；用户的列设置持久化到服务端账号维度（与筛选预设一致，跨设备可用）。
- 金额、数字列使用等宽数字字体，便于纵向对比。

**状态设计**

- 表格统一展示状态：有数据、空数据、筛选无结果、加载失败，并覆盖加载中瞬时态；各状态文案与引导不同。
- 空数据态提供操作引导（如"去创建""去导入"）；筛选无结果态提示"无符合条件的数据"并提供"清除全部筛选条件"入口；加载失败态提供重试入口。

**移动端表格形态**

- 移动端表格默认卡片化：每行转为一组"标签 + 值"字段的卡片，纵向排布，点击卡片进入详情；列少且无需编辑的表格可采用横滑，并固定表头与首列。
- 筛选、排序在移动端以抽屉面板呈现，交互规则同本节。
- 移动端交互目标（按钮、选项等）不小于 44px。

### 10.3 通用操作与导出规则

- 危险操作须二次确认。批量软删除、批量注销/恢复和字典/分类批量硬删除必须按 §2.6 全有或全无，任一校验失败时整批不变更。
- **批量操作栏**：默认不显示批量操作区，勾选行后浮现批量操作栏（顶部或底部），显示已选数量及全选/半选状态，可取消选择；危险操作的确认文案必须包含影响数量。
- 行内操作按钮不超过 3 个，超出部分收敛到「更多」下拉菜单，高频操作优先直显。
- **导出规则**：本期导出文件统一为 `.xlsx`。除业务章节明确规定无导出或使用固定模板的页面外，导出统一只支持"导出所有 / 导出已筛选"两种范围，不提供"导出当前页"。普通业务实体的"导出所有"导出当前用户权限范围内全部未逻辑删除数据并忽略页面筛选与分页；"导出已筛选"导出符合当前筛选条件的全部未逻辑删除数据并忽略分页。无软删除状态的日志、流水等只读记录按当前权限范围应用相同的"所有/已筛选"语义。利润分析两种范围均按 fin PRD §4 的固定 Excel 模板生成；其它页面使用平台统一的基础工作簿样式。所有导出均遵守系统容量限制并明确提示失败原因；用户输入文本按普通单元格值写入，不得被解释为公式、外部链接或宏。
- **导出行数上限**：单次导出的业务数据行数默认上限为 100,000 行，"导出所有"和"导出已筛选"使用同一上限；表头、业务分类分组行和小计行不计入该配置值，但生成后的任一工作表仍不得超过 `.xlsx` 格式物理行数上限。该参数由 backstage PRD §7 系统设置维护，只允许正整数且最高不超过 200,000（值域与固定 120 秒导出总时限相匹配，避免配置出实际必然超时失败的导出），导出请求不能自行传入或提高上限；每次请求在开始时读取配置快照，修改配置不追溯影响已开始的导出。
- 服务端必须在开始生成和发送附件前统计当前权限及导出范围内的数据行数；超过配置上限时整次拒绝，不生成文件、不截断前 100,000 行，也不把部分结果伪装成"导出所有"，返回 `BUSINESS + EXPORT + ROW_LIMIT_EXCEEDED`，并在安全详情中提供实际行数、当前上限和"缩小筛选范围"的建议。即使业务数据未超限，加入标题、表头、分组及小计后会超过 Excel 工作表物理上限时也同样整次拒绝。
- **一致性快照**：每次导出在 PostgreSQL `REPEATABLE READ, READ ONLY` 事务中建立只读一致性快照；权限条件、软删除条件、筛选条件、行数统计、汇总/小计和最终数据读取全部基于同一快照，保证导出期间发生的新增、修改或软删除不会造成统计数与文件内容不一致、重复行或漏行。导出数据按稳定唯一排序并在同一快照内使用游标/键集分批读取，不使用随数据变化易漂移的 OFFSET 分页拼接文件。
- **单用户导出并发**：同一平台用户在全部浏览器、会话、服务实例和导出页面之间最多只能有 1 个正在执行的导出；并发占用以 `userId` 为键，通过 Redis 带随机所有者令牌、自动过期和安全释放的分布式互斥记录实现，从请求通过校验后开始持有，直到响应正常结束、失败、取消或超时。租约必须覆盖 120 秒总时限及短暂清理余量，只有持有同一所有者令牌的请求可以续租或释放，避免旧请求误删新请求的占用。第二个请求不排队，直接返回 `429 RATE_LIMIT + EXPORT_ALREADY_RUNNING` 并提示等待当前导出结束。平台不设置"全体用户合计最多多少个导出"的业务拒绝阈值，但数据库连接池、流背压和 §9.1 的 CPU 工作池仍必须有界，不能以"不限平台并发"为由无限创建连接、线程或内存缓冲。
- **固定总超时**：每次导出总时限固定为 120 秒，本期不放入系统设置；从取得单用户并发占用开始计算，覆盖行数统计、建立/读取一致性快照、等待和执行 CPU 工作、工作簿生成以及服务端完成附件响应的全过程。到期必须取消尚未开始的工作、通知正在执行的读取/工作线程停止、关闭游标和事务并释放并发占用；响应头尚未发送时返回 `503 TIMEOUT + EXPORT_TIMEOUT`，附件传输已经开始时终止响应并由浏览器显示下载失败，不生成一个看似成功的截断文件。Nginx 与 Node.js 的流式响应超时必须高于应用层 120 秒，以便由应用先完成受控取消和错误处理。
- 只读导出事务设置短于总时限的独立语句超时；语句超时、总超时或快照建立失败时整次导出失败，不降级为读取不一致的最新数据。事务在最后一批数据库数据读取完成后立即结束，不等待浏览器完成网络接收；工作簿仍按 fin PRD §4、§9.2 直接流向浏览器且不写 OSS、PostgreSQL 或服务器持久磁盘。只读快照不阻塞普通业务写入，但不得因导出请求长期占用数据库连接或无限持有旧快照。
- 请求取消、浏览器关闭下载或网络连接中断时，服务端必须传播取消信号，停止后续数据库批次读取和工作簿生成，关闭游标并结束只读事务；不能在客户端已经离线后继续消耗 CPU、内存或数据库连接。中断下载只记录失败访问结果及必要系统日志，不写成功导出操作日志，也不保留半成品文件。

### 10.4 权限显隐

- 菜单、页面入口、行内操作按钮均按当前用户的功能授权与数据范围显示/隐藏；只读用户看不到任何编辑入口。
- 服务端始终进行最终校验；前端显隐仅作为体验优化，不承担安全职责。

### 10.5 统一反馈

- 全站统一使用 Ant Design 原生 `Message`、`Notification` 和 `Modal` 提供反馈（通过统一的前端反馈服务封装），不自行重造通知组件；业务页面不得直接调用 `message.xxx`、`notification.xxx` 或自行实现 Toast。
- 请求层集中消费 §9.5 的错误类型/错误码进行统一反馈（如会话失效时提示并引导重新登录）；未知异常只展示统一安全文案与 `requestId`。通知内容只能使用 React 文本节点和受控组件，禁止把后端文案作为 HTML 注入。前端显示通知不代替 backstage PRD §8 系统日志、§3.3 操作日志或领域审计。
- 本节"反馈/通知"仅指当前页面中的即时 UI 提示，不等于系统公告、站内消息中心或钉钉消息推送，也不因此把站内消息中心、钉钉消息推送等 MVP 阶段暂不提供的能力引入本版本。

### 10.6 页面壳与展示原则

- 所有业务页面的顶部页栏左上方统一提供「回退 / 前进 / 刷新」三个导航按钮；刷新为软刷新（重挂载当前页面内容并重新拉取数据），不整页重载。
- 系统内侧边导航按 §2.1 的业务分组结构呈现（默认三级，菜单管理可配置为任意层级），直链或刷新进入深层页面时祖先分组自动展开；当前页面位置的面包屑展示在顶部 Header 中，逐级展示「系统名 → 各级分组 → 页面」。
- main 内容区不展示页面标题、副标题或说明性描述语句；功能提示如需保留应放入对应表单、弹窗或操作确认中，避免在页面主体堆叠冗余文案。
- 业务列表与详情视图不展示记录 ID、用户 ID 等纯技术标识字段；这些字段只用于前后端交互与行操作，不进入表格列、详情与弹窗展示。业务编号（如申请单号）不属于此列。

## 11. 非功能需求

- **并发一致性**：库存、调拨、审批、借还数据在并发操作下保持一致，不出现负库存、重复移库、调拨前后总量变化、重复出库、重复批准或覆盖审批结果。
- **安全**：账号、业务数据和管理员操作受到访问控制；敏感信息（密钥等）加密或隔离；登录防爆破；文件存储访问受控。
- **审计追溯**：关键配置、授权、审批、调度、库存、财务变更可追溯到操作者与时间；审计数据不可覆盖。
- **容量与限流**：导出、批量上传、批量处理有明确上限与失败反馈；登录有并发/频率限制；单个任务的资源消耗受控。
- **异步与响应正确性**：请求内 I/O 使用非阻塞 API 并处理流背压，CPU 密集步骤使用有界工作池；正式业务写入必须在事务和审计提交后才响应成功，后台任务仅用于 §9.1 明确列出的可持久化长任务，不以 fire-and-forget 牺牲结果确定性。
- **可用性**：业务系统下线、授权变更、会话失效不造成数据丢失；故障时提供明确状态与恢复手段。
- **双端支持**：桌面端与移动端均可完成主要查询、提交、审批和已授权编辑操作；移动端可改变呈现形式，但不得以宽表不适配为由删减利润分析编辑能力。
- **可维护性**：需要管理员调整的业务规则（如会话参数、额度周期等）统一配置管理并明确是否形成提交时快照；节假日数据按 hr PRD §3 调用 API 后直接保存，不建设人工维护或审批流程；审批超时自动取消天数在系统设置中配置。

## 13. 技术方案要点

> 本版本确定的技术实现基线，供开发阶段细化。

- **前端**：TypeScript + React 18 或更高兼容版本 + Vite + Ant Design v6；根 `ConfigProvider` 使用 `docs/for-frontend/ant-design/theme.json`，组件与 Token 规范遵循 `docs/for-frontend/ant-design/design.md`。利润分析桌面端复用 Ant Design `Table` 的 Editable Cells 范式，不引入第二套表格组件库；全局反馈复用 Ant Design `App`、`Message`、`Notification` 和 `Modal`。
- **业务后端**：TypeScript + NestJS + Prisma 7.x（multiSchema 与 multi-file schema；各部署单元迁移元数据表落位于各自默认 schema 并相互隔离，见 §9.9）；HTTP、数据库、Redis、OSS 与文件流采用请求内非阻塞异步 I/O，CPU 密集型 Excel 解析/序列化使用有界 Node.js Worker Threads 工作池，边界见 §9.1。
- **AI 后端**：Python + FastAPI + LangChain/LangGraph（智能模块启用后）。
- **接口**：面向前端的版本化 REST 本期前缀为 `/api/v1`；不同部署单元之间的内部 REST 前缀为 `/internal/v1`，base/backstage 在 `platform-core` 内使用类型明确的应用服务接口而非 HTTP；按 DTO 生成 OpenAPI 文档；SSE 流式接口仅为后续智能模块预留。内部 REST 仅经 Docker 私网访问，使用一个部署级共享令牌和调用方白名单，不引入 JWT、mTLS 或独立认证中心。
- **内存与队列**：单个 Redis 容器——集中会话、登录限流计数、BullMQ 后台任务投递、配置广播和分布式锁；除数据库恢复执行阶段按 backstage PRD §10 使用 ECS 持久化恢复控制清单外，后台任务事实与最终状态保存在 PostgreSQL 统一任务表，该表同时作为轻量 Outbox。BullMQ 只承载 §9.1 明确列出的跨请求长任务唤醒，导入导出仍在当前请求中处理。BullMQ 成功/失败记录分别按"7 天且每队列 1,000 条"与"30 天且每队列 5,000 条"限制，并由启动/每小时清理弥补惰性年龄清理。Redis 启用持久化与 `noeviction`，启动强依赖和运行时降级规则见 §9.8；PostgreSQL 整库恢复后必须先清空专用 Redis 数据集并完成重建，所有会话失效后才可退出维护状态。
- **身份与登录**：接入钉钉当前官方网页扫码授权流程，稳定钉钉用户标识与平台用户一对一绑定；授权码由后端兑换，钉钉密钥和访问凭证不进入前端。平台同时保留手机号 + 密码登录；管理员创建的待激活基础账号通过一次性二维码/链接交由员工完成钉钉绑定与密码设置，手机号以钉钉返回值为准且本期不可修改（详见 base PRD §2）。
- **会话**：Redis 服务端会话 + `httpOnly/secure/sameSite` Cookie + CSRF 防护；普通会话与"记住我"会话分别设置空闲/绝对超时，"记住我"仅延长时限并随绝对过期时限持久化会话 Cookie（未勾选为浏览器会话级），不创建永不过期会话；"修改密码后全部会话失效"通过会话版本号实现（版本递增即全部踢下线）。MVP 不建设密码/钉钉二次认证产生的高危操作会话，高危管理动作使用当前有效会话、明确二次确认、实时角色/权限复核、幂等和审计，见 base PRD §3。
- **数据库**：单个 PostgreSQL 实例，按逻辑模块分 schema，应用侧所有服务、Worker、恢复执行器、Migration Runner 和备份任务复用一个连接账号。`platform-core` 声明拥有 base/backstage，并用一个 multi-file Prisma Schema、一个 Prisma Client 和一套迁移序列管理两者；asset、hr、fin 分别拥有同名 schema 及独立 Client。业务写入只能通过拥有模块，同一核心进程内使用公开应用服务接口和显式传递的事务客户端，不同部署单元间调用目标服务 REST API。特殊跨模块读取只通过经评审的只读数据库视图开放。部门、岗位、职称规则和用户组织关系由 hr schema 拥有，其它模块只读使用，用户恢复必须在 hr 就绪时按 backstage PRD §3 调用内部接口协调。公共基础设施写入例外共四项：共享日志模块写入/聚合 `backstage` 集中错误日志与安全日志，共享任务模块创建和条件更新 `backstage` 统一后台任务表，审批超时自动取消扫描对 backstage/hr/asset 三 schema 同构 `approval_requests` 的受限条件更新（含同事务业务占用释放 hook），以及图片孤儿清理对 `backstage.image_objects` 注册表行的同步删除（范围与白名单约束见 §9.4）。迁移由发布入口中的一次性 Migration Runner 统一编排，各部署单元的 `_prisma_migrations` 位于其指定默认 schema 并相互隔离，启动只校验自己声明的结构版本，见 backstage PRD §8、§9.1、§9.9。
- **文件存储与备份**：资产/消耗品图片与数据库备份使用阿里云 OSS 私有存储空间（限时/限路径预签名直传；图片前端压缩至 1MB 内且后端校验）；利润分析 Excel 每个请求可通过单个文件批量导入最多 10,000 个项目数据行，文件最大 20 MiB、累计解压最大 200 MiB、ZIP 条目最多 1,000 个，预览有效期 30 分钟，预览与确认各自固定总超时 120 秒；导入在请求内以非阻塞流读取且不留存原文件（详见 fin PRD §4）。导出在 PostgreSQL 只读一致性快照中读取并直接流向浏览器，不经过 OSS，单用户同时 1 个且固定总超时 120 秒。导入与导出分别限制单用户同时 1 个请求，二者可以并行。PostgreSQL 使用每日 `pg_dump`、立即备份与恢复前紧急备份，本期不提供 PITR（详见 backstage PRD §10）。
- **部署**：阿里云 ECS（Ubuntu 22.04）+ Docker Compose 起步（Nginx + `platform-core` + asset + hr + fin + BullMQ Worker + 恢复执行器 + Migration Runner + 单个 Redis + PostgreSQL；未启用业务模块不启动，恢复执行器作为基础设施常驻）；Nginx 统一入口，base/backstage 路由到同一个 `platform-core`，asset、hr、fin 容器可单独启停。生产发布统一把全部组件镜像更新到同一后继 Git commit，不允许版本漂移或回滚；下游不可用时按 §9.4 降级。部署与迁移封装为单条命令，成功并通过就绪检查后按 backstage PRD §9 从 Git commit 范围自动生成更新日志，无需维护者另写发布说明。发布入口在数据库外原子维护最近成功部署标识和运行 commit，数据库恢复不得使该应用版本基线倒退。全部容器显式使用 Docker `local` 日志驱动并按 20MB × 5 轮转，部署后自动核验。数据库恢复维护标记与最小恢复控制清单共同存放在数据库外的 ECS 持久化目录，恢复执行器可读写，Nginx 和其它容器只按所需最小权限读取维护状态；SSE 反代需关闭缓冲。
- **并发一致性**：数据库唯一/检查约束、条件更新、行锁或适当隔离级别与数据库事务是正确性的主要保障；审批使用状态机 + 版本号，重要写入使用幂等键；Redis 分布式锁只作为减少冲突的辅助机制。
- **日期时间**：平台业务时区固定 `Asia/Shanghai`；时间点以 UTC 存储并按北京时间展示，纯业务日期使用 PostgreSQL `date`，周期与定时任务边界按北京时间计算。节假日判断由 hr 后端调用 `holiday.ailcc.com` 的国内免费 API，24 小时缓存并保存规范化结果，不接入付费数据源，见 hr PRD §3、§9.10。
- **数量与金额精度**：消耗品业务变动数量只接受正整数，库存余额允许为 0 且不得为负；人民币手工金额不得为负，统一使用 PostgreSQL `numeric(18,2)` 与后端 Decimal 类型，API 按十进制字符串传输，禁止使用 JavaScript 浮点数计算金额；毛利率内部以十进制比率表达，Web 与 Excel 按百分比展示两位小数，见 asset PRD §5、§9.11。
- **全局基础设施**：NestJS 统一配置请求上下文中间件、输入校验管道、认证/授权守卫、耗时/超时拦截器与单一全局异常过滤器；异常区分 `BusinessException`、校验、认证授权、冲突、限流、本服务操作超时、依赖和未知系统异常，业务异常再按领域错误目录细分。重要运行异常集中写入后台系统日志表，并按异常指纹和固定五分钟窗口并发聚合，实现统一追踪、错误和安全契约。
- **参数配置**：数据库存储，设置页维护，Redis 变更广播刷新各服务缓存。
- **健康检查**：各后端部署单元提供 `/healthz`（进程存活）与 `/readyz`（依赖就绪），`platform-core` 同时汇总 base/backstage 所需依赖；探针仅供 Docker healthcheck 与 Nginx 探活并返回最小状态。登录后的"健康状态"页面另按权限展示服务/依赖状态、全平台后台任务总览及"所属模块 + 任务类型"分组的当前数量、最近 24 小时失败数量和最近一次失败时间，不累计展示全部历史失败，也不新增统一任务中心或逐条任务管理。有目标页面权限时可跳转到相应业务页；同时具有"系统日志"权限时，内部任务可跳转到安全筛选后的系统日志。Redis 启动检查失败时后端进程不启动，运行中失联时存活保持、就绪失败并按 §9.8 降级。

# 管理后台 PRD（backstage）

> 本文档定义 WBME 企业管理平台**管理后台**的需求。
> backstage 与 base 共同运行于部署单元 `platform-core` 中（见主 PRD §1.3），本文只描述 backstage 逻辑模块。
> 平台级通用机制见主 PRD：`docs/prds/prd.md`——其中功能权限机制见主 PRD §3.1，统一审批机制见主 PRD §3.2，操作日志见主 PRD §3.3，其余通用机制见主 PRD §9～§13。

---

## 1. 功能权限清单

> 目录按「系统 → 业务板块 → 功能」三层组织；授权机制、数据范围语义与申请类/审批类功能通用规则见主 PRD §2.5、§3.1。

| 系统 | 业务板块 | 功能 | 可选数据范围 | 说明 |
| --- | --- | --- | --- | --- |
| backstage | 用户 | 用户管理 | 公司 | 用户创建、查询、编辑、批量注销/恢复、发起本人验证式密码重置、解锁账号、资料修改审批（管理员） |
| backstage | 内容 | 更新日志查看 | 公司 | 只读查看每次成功部署自动追加的版本更新日志；与系统公告权限相互独立 |
| backstage | 内容 | 系统公告管理 | 公司 | 创建、编辑、发布、撤回和批量删除系统公告；可读取更新日志并复制为公告内容来源 |
| backstage | 权限 | 操作日志 | 部门/公司 | 全员操作日志查询（个人日志全员可用，不在此授权） |

| backstage | 系统 | 健康状态 | 公司 | 查看服务就绪状态、依赖概况与后台任务状态数量，不查看统一任务明细 |
| backstage | 权限 | 权限管理 | 公司 | 管理全部系统内员工的功能授权与权限组；仅超级管理员可授予或撤销 |

## 2. 模块定位与边界

- 管理后台（backstage）承载平台级管理能力——用户管理、功能权限管理、系统设置（含系统开放状态）、系统日志、更新日志与系统公告、数据备份、操作日志、健康状态（区域边界见主 PRD §2.2）。
- **组织信息**：用户管理位于管理后台；组织架构、部门管理、岗位管理、职称管理位于人事系统（hr PRD §5～§8）。
- 配置与组织功能按各自所属系统的功能授予与委派。

## 3. 用户管理

- 权限：backstage 功能"用户管理"。
- 功能：创建、查询、编辑、批量注销和批量恢复用户；查看账号激活状态、钉钉绑定状态，为待激活账号生成或重新生成一次性激活二维码/链接；为已激活账号发起密码重置；解锁账号（见 base PRD §4）。超级管理员还可在本页任命普通员工为超级管理员，或把其它超级管理员降级为普通员工，入口和服务端规则遵循主 PRD §3.1 的最后一名超管保护、当前角色复核、二次确认与审计；普通“用户管理”持有者看不到该操作，它也不拆成可委派功能。待激活账号尚无密码，不显示重置密码操作。本期不另设“封号/解封”状态，临时登录锁定由 base PRD §4 的登录保护机制负责。
- 创建用户时填写姓名、手机号（在待激活与正常账号间唯一，仅作激活前的联系参考，激活时以钉钉返回为准）和性别，只创建无密码、未绑定钉钉的基础账号，不提供部门或岗位选择；新账号处于“待激活”状态，默认无部门、无岗位、无业务功能权限，由员工按 base PRD §2 使用一次性二维码或链接激活。
- 用户资料中的部门/岗位仅可查看，不可在管理后台创建或修改；账号创建后的部门与岗位统一由人事系统「组织架构」直接编排，员工后续也可按 base PRD §6 提交岗位变更申请。
- 编辑用户基本资料仅包括姓名和性别；手机号只读展示，本期不提供管理员或员工修改手机号的入口与接口。
- **管理员发起密码重置**不允许管理员输入、查看或生成员工的新密码。操作后只生成限时、一次性的重置二维码/链接，由目标员工完成钉钉授权；校验钉钉稳定标识与账号现有绑定一致、属于本公司组织后，员工自行设置新密码，完成时按 base PRD §2 的手机号同步规则更新手机号。旧密码和旧会话在重置流程完成前保持有效，完成事务提交后才统一失效；需要立即阻断疑似被盗账号时应先注销账号。凭证按摘要存储，不进入 URL 访问日志、操作日志或前端持久存储；失败、过期或已使用均不得重放。普通“用户管理”持有者只能为普通员工发起该流程，超级管理员账号只能由另一名超级管理员或本人通过 base PRD §2 的钉钉验证重置，避免用户管理员借密码重置接管根权限。
- **批量注销**遵循主 PRD §2.6：正常用户列表只提供勾选后的“批量注销”，不提供单个注销或任何硬删除入口；注销写入注销时间和操作人，立即撤销全部会话，使其授权与组织关系在注销期间不生效，并从正常用户查询、组织编排和授权目标中排除，但保留原账号标识、钉钉/手机号绑定、授权关系、组织关系和全部历史引用。
- **注销后的待审批申请**：注销不能抹去或阻断已经形成的公司业务事实。注销前已提交的加班、库存入库、库存变更、消耗品申领、归还、核销及其它被申请类型声明为“公司业务型”的待审批记录继续保留并按原规则批准、驳回或取消；审批接口不得仅因申请人、代交人或申请对象账号已注销而拒绝处理，审批通过后的业务结果仍归入原用户 ID 和提交时快照。资料修改、岗位变更及其它被声明为“账号资料型”的待审批记录则在注销时自动取消，取消来源固定记录为 `ACCOUNT_DEACTIVATED`，不再允许批准或驳回；恢复账号不会重新打开这些旧申请，需要时由员工重新提交。以后新增审批类型时必须显式选择两类之一，不能依赖页面临时判断。
- **跨模块自动取消**：`platform-core` 的账号生命周期编排服务在同一个本地数据库事务中通过 base 模块注销账号、通过 backstage 模块取消待审批资料修改申请，并为每名被注销用户写入包含用户 ID、注销时间和账号生命周期版本的“账号生命周期处理”任务；任一部分失败则整批注销回滚。hr 消费该任务后，只取消注销发生前已经提交且仍为待审批的岗位申请，不能误取消账号恢复后新提交的申请。任务使用稳定业务键幂等处理；hr 暂时下线不阻塞整批注销，恢复服务后继续处理。任务尚未消费时，岗位审批接口发现目标账号已注销必须拒绝批准并返回“账号注销，申请将自动取消”，不得产生组织变更；对应申请最终仍由任务写入统一的已取消终态和取消来源。
- **批量恢复与 HR 前置条件**：用户管理提供“正常 / 已注销”状态筛选；“已注销”列表是主 PRD §2.6 默认过滤规则的管理专用例外。进入已注销视图后，同一批量操作按钮显示为“恢复”。组织数据由 hr 服务拥有，因此打开恢复预览和提交最终确认时都必须检查 hr 服务当前就绪状态并实际调用其受保护内部接口；hr 容器已停止、未就绪、调用超时或返回无效响应时，恢复功能不可用，返回 `DEPENDENCY` 类型、`HR_SERVICE_UNAVAILABLE` 错误码并明确提示“人事系统当前不可用，无法恢复用户”。检查产品状态是否为“开放”不能代替服务就绪检查；只要 hr 服务未就绪，任何被选账号、权限和组织关系均不得发生变化。
- **恢复内容兼容性**：恢复前按当前系统状态生成兼容性检查结果，并尽量恢复注销前全部信息。原用户 ID、钉钉/手机号绑定和仍有效的站点角色保持；hr 对多部门关系与单一岗位进行兼容性检查，只保留仍存在且可用的部门关系，若没有有效部门则所属部门置空，岗位不存在或不再适用于全部保留部门时岗位置空；backstage 对原功能授权只保留当前仍由代码注册且原数据范围仍受支持的权限，已移除功能或失效范围的授权直接撤销。手机号唯一性纳入恢复兼容性检查：原手机号已被其他“待激活/正常”账号占用的目标在恢复预览中标记且不可恢复，待占用解除（占用方完成同步或被注销）后重试。系统公告状态、业务系统是否开放不属于权限弃用，不因此删除授权。若账号注销时 hr 停机导致本节的账号生命周期任务尚未消费，hr 必须在本次恢复应用事务中先幂等取消该账号注销时间之前提交且仍为待审批的岗位申请，再处理组织兼容性；恢复成功后旧岗位申请不得重新成为待办，之后到达的原生命周期任务只作幂等确认。
- 待激活账号也可以参与批量注销；注销时其全部未使用邀请立即失效。恢复后仍回到“待激活”而不是直接变成正常账号，管理员需重新生成一次性邀请；已激活账号恢复后仍按原钉钉绑定和密码登录，不生成新的激活邀请。
- 恢复确认界面必须逐个用户列出“完整恢复、被清除的部门/岗位、被移除的功能权限”等差异。确认请求使用稳定恢复请求 ID 和各账号生命周期版本：`platform-core` 先调用 hr 的幂等恢复应用接口，hr 在自己的单个数据库事务中重新校验全部目标并应用整批组织兼容性清理，任一目标已变化或不可处理则 hr 整批回滚，`platform-core` 不恢复任何账号；hr 整批成功后，账号生命周期编排服务才让 base 与 backstage 通过各自公开接口参与同一个本地 PostgreSQL 事务，清除全部目标的注销标记、写入恢复人和恢复时间并应用权限兼容性清理。若 hr 已成功而该本地事务失败，全部账号仍保持注销，不能对外产生有效组织权限；操作者使用同一恢复请求 ID 重试时，hr 返回原幂等结果，再由 `platform-core` 完成恢复，不要求人工补偿或跨服务直写。不创建新账号，旧会话不恢复，用户需重新登录；被清理的旧关系仍保留在审计记录中，不作为当前有效关系参与查询或授权。
- 批量注销不能包含当前操作人或最后一个可用的超级管理员；普通员工即使持有“用户管理”，也不能编辑、注销、恢复、重置、解锁或改变超级管理员账号的站点角色，超级管理员目标仅由超级管理员管理。批量注销与批量恢复均按主 PRD §2.6 先完整校验，任一目标不可操作时整批不产生变更。
- 账号注销或会话失效时，用户得到明确提示，而非无提示跳回登录页。

## 4. 统一人员权限管理（界面需求）

> 功能权限机制（授权目录、数据范围、角色与委派、入口推导、变更审计）见主 PRD §3.1，本文只描述管理界面需求。

- 权限管理只在管理后台提供，面向全体普通员工；页面名为「人员权限」。
- 支持按姓名/手机号检索与多选；列表展示姓名（超级管理员附"超管"标记）、所属部门、可进系统（该员工每拥有一个系统的任一功能即列入，以"资产系统、人事系统……"形式顿号连接，最多 3 行、每行 10 字）、可用功能（全部已授予功能，含数据范围标注，如"固定资产维护（部门）"，最多 3 行、每行 15 字；超出部分悬浮查看全量），行内提供「修改权限」操作。
- 多选后可**批量撤销**所选员工在当前操作人可管理范围内的全部功能授权（不删除账号，需二次确认）。服务端先对全部目标执行操作人管理范围、目标账号状态、超级管理员保护和授权版本校验，再在一个 PostgreSQL 事务内完成整批撤销与逐人操作日志；任一目标失败则整批回滚，并返回逐人校验结果和阻塞原因，不能出现页面显示批量完成而实际只撤销部分人员。请求使用稳定幂等键，重试不得重复产生权限版本递增或日志。
- 多选后可**批量授权**（增量授权，机制见主 PRD §3.1）：为所选员工追加功能授权，不改动其已有授权。授权内容可为逐项功能（含数据范围）或选择一个或多个**权限组**（见本节下文）展开；提交前展示所选员工数与将追加的权限摘要并二次确认。服务端先对全部目标执行操作人管理范围、目标账号状态、超级管理员保护和授权版本校验，再在一个 PostgreSQL 事务内完成整批授权与逐人操作日志；任一目标失败则整批回滚并返回逐人校验结果和阻塞原因，不出现部分成功。请求使用稳定幂等键，重试不得重复产生授权。
- 「修改权限」以抽屉承载，抽屉内只含授权内容：按系统分 tab 展示可授权功能，单个系统 tab 内按业务板块分组、每行 3 个功能紧凑排布，勾选/取消勾选后在抽屉底部统一保存；权限管理员可管理全部系统的普通功能授权；"权限管理"功能本身只对超级管理员可见和操作。操作人不能修改自己的授权（见本节末尾）。
- 支持数据范围的功能在勾选后于其旁选择数据范围（本人/部门/公司），单档范围功能自动取该档。
- **权限组（授权预设）**：管理后台提供权限组维护——创建、编辑、删除与查看组内权限（机制定义见主 PRD §3.1）。权限组命名且**可跨系统**（一个组可包含多个系统的功能授权，每个功能含数据范围）；权限组编辑采用**矩阵式点选**：功能权限按「系统 → 业务板块」分组排列为矩阵行，可选数据范围档位为矩阵列（无数据范围选项的功能以单列"启用"表示），勾选单元格即把该功能连同所选数据范围加入组内。权限组只作为授权模板，授予员工时展开为员工的功能授权快照，之后修改或删除权限组不影响已授权员工。维护边界：持有"权限管理"功能者（含超级管理员）可维护全部权限组。单人"修改权限"与批量授权均可选择一个或多个权限组展开填充。权限组变更按主 PRD §3.3 记录操作日志。
- 保存一次性提交目标员工在当前可管理系统范围内的完整功能状态；打开权限管理时同时取得目标员工的当前授权版本，保存接口必须携带该版本并在事务中按版本条件更新。若期间已被其他管理员修改，服务端返回明确 `CONFLICT`，不得以后提交的数据静默覆盖先完成的变更；前端保留本次勾选内容，提示“权限已被他人更新”，允许刷新最新权限后人工比较并重新提交。保存成功后门户、菜单、页面及操作入口同步更新。
- 操作人不能修改自己的授权（防止自我提权），如需变更由超级管理员或其他持有"权限管理"功能的管理员操作。
- 页面布局、交互与视觉遵循 Ant Design 设计体系，细节由开发阶段设计。

## 5. 管理后台资料修改审批

> 统一审批机制（状态流转、权限与数据范围、并发幂等与各业务待审批数量规则）见主 PRD §3.2；本节只描述管理后台特有的审批类型。

- 当前申请类型：普通员工修改个人资料（姓名、性别）。
- 审批权归属"用户管理"功能：持有"用户管理"功能者自动获得资料修改审批权，在审批中心处理待办。
- 审批通过前不改变正式资料，通过时再次校验目标数据有效性。
- 同一员工同时最多一条待审批资料修改申请；岗位变更是否待审批不影响资料修改申请。审批记录作为审计信息保留，不提供删除或覆盖。
- 后续管理后台审批类型统一接入主 PRD §3.2 的同一审批中心，不为每类申请重复建设入口。

## 6. 系统开放状态

- 权限：归入"系统设置"功能，在「系统设置」页签中切换。
- 系统产品状态：开放 / 即将上线；base 与 backstage 共享 `platform-core` 且均不提供主动下线操作，asset、hr、fin 可调整状态。
- 服务停止是运维操作，不提供"关闭服务"切换；目标服务已停止或不就绪时，依赖它的跨系统功能不得直接写入其 schema，必须终止当次操作并提示"目标系统当前不可用，未提交成功"。恢复服务或重新开放不改变原有授权。

## 7. 系统设置

- 权限：backstage 功能"系统设置"。
- 系统设置包含两类配置：
  - **平台配置**：普通会话与"记住我"会话各自的空闲超时/绝对过期时限、账号锁与 IP 锁的计数窗口/次数上限/锁定时长（见 base PRD §4）、默认查询时间窗口（默认最近 30 天，用户可在具体页面清空或调整）、单次导出最大数据行数（默认 100,000 行）、备份保留天数（默认 30 天，可设 7～365 天）、未关联业务图片保留时长（默认 24 小时）、审批超时自动取消天数（默认 30 天，见主 PRD §3.2）等。
  - **AI 配置**：智能模型配置、模型连接信息等；随智能模块（ai）启用后提供，本期无内容。
- 本页只维护主 PRD §1.4 定义的管理员可调业务参数；参数存储在数据库，修改后无需重新部署并按各业务的快照/非追溯规则生效。主 PRD §1.4 定义的版本化工程与安全常量以及部署级机密不在本页面展示或修改。
- 敏感配置（如模型密钥）加密存储，不明文展示、不写入普通日志；设置变更可追溯到操作者。

## 8. 系统日志

- 权限：backstage 功能"系统日志"。
- **集中存储与分类**：系统日志分为"错误日志 / 安全日志"两类，对应 `backstage` schema 内的错误日志表与安全日志表两张表；`platform-core`、asset、hr、fin、Worker 和后续新增服务均通过同一个共享日志模块直接写入，不调用管理后台 HTTP 接口，因此 `platform-core` 以外的业务服务记录不依赖管理后台页面或接口是否可用。两张表及迁移仍由 `platform-core` 内的 backstage 逻辑模块拥有，管理后台直接查询和更新处置元数据。
- **跨 schema 明确例外**：写入集中错误日志与安全日志是主 PRD §9.4"业务服务不跨 schema 写入"的平台基础设施写例外之一（另一项是主 PRD §9.1 的统一后台任务表）。共享日志模块只允许执行预定义的新增/聚合语句；业务模块不得借此读取或修改其它 backstage 表，也不得把业务数据、操作日志或领域审计写入集中系统日志。操作日志仍按主 PRD §3.3 分模块存储并随业务事务提交，两类日志不能混用。
- 重要运行异常只能由后端异常处理链路自动新增或聚合，记录级别、服务、来源、错误分类、部署 commit、异常指纹、首次/最后发生时间、发生次数、首个与最近追踪标识及脱敏异常样本；不提供人工新增、编辑原始异常内容或删除日志的接口。
- **五分钟聚合**：共享日志模块基于“服务 + 部署 commit + 错误分类/异常类型 + 稳定执行入口 + 稳定堆栈位置”生成 SHA-256 指纹；HTTP 请求的稳定执行入口是规范化路由模板，后台任务则是注册的稳定任务处理器标识/任务类型，不能为不存在的 HTTP 路由填入随机值。指纹不得包含 requestId、用户标识、任务 ID、请求参数、手机号、凭证或其它高基数/敏感值。同一指纹在同一固定五分钟时间桶内只保留一条待处理记录，后续并发异常原子增加发生次数并更新最后发生时间和最近追踪标识；第一个异常的脱敏样本、首次发生时间和首个追踪标识保持不变。以“指纹 + 时间桶起点”在待处理状态下的 PostgreSQL 条件唯一索引和原子 UPSERT 保证多个服务实例并发写入时不会产生重复聚合记录，不能依赖 Redis 去重。
- “已处理”和“已忽略”均关闭当前聚合记录；同一异常之后再次发生时必须新建“待处理”记录，即使仍在原五分钟时间桶内也不得继续追加到已关闭记录或静默抑制。五分钟时间桶自然结束后再次发生同样新建记录；无人处理中途关闭时，持续异常最多每个指纹每五分钟生成一条记录，而不是为每次发生新增一行或无限增长同一行。
- **处置状态单向流转**：记录创建时固定为“待处理”，只允许一次转为“已处理”或“已忽略”；两个终态不能恢复为待处理，也不能在已处理与已忽略之间互相切换。处置接口使用当前状态条件更新防止两名管理员并发覆盖，只有第一个终态操作成功，后续返回明确 `CONFLICT`。两种终态的处理备注均为可选，提交时记录处理人和处理时间；原始异常样本、聚合数据和既有处置结果均不允许人工覆盖。
- **安全日志记录范围**：登录成功/失败、登出、账号锁与 IP 锁的锁定/解锁、账号激活、邀请生成与使用、密码修改、密码重置的发起与完成、手机号自动同步及同步冲突、内部服务令牌校验失败（401/403）等认证与账号安全事件。每个事件追加一条记录，不做指纹聚合。属于管理功能的操作（如管理员发起密码重置）同时按主 PRD §3.3 记录操作日志。
- **安全日志字段**：事件类型、主体账号（操作者，匿名失败尝试可为空）、目标账号、结果（成功/失败及安全化原因）、来源 IP、时间、requestId/traceId 与最小上下文（如锁定时长、同步前后手机号的脱敏形式）；不记录密码、凭证、会话标识、邀请原文。安全日志只追加，不提供修改或删除接口；支持按事件类型、账号、结果、时间筛选；详情与导出可展示来源 IP（区别于错误日志的脱敏导出限制），导出遵循主 PRD §10.3 的“导出所有 / 导出已筛选”。
- 错误日志支持按首次/最后发生时间、级别、服务、来源、错误分类、异常指纹和处理状态筛选；可查看发生次数与最后发生时间，默认按最后发生时间倒序。后台任务失败日志的来源使用稳定的 `BACKGROUND_TASK:<任务类型>`，供 §11 健康状态跳转时筛选，不把任务参数或业务数据拼入来源。状态、处理备注、发生次数与最后发生信息属于处置/聚合元数据，不改写后端保存的首个脱敏异常样本。
- **详情权限**：持有“系统日志”功能者即可查看完整的脱敏异常样本，包括脱敏后的 message、堆栈、cause 链、内部模块/文件位置以及首个和最近 `requestId/traceId`，不再额外限制为超级管理员。详情仍不得显示密码、Cookie、会话标识、钉钉/OSS/数据库凭证、完整手机号、请求头或未经白名单处理的请求参数；所有内容按纯文本呈现，不解析 HTML。该详情权限不改变下述 Excel 只能导出脱敏摘要的限制。
- **脱敏摘要导出**：错误日志遵循主 PRD §10.3，只提供“导出所有 / 导出已筛选”的 `.xlsx`，并受单次导出行数上限控制。导出字段固定为日志编号、级别、服务、来源、错误分类、部署 commit、异常指纹、首次/最后发生时间、发生次数、服务端生成的安全摘要、处理状态、处理人和处理时间；不得导出处理备注、堆栈、cause 链、内部文件/模块路径、首个或最近 `requestId/traceId`、请求参数、请求头、客户端 IP、数据库错误正文或其它排障详情。导出端重新按字段白名单构造 DTO，不能先序列化完整日志再在前端隐藏列；安全摘要不得直接使用未经脱敏的原始异常 message。系统日志导出本身按主 PRD §3.3 记录操作日志。

## 9. 更新日志与系统公告

- 权限：“更新日志查看”仅控制更新日志功能；“系统公告管理”仅控制公告维护功能，并按下述规则内含公告编辑器所需的更新日志来源读取能力。
- 更新日志与系统公告使用不同实体和权限，不共用记录，也不因标题或内容相同自动关联；用户只看到自己有权访问的内容。
- **更新日志查看**：每次生产部署成功并通过全部应运行服务的就绪检查后，发布流程按唯一发布标识自动追加一条平台级更新日志，记录版本号、发布时间、全平台部署 Git commit、提交范围和本次变更说明；相同发布标识或目标 commit 重试不得重复生成。所有生产组件使用同一目标 commit，因此变更说明统一收集“上次成功部署 commit（不含）→ 本次部署 commit（含）”范围内的 Git commit 标题，按提交时间从旧到新逐条展示；首次部署没有基线时只记录本次部署 commit。提交范围的权威基线来自生产发布入口维护的当前运行 commit，而不是从可能被整库恢复覆盖的更新日志最后一行反推；发布入口在数据库外的 ECS 持久化部署状态中原子保存最近一次成功部署标识和 commit，并与当前镜像标签相互校验。数据库恢复后按 §10 把数据库内的发布基线重新对齐到当前运行 commit，避免下一次发布重复收集已经上线的提交；更新日志本身仍只展示恢复点内存在的历史，不伪造恢复点之后已丢失的日志行。
- **提交标题提取规则**：对于符合 Conventional Commits 形式的标题，移除开头的 `type(scope):`、`type:` 或带破坏性标记的同类前缀及其后空白，只保留冒号后的说明正文。例如 `feat(xxx): 更新内容/changelog ……` 在更新日志中显示为 `更新内容/changelog ……`。不符合该形式的标题保留完整标题并记录发布校验警告，不因单条格式问题阻断部署；提交说明按纯文本处理，不解析 HTML。更新日志只能在管理后台“更新日志”功能中只读查看，不允许通过业务页面手工新增、编辑或删除，不在门户或其它业务系统展示。
- **系统公告管理**：公告是管理员独立编辑的“标题 + 内容”，状态为“草稿 / 正在展示 / 已撤回”，并记录最近发布时间。MVP 的标题与内容均为纯文本，内容保留换行但不解析 HTML、Markdown、脚本、图片或嵌入内容；门户使用 React 文本节点与受控排版组件展示。管理员可以空白创建公告，也可以在公告编辑器中读取并选择一条更新日志，将其标题和变更说明**复制**为公告草稿的初始内容；该读取能力由“系统公告管理”自身包含，不要求同时拥有“更新日志查看”。复制后公告是独立快照，可继续编辑，后续公告变更不修改更新日志，更新日志也不自动同步到公告。
- **单条展示规则**：全平台同一时刻最多只能有一条未软删除公告处于“正在展示”。发布草稿或重新发布已撤回公告时，在一个 PostgreSQL 事务中把原正在展示公告转为“已撤回”，再把目标公告转为“正在展示”；数据库使用符合状态条件的唯一约束/索引兜底，避免并发发布形成两条正在展示。门户只读取当前这条，不按发布时间自动回退展示其它已撤回公告。
- 系统公告支持创建、编辑、发布、撤回和批量删除；正在展示的公告可直接执行删除而无需先撤回，删除按主 PRD §2.6 软删除并立即从门户消失。删除或撤回当前公告后，门户固定显示“暂无公告”，不会自动恢复或展示上一条公告；需要展示其它公告时由管理员明确重新发布。批量删除包含当前公告时也遵循同一规则并按主 PRD §2.6 整批成功或整批回滚。
- 更新日志的自动追加，以及系统公告的增删改、发布与撤回，均记录操作日志。

## 10. 数据备份与恢复

- 权限：backstage 功能“数据备份”允许进入页面、查看备份与恢复记录并执行定时/立即备份相关操作；**发起整库恢复、恢复预检后的最终确认、失败后的重试或改用紧急备份恢复仅允许超级管理员执行**。前端对非超级管理员隐藏或禁用全部整库恢复操作，后端在进入维护状态前的每个恢复控制接口再次校验当前站点角色，不能只依赖页面权限。最终确认页必须明确展示目标备份时间、可能丢失的数据时间范围、紧急备份状态和“即将覆盖当前数据库”的不可逆影响，并由超级管理员二次确认；按 base PRD §3 只使用其当前有效会话，不要求重新输入密码或钉钉扫码。已确认并交给恢复执行器的任务不因其普通登录会话随后失效而中断。维护状态建立后的状态查询与重试改用下述本次恢复专用控制会话，不能再依赖即将被清空的普通 Redis 会话；该控制会话用于跨越数据库/Redis 替换继续同一次恢复，不是通用高危操作权限提升状态。
- **定时备份**：默认每天北京时间 02:00 对 Docker 中运行的 PostgreSQL 执行一次 `pg_dump` 压缩格式逻辑备份，调度边界按主 PRD §9.10；本期不增加备份时刻设置项。完成后上传至阿里云 OSS 私有存储空间；记录任务状态、备份时间、数据库版本、文件大小、校验和、OSS 对象标识和脱敏后的错误信息。每个上传成功的备份同时在固定备份前缀下写入一份不可变的最小清单文件，包含备份 ID、类型、完成时间、数据库版本、文件大小、对象标识和 SHA-256 校验和，不含凭证或数据库业务内容；PostgreSQL 备份记录是页面目录，OSS 清单用于整库恢复后自动找回被旧快照覆盖的备份元数据。
- **保留策略**：按设定天数保留（天数在系统设置中调整），过期备份的数据库目录记录、OSS 备份对象和对应最小清单一并清理；任一对象清理失败必须保留失败记录并可重试，不能先删除目录记录导致剩余对象不可追踪。备份 Worker 同时分页扫描固定备份前缀，对超过 24 小时仍缺少合法配对清单或备份对象的残留文件，在确认未被未完成恢复控制清单引用后物理清理；不得触碰未过期的完整备份对、当前恢复对象或其它 OSS 前缀。
- **立即备份**：数据备份页提供「立即备份」按钮，管理员可随时主动创建一份与定时备份同格式的备份；重复点击不得重复创建同一任务，页面可查看执行进度和结果。
- **备份/恢复互斥**：全平台同一时刻只允许一个 `pg_dump`、紧急备份或整库恢复执行阶段占用数据库备份恢复锁，正确性以 PostgreSQL 中的任务状态/排他锁和 §10 外部恢复清单为准，不只依赖 Redis。定时与立即备份相遇时保留各自任务记录并按创建时间串行执行；同一调度周期不得重复创建每日任务。普通备份仍在运行时，整库恢复只能停留在预检等待阶段，必须等其完成或明确失败后才能创建恢复前紧急备份并进入维护状态；一旦存在未完成恢复清单，新的定时/立即备份请求不再排队而是拒绝并提示恢复处理中，避免跨越待恢复时间线继续制造普通备份。
- **恢复前紧急备份**：「紧急备份」名称仅用于恢复流程自动创建的回退副本；从旧备份恢复前必须先尝试完成紧急备份并验证上传结果及 OSS 最小清单。如当前数据库已损坏导致紧急备份无法完成，界面必须显示明确风险并要求再次人工确认，不得伪装为已有回退副本。
- **恢复**：恢复执行前先校验所选备份的完成状态、校验和、备份格式和 PostgreSQL 版本兼容性，不允许用未校验或已损坏文件覆盖当前数据库。通过预检后，恢复执行器先持久化下述数据库外恢复清单并进入统一维护状态，停止接收新业务请求和新任务；随后在有界时间内等待已进入的写事务和 Worker 任务结束，关闭各应用连接池，并确认除恢复执行器外不存在仍可写入目标数据库的连接。无法完成停写时必须在覆盖数据库前终止本次恢复并保持维护状态等待人工处理，不能边恢复边接受旧连接写入。恢复备份数据后，由恢复流程在维护状态内复用 Migration Runner 的迁移执行器，只执行该备份尚未包含、且属于当前已部署 commit 的正向迁移，把旧备份结构推进到当前代码要求的版本，不启动旧代码、不执行降级迁移，也不递归触发发布流程的“迁移前立即备份”（原始恢复文件与恢复前紧急备份已经分别保留）。随后把备份中恢复出来的历史非终态后台任务统一标记为“因整库恢复取消”，不得把旧快照中的待投递/执行中任务重新执行；当前恢复结果按外部清单中的稳定恢复标识重新写入恢复业务记录和任务结果。恢复执行器还必须扫描固定 OSS 备份前缀，逐一校验最小清单与对象的大小、校验和和格式，把数据库快照中缺失但仍完整存在的定时、立即和紧急备份记录幂等补回页面目录；无清单、清单不合法或对象不完整的文件不得自动登记为可恢复备份，也不得在恢复过程中自动删除。数据库内的当前发布基线同步校正为部署状态和当前镜像共同确认的运行 commit，不因恢复旧库而把应用版本基线倒退。最后执行数据库连接、迁移完整性、结构版本、至少一名“未注销且已激活”的超级管理员、其它核心数据和全部应运行服务的就绪检查，全部通过后才退出维护状态；若不存在可登录超级管理员，则本次恢复校验失败并保持维护状态，只能由原超级管理员选择紧急备份或其它有效备份重新恢复，不能临时绕过身份体系开放站点。任一恢复、迁移或校验步骤失败都保持维护状态并保存明确阶段和脱敏原因；恢复任务不自动重试，由超级管理员手动决定重试或使用紧急备份重新恢复。
- **Redis 恢复边界**：PostgreSQL 恢复成功并完成正向迁移、且所有应用与 Worker 仍保持停写时，恢复执行器必须清空本平台专用 Redis 容器的整个应用数据集，不得保留恢复操作开始前的会话、登录限流计数、配置缓存/广播、幂等响应缓存、并发占用、分布式锁或 BullMQ 作业。不得尝试把当前 Redis AOF/RDB 数据与旧 PostgreSQL 快照拼接使用；否则其中的引用和作业可能指向恢复点之后已不存在或状态不同的数据。清空后，各服务从已恢复的 PostgreSQL 重新加载配置和必要缓存，调度器只根据恢复后任务表重建允许的调度；备份中恢复出的历史非终态任务已经按上条取消，不能重新投递。全部已有登录会话统一失效，维护结束后所有用户重新登录。Redis 清空、重新健康探测、配置刷新或调度重建任一步失败都必须保持维护状态，不得带着混合时间线开放流量；该操作只作用于本项目专用 Redis 数据集，不提供前端按钮或任意键模式参数。
- **维护状态独立性**：恢复所用的维护状态不得存放在即将被替换的 PostgreSQL 数据库中。恢复执行器在 ECS 持久化目录创建维护标记文件，Nginx 与后端容器以只读挂载方式读取；标记存在时，Nginx 对业务页面和 API 统一返回维护页面或 `503 SYSTEM_MAINTENANCE`，仅保留健康探针和恢复流程自身需要的内部通道。即使数据库被旧备份覆盖、服务或 ECS 重启，维护状态仍保持；只有恢复执行器完成全部校验后才能原子移除标记并恢复流量，人工强制移除必须记录运维审计。
- **恢复控制状态独立性**：PostgreSQL 中的后台任务、恢复业务记录和备份页面目录会被整库恢复覆盖，因此不能作为恢复执行阶段的唯一事实来源。恢复执行器在与维护标记相同的 ECS 持久化目录中，以原子替换方式维护一份权限受限的恢复控制清单，只保存恢复标识、所选 OSS 对象标识与校验和、恢复前紧急备份标识、发起人用户 ID、当前阶段、阶段时间、脱敏错误和本次控制凭证摘要，不保存数据库密码、OSS 凭证、控制凭证原文或临时签名地址。BullMQ 和 PostgreSQL 任务表只负责把人工恢复请求可靠交给执行器；执行器成功写入外部清单后，以该清单作为恢复完成前的状态事实来源，不再依赖可能被替换的数据库任务行。执行器或 ECS 重启时发现未完成清单，必须继续保持维护状态并显示“恢复未完成”，不得自动重放任何破坏性步骤；由原发起超级管理员通过恢复专用控制会话明确选择重试当前阶段或使用紧急备份恢复。全部校验成功并把最终结果写回新数据库、补回 OSS 中可验证的备份目录后，清单原子标记完成，再移除维护标记；完成清单可保留为本次恢复的数据库外最小运维记录。
- **恢复专用控制会话**：超级管理员完成最终恢复确认、但尚未进入维护状态前，恢复执行器生成仅绑定本次恢复的高熵随机控制凭证，外部清单只保存摘要，浏览器仅通过 `HttpOnly + Secure + SameSite=Strict` 且 Path 限定为恢复控制路径的 Cookie 持有原文；凭证不得出现在 URL、页面文本、日志、PostgreSQL 或 Redis。维护状态下 Nginx 只额外开放独立的恢复状态/确认路由，该路由由恢复执行器直接校验外部清单和控制凭证，可查看当前阶段与脱敏错误、重试当前失败阶段或改用清单中已记录的紧急备份，不允许查询业务数据、任意选择 OSS 路径、移除维护标记或调用普通后台 API。每次破坏性重试仍需在恢复页二次确认，控制凭证在清单完成或明确终止后立即失效。
- 浏览器关闭、Cookie 丢失或控制凭证失效时，不创建数据库后门账号，也不为了恢复普通登录而跳过维护状态。拥有 ECS 运维权限的维护者只能通过项目提供的受控部署命令，为当前未完成恢复清单轮换并在当前终端一次性显示新的恢复控制链接；链接同样使用 `/recovery#<token>` fragment，恢复页以请求体兑换为上述受限 Cookie 后立即清除地址栏，令牌不得进入终端历史以外的持久日志、Nginx URL 或前端存储。命令不得接受任意恢复对象参数，不得直接删除维护标记，执行与轮换时间写入同一数据库外运维记录。这样即使 Redis 已清空或 PostgreSQL 尚不可登录，仍能继续完成既有恢复，而该兜底不能访问正常业务功能。
- **备份能力边界**：本期明确采用"每日逻辑备份 + 立即备份 + OSS 存储"，不提供 WAL 归档或任意时点恢复；可恢复点为最近一次校验成功的备份，页面必须向操作人显示备份时间与可能的数据缺口。
- **可恢复性验证**：备份成功不能只以 OSS 上传成功为判定依据，至少校验文件校验和、归档格式，并确认 `pg_restore --list` 能完整解析归档目录；MVP 不建设定期或自动恢复演练任务。实际恢复只由超级管理员在数据备份页面手动发起，并继续完整执行恢复前预检、维护状态、正向迁移与恢复后校验。
- **删除与历史**：关键业务数据按主 PRD §2.6 软删除并保留历史记录，仅从正常使用中移除，保证可追溯；是否提供用户可见的恢复入口由对应业务章节决定，整库误操作恢复由备份能力承担。

## 11. 健康状态

- 管理页面权限：backstage 功能“健康状态”。该登录后页面与下述免登录探针接口是两个不同界面；权限只控制管理页面，不改变 Docker/Nginx 访问探针的方式。
- 管理页面按服务显示存活、就绪、依赖状态与最后检查时间；后台任务先显示全平台总览，再按“所属模块 + 任务类型”分组汇总统一后台任务表中的当前待投递数、当前队列中/执行中数量、当前执行租约异常数，以及**最近 24 小时滚动窗口内的失败数量和最近一次失败时间**。24 小时为固定展示口径，不放入系统设置；页面不累计展示全部历史失败数量，不展示任务参数、业务数据、异常堆栈或逐条统一任务明细，也不提供通用重试、取消和删除按钮，因此本期不新增“任务中心”页面或“后台任务管理”权限。
- 用户主动发起且需要查看结果的任务继续在所属业务页面查询，例如备份与恢复在“数据备份”。健康状态页对应分组存在明确业务页面且当前用户具有该页面权限时，数量或最近失败时间可跳转到该业务页面并带入任务类型、失败状态和 24 小时时间范围；账号生命周期处理、未关联图片清理等纯内部维护任务，或没有业务明细页的任务，可在当前用户同时拥有“系统日志”权限时跳转到按模块、任务类型和时间范围筛选的 §8 系统日志。用户没有目标页面权限时不显示跳转入口，不能因为拥有“健康状态”权限而获得额外业务记录或错误详情。健康状态汇总只用于发现异常，具体排障仍通过有权访问的业务记录、系统日志和容器日志完成。
- 各后端部署单元提供一个健康状态接口：存活（进程活着）与就绪（依赖就绪、可服务）两级状态，供外部监控与部署检查使用（Docker/Nginx 探针）；`platform-core` 不为 base/backstage 伪造两个进程探针，但其就绪检查必须覆盖两者全部必需依赖。
- 探针接口为机器探测专用，免登录访问，仅返回当前服务的最小存活/就绪状态，不返回依赖地址、错误正文、任务数量或任何业务数据；管理页面通过登录后的受保护接口读取上述汇总。

## 12. 数据实体清单

> 供需求梳理与数据设计时参考；只列业务概念，不含字段细节。

- **backstage（`platform-core` 内）**：系统入口与业务分组、功能权限目录（系统/业务板块/功能三层）、员工功能授权（含数据范围）、权限组（命名的一组功能授权，可跨系统）、系统设置项、全平台集中错误日志（含指纹、时间桶、发生次数、脱敏样本和处置元数据）、安全日志（认证与账号安全事件）、统一后台任务事实/投递记录、更新日志、系统公告、备份与恢复业务记录、资料修改申请（含状态/版本/申请对象与部门快照）。用户、激活邀请、钉钉绑定、会话等 base 实体见 base PRD §7。
- **各模块公共实体**：模块内操作日志（统一字段：操作者、部门快照、系统、功能、操作性质、摘要、追踪标识等），由各模块分别存储于各自 schema，管理后台使用联合只读视图汇总（机制见主 PRD §3.3）。

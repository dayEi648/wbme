> 本文档定义 WBME 企业管理平台**人事系统**的需求。
> 平台级通用机制（功能权限、统一审批、软删除、基础设施、前端规范等）见主 PRD：`docs/prds/prd.md`。

## 2. 面向用户

普通员工（提交本人加班申请、查看本人加班记录）、项目负责人/代提人（为符合条件员工代提交加班）、加班审批人（处理加班待办、管理视图查询）、人事管理员（hr 配置、字典）、组织管理员（组织架构、部门管理、岗位管理、职称管理）。

## 3. 加班管理

加班能力拆分为多个独立功能，使用者各不相同：

**加班申请表单**（由 hr 功能"加班申请"与"代交加班"共同控制）

- 加班申请统一使用一个表单：填写日期、起止时间、事由和加班人员名单，一个批次中所有人员共用同一日期、时间段和事由。
- 一张申请只允许填写同一自然日内的时间段，结束时间必须晚于开始时间；结束时间可使用 `24:00` 表示当日结束。跨午夜加班必须按两个自然日拆成两张申请，例如第一张至当日 `24:00`、第二张从次日 `00:00` 开始，系统不自动跨日拆单。
- 进入表单时默认已添加当前用户。用户只拥有"加班申请"功能时，名单固定只能包含本人，不显示添加其他员工的入口。
- 用户拥有"代交加班"功能时，可以在其授权数据范围内添加一名或多名其他员工，也可保留或移除名单中的本人；同一批次内同一员工不能重复出现。
- 只拥有"代交加班"而未拥有"加班申请"时仍可进入同一表单；"部门/公司"范围均隐含本人，因此可在授权范围内选择包含本人。
- 系统按中国法定节假日、调休和周末判断日期类型（工作日/休息日/法定节假日）并计算加班时长（小时，保留两位小数）；提交前展示日期类型、时长和补交提示。日期判断统一调用后端节假日 API 适配器，不让前端直连第三方，也不要求管理员维护本地日历。
- 加班时长按结束时间与开始时间之间的实际分钟数计算，不自动扣除用餐、休息或其它时间；如需扣除，由申请人拆分或调整所填时间段。展示与汇总时以“分钟数 ÷ 60”计算小时并按十进制四舍五入保留两位小数，数据库保留原始分钟数作为计算依据，避免多次汇总舍入误差。
- **免费节假日数据源**：MVP 固定接入国内免费服务 `https://holiday.ailcc.com`，使用无需付费套餐或付费密钥的 `GET /api/holiday/info/{date}` 接口，由 hr 后端调用，前端不直连。本期不接入聚合数据等付费节假日接口，也不建设多供应商自动切换；如果该免费服务以后停止维护，由开发者在适配器内切换另一项国内免费数据源并通过正常版本发布完成，不改变业务页面和已保存数据结构。
- **调用、缓存与限流**：hr 按北京时间日期查询。相同日期已有 24 小时内成功获取的规范化结果时直接复用；否则调用免费 API，同一日期的并发查询合并为一次外部请求，并按供应商公开限额设置进程级有界限流，不通过无意义轮询消耗免费额度。调用成功后直接在 PostgreSQL 中按日期新增或覆盖规范化结果，不增加同步审批、待确认状态、人工审核或独立同步任务。24 小时是集成缓存的固定工程参数，不放入人事设置；已提交加班仍使用下述业务快照，不受缓存刷新影响。
- **响应校验与失败兜底**：适配器只接受 HTTPS，严格校验响应成功码、请求日期、日期类型枚举（工作日/周末/节日/调休放假/补班）、星期值及休息/补班语义的一致性；保存供应商标识、规范化结果、获取时间和原始响应的 SHA-256 摘要，不依赖供应商未提供的“版本号”。超时、限流、响应缺字段、类型矛盾或日期不匹配均按依赖失败处理。调用失败时，如果同一日期已有保存成功的结果则复用并在日志中记录本次依赖失败；没有已保存结果时，回落到**随版本内置的离线兜底数据**：每年国务院办公厅节假日安排由开发者更新为受版本控制的静态数据文件（不属于节假日日历管理，无需管理员维护），命中时按内置数据判断并在快照中记录降级来源标识；内置数据未覆盖的日期才返回 `DEPENDENCY` 类型、`HOLIDAY_API_UNAVAILABLE` 错误码并提示稍后重试，不按周一至周五自行猜测，也不提交半成品申请。第三方原始错误不得直接返回前端。
- **外部请求安全边界**：供应商域名和 HTTPS 基础地址作为受版本控制的部署级集成配置固定在允许列表中，不进入管理页面，也不能由请求参数、数据库普通设置或管理员填写任意 URL；调用路径只能由服务端以校验后的 `YYYY-MM-DD` 日期生成，禁止跟随重定向到白名单外主机，并设置固定连接、响应与响应体大小上限。该免费接口默认不需要凭证；以后即使免费替代源需要凭证，也只能从部署机密注入，不得返回前端或写入日志/业务记录。
- 每条加班明细在提交时保存当次采用的日期类型、来源标识（供应商标识或离线兜底数据版本）、响应/内置数据摘要、获取时间以及是否使用已保存结果的快照；以后供应商数据变化不追溯改写已提交、已审批或历史记录，保证审批和月度汇总可复现。
- 加班申请面向**计划性加班**：加班日期允许为未来日期，可提前的天数在人事配置中设置（提前申请窗口，默认 30 天，见 §9）；同时支持在规定窗口内补交过去的加班（补交窗口默认最近 7 天，在人事配置中设置，见 §9）。加班日期必须位于“当前日期 − 补交窗口 ～ 当前日期 + 提前申请窗口”区间内（按主 PRD §9.10 北京时间计算）。未来日期的日期类型同样由节假日 API 适配器返回并形成提交时快照；供应商尚未公布节假日安排的日期按其返回的工作日/周末语义使用，后续官方安排发布不追溯改写已提交快照。
- 同一员工同一天可提交多条不重叠的加班时间段；提交时校验当批次与该员工已有待审批/已批准记录的时间段，禁止重叠计时。
- 多人加班批次按**整批全有或全无**提交：服务端先校验全部人员的在职状态、授权范围、时间重叠、日期窗口（提前申请/补交）和日期/时间合法性；任一人员失败时不创建审批批次或任何加班明细，并逐人返回失败原因。全部通过后在同一事务中创建一个批次及全部人员明细，后续仍由审批人整批批准或驳回。
- 查看本人已批准的加班记录与月度汇总（个人视图）、取消本人待审批批次（批准或驳回后不能取消）；含"加班申请 / 历史记录"两个视图，本人历史隐含。

**代交加班权限与跟踪**（hr 功能"代交加班"，数据范围部门/公司）

- 项目负责人/代提人可通过上述统一表单为范围内员工提交加班；代提对象必须在其授权数据范围内，提交时保留代提人、每名加班员工与其部门快照。
- 代提批次由代提人跟踪、取消（批准或驳回后不能取消）。
- 同一批次内同一员工不能重复出现；员工调岗不影响历史记录查看。

**加班审批**（hr 功能"加班审批"，数据范围部门/公司）

- 审批中心处理加班申请：整批批准或驳回，驳回必须填写原因；待审批批次只有提交人（或代提人）可取消。审批人的数据范围必须覆盖批次中全部加班员工；跨范围批次需由公司范围审批人处理。
- 含已处理历史（审批上下文）；审批人可见的待办范围由其授权数据范围决定。

**加班历史记录**（hr 功能"加班历史记录"，数据范围部门/公司）

- 管理视图查询：员工列表 + 月度统计 + 下钻查看员工记录 + 导出。

## 4. 审批中心（hr）

- 统一待办，支持按"申请类型"筛选：**加班申请、岗位申请**两类；待处理/已处理筛选；关键字、申请人、审批人搜索；支持导出。
- 加班申请类型的审批权归属"加班审批"功能（数据范围部门/公司，决定可见待办）；岗位申请类型的审批权归属"组织架构"功能（数据范围公司）；类型选项按当前用户功能授权显示。
- 审批中心只承载待办处理与历史查看；本人记录由各功能"历史记录"视图按授权数据范围承载。

## 5. 组织架构

- 权限：hr 功能"组织架构"。
- 组织架构（部门树 + 全体员工列表）；部门树的维护操作由"部门管理"功能权限控制（功能入口对持有"组织架构"或"部门管理"任一功能者开放），本功能负责用户编排。
- **用户组织信息维护**：查看全体员工，直接调整任意用户的所属部门与岗位（包括超级管理员的部门/岗位）；一个员工可由组织管理员手工加入多个部门，多部门并列展示，展开任一归属部门均可见该员工且无主次之分。员工只能有一个当前岗位，组织管理员也不能为同一员工分配多个岗位；所选岗位必须同时适用于其全部当前部门，超级管理员、组织管理员和普通员工一视同仁，管理员手工编排与岗位申请审批均不能绕过。多部门关系的新增、调整和移除只能在本页面手工完成，不通过员工自助申请；员工调岗不影响其历史记录查看。
- **岗位申请审批**：持有"组织架构"功能者自动获得岗位申请审批权（在 §4 审批中心处理）；申请来源为员工个人中心提交的岗位变更申请，每张申请固定为一个目标部门和一个目标岗位。同一员工同时最多一条待审批岗位申请，批准、驳回或取消后可再次申请；提交与审批时均校验该员工不存在另一条待审批岗位申请。批准时再次校验员工仍为无部门或单部门状态，以及目标部门仍有效、目标岗位仍启用并允许自助申请且适用于目标部门；任一条件不再成立时保持待审批并明确提示不能批准，审批人可驳回，申请人也可取消。若管理员在待审批期间已将其调整为多部门员工，则同样不能批准该申请，避免自助申请覆盖管理员维护的多部门关系。管理后台创建用户不产生岗位申请，新账号的初始部门与岗位由组织管理员在本页面直接编排。

## 6. 部门管理

- 权限：hr 功能"部门管理"。
- 位于组织架构功能内（与组织架构共用，无独立功能入口）。
- **部门树维护**：维护公司多级部门树；一个部门可有多名负责人；支持查询、创建、编辑、停用和批量硬删除（按主 PRD §2.6 配置类数据规则）。有未删除下级部门时禁止删除（须先处理下级）；删除前展示该部门的在职员工数、固定资产归属数、待审批申请与职称规则引用数并要求确认，确认后在同一事务中物理删除并把当前业务引用置空：该部门员工的所属部门、固定资产的所属部门、部门负责人关系等（这些字段原本允许为空，置空后员工变为无部门员工，可由组织管理员重新编排）。历史审批快照、操作记录等历史引用不受影响，仍按快照展示原部门名称。组织关系调整不能形成循环。部门停用后不得作为新建下级部门、新组织关系、岗位申请或其它新业务归属的选择目标，但既有员工关系、部门范围授权计算和业务引用继续有效并标记“部门已停用”，不能因停用静默缩小已有管理员的数据范围。
- 部门父子关系、停用状态或删除会影响“部门及全部下级”的闭包或可选目标，hr 必须在对应事务中递增全局组织树版本并记录变更前后结构；移动部门节点时页面明确展示受影响子树并二次确认。所有服务按 base PRD §3 的会话版本校验规则在下一次受保护请求校验该版本，使旧的部门范围授权缓存整体失效，不能只给部门表改父节点而继续复用旧权限集合。
- 部门数据被全站多个功能引用（数据范围计算、员工组织关系、资产台账、申请与审批等），独立授权便于将部门维护交给指定人员；财务项目按 fin PRD §2 为公司范围且当前字段不包含部门，不虚构财务项目与部门的直接关联。

## 7. 岗位管理

- 权限：hr 功能"岗位管理"（独立权限，与组织架构同级）。
- 维护岗位名称、说明、启用状态、排序；可设置是否允许员工自助申请及适用的部门范围。岗位停用后不再出现在新的组织编排和员工自助申请选择器中，既有员工关系和历史记录仍保留并标记“岗位已停用”，不能因停用自动清空员工岗位。
- 修改岗位适用部门前必须校验当前仍分配该岗位的全部员工；若修改后岗位不再同时适用于某名员工的全部所属部门，则整次修改拒绝并返回受影响员工，不允许通过配置变更制造违反 §5 的现存组织关系。是否允许自助申请的变更只影响之后的提交与待审批申请能否批准，不改写已完成历史。
- 岗位支持批量硬删除并遵循主 PRD §2.6 配置类数据规则；删除前展示当前分配员工数、待审批岗位申请数与职称规则引用数并要求确认，确认后在同一事务中物理删除并把当前员工的该岗位置空（原本允许为空）；仍引用该岗位的待审批岗位申请此后无法批准（批准时校验“目标岗位仍存在且启用”失败），只能驳回或由申请人取消，删除确认中需明确提示这一点。历史终态申请和只读审计通过岗位快照继续展示；职称规则中被删除岗位的条件永不命中，由管理员自行清理。
- 岗位可被分配给员工；岗位本身不携带任何业务权限；岗位数据被岗位申请等业务引用，独立授权。

## 8. 职称管理

- 权限：hr 功能"职称管理"。
- 维护"部门、岗位、站点角色"与职称名称之间的匹配规则；每条规则包含职称名称，可只填写部分匹配条件，并维护启用状态和排序。部门条件对多部门员工采用“任一当前所属部门命中即匹配”，岗位和站点角色按当前唯一值匹配；一条规则中填写的全部非空条件仍须同时成立。
- 查询员工当前职称时，先筛选全部已启用且其非空条件均匹配的规则，再按“非空匹配条件数量更多 → 排序值更小 → 规则 ID 更小”确定唯一职称；因此部门、岗位和站点角色同时匹配的规则优先于只匹配其中一项的通用规则，同等具体程度由管理员排序决定。没有规则命中时职称为空，但不阻止账号或组织信息正常保存。
- 当前职称是规则计算得到的派生值，不作为可人工编辑的独立员工字段，也不在用户表冗余保存。hr 维护的受评审只读视图按当前部门、岗位、站点角色和有效规则返回职称，因此组织、角色或规则变更后下一次查询立即得到新结果，不需要跨服务同步任务、批量回填或人工“重新计算”按钮；公司不足 100 人，本期该查询成本可控。以后某项业务确实需要保留当时职称时，应在业务记录中保存提交时职称文字快照，不能依赖之后重新计算。职称规则的增删改按主 PRD §3.3 记录操作日志；规则作为普通实体仅支持批量软删除，软删除规则不再参与匹配，不提供硬删除。

## 9. 人事配置（系统内页面）

- 权限：hr 功能"人事配置"。
- 运行参数：加班提前申请窗口（默认 30 天）、加班补交窗口（默认 7 天）等（随业务引入）。
- 节假日判断按 §3 使用固定白名单中的国内免费 API，并把成功结果直接保存；本期不提供节假日日历管理、立即同步、人工确认、审批或付费接口配置。供应商地址属于受版本控制的部署级集成配置，不在业务页面编辑或展示；当前免费接口无需凭证。
- 人事字典（机制保留，字典项随业务引入）：表单只能使用启用选项；选项可新增、编辑、排序、停用，并按主 PRD §2.6 批量硬删除未被引用的字典项；任一目标已被业务或历史记录引用时整批拒绝。停用和硬删除均不能破坏历史记录，历史数据引用停用选项时仍显示原值。

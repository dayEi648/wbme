# WBME 待修复清单

> 依据：主 PRD + base/backstage/asset/hr/fin 五份子系统 PRD 与全库代码对照。
> 严重度：`S` 严重（数据丢失/安全底线/功能完全不可用）· `M` 中等（明确违背 PRD 契约）· `L` 轻微。
> 位置前缀：`PC` platform-core · `AS` asset · `HR` hr · `FIN` fin · `WEB` 前端 · `DEP` 部署/基础设施。

## 〇、总原则（所有修复必须遵守）

1. **严禁偷懒**：不得强行套用同一组件、不得强行做一样的页面、不得强行简化功能实现；每个页面/弹窗/表单按自身业务形态设计。
2. 导航按业务分组、一表一页、全站分页默认 20 条/页、删除一切开发笔记式描述文案、禁止让用户面对代码（JSON/ID 手输）。
3. **修复口径**：
   - 分类/库位/字典项属于配置类数据：被引用时**不整批拒绝**——删除前服务端返回每个目标仍被引用的情况、前端明确展示并要求确认，确认后物理删除；既有业务与历史记录按删除前名称快照原样展示。按主 PRD §2.6 修复。
   - 具体实现层面问题：优先遵循 PRD；实现与 PRD 不符 → 按 PRD 修复；PRD 内部矛盾或 PRD 非最优决策 → 向产品提问，结论同步回 PRD。
   - 功能需求层面：必须符合 PRD（如「不设个人记录汇集页」）。
4. 修复后必须同步 PRD / API 文档 / `docs/directory.md`（如结构变化），并按约定运行 `pnpm lint / typecheck / test / build`。

## 批次 1：共享契约与展示基线

### 1. 全局 30 秒请求超时拦截器仍会截断恢复确认前的紧急备份等待【M·PC】
- 位置：`apps/platform-core/src/modules/backstage/backup/backup.controller.ts:55-57`（`POST /restores/confirm` 未挂 `@RequestTimeout`）；`apps/platform-core/src/modules/backstage/backup/backup.service.ts:226-250,364-380`（`confirmRestore` 内同步轮询等待紧急备份，上限 `EMERGENCY_BACKUP_WAIT_MS=300_000`）。
- 现状：导出类长任务路由显式 `@RequestTimeout(EXPORT_TIMEOUT_MS)`，恢复确认路由仍走全局默认 30s；紧急备份超过 30s 时请求会被 503 截断，任务仍可能继续执行。
- 修复方向：为 `POST /restores/confirm` 挂独立超时（或专用 `RESTORE_CONFIRM_TIMEOUT_MS`），或改为创建紧急备份后立即返回、前端轮询终态，避免同步等待超过全局超时。

## 批次 2：platform-core 契约与健康

### 1. 公告列表在自定义排序时仍缺少 id 唯一性兜底【M·PC】
- 位置：`apps/platform-core/src/modules/backstage/content/announcement.service.ts:56-59`（`orderBy: tableQuery.orderBy ?? [{ updatedAt: 'desc' }, { id: 'desc' }]`）；`packages/server/src/table-query.ts:156-161`（自定义 `sorts` 不追加 id）。
- 现状：release-log / backup 默认排序带 id 兜底；公告列表一旦用户传入自定义排序，`tableQuery.orderBy` 直接生效，同值行翻页边界仍可能重复或遗漏。
- 修复方向：统一在最终 `orderBy` 末尾追加 `{ id: 'desc' }`，或让 `buildTablePrismaQuery` 自动补唯一性字段。

## 批次 3：前端页面结构重构

### 1. 导航默认分组结构与既定分组口径仍有差异【M·WEB】
- 位置：`apps/web/src/pages/backstage/BackstagePage.tsx:22-33`、`apps/web/src/pages/asset/AssetPage.tsx:53-73`、`apps/web/src/pages/hr/HrPage.tsx:28-36`、`apps/web/src/pages/fin/FinPage.tsx:40-45`。
- 现状：AppShell 支持分组/子菜单/搜索/面包屑，默认导航未完全按清单分组口径落地：asset 的“审批中心/系统设置”仍为顶层叶子，hr 的“加班管理/审批中心/系统设置”未分组，asset 分组名与“库存管理/申请与审批/历史记录”不一致。
- 修复方向：调整默认 `NAVIGATION` 的 `group/subGroup` 使其符合既定分组口径；若产品接受“审批中心/系统设置”作为顶层叶子，则同步修正 PRD/清单口径。

### 2. 扫码进入消耗品申领页仍有一个功能性说明作为页面副标题【M·WEB】

- 修复方向：删除该 `description`，将扫码定位提示移到表单内（如表单顶部 Alert 或明细区提示）。

### 3. 新建/提交按钮文案仍未统一【L·WEB】
- 位置：`apps/web/src/pages/asset/AssetPage.tsx:257,298,640,922`、`apps/web/src/pages/backstage/BackstagePage.tsx:414` 等。
- 现状：已结清借还按钮禁用、二维码停用/重新生成 danger、解锁按钮按状态显隐、Portal Tooltip 等具备；但新建/提交类按钮仍存在“发起调拨/登记维修/提交申领/执行直接处置/生成恢复预览”等差异文案，未形成统一命名规范。
- 修复方向：明确按钮命名规范并统一；若产品确认按动作语义命名可接受，则移除本条。

## 批次 4：部署与基础设施

### 1. 恢复预检对缺失 SSE 加密头的备份对象未 fail-closed【M·DEP】
- 位置：`apps/recovery-executor/src/recovery-executor.service.ts:432-446`；上传侧 `packages/files/src/file-storage.ts:246,350` 携带 `x-oss-server-side-encryption: AES256`。
- 现状：备份上传统一带 SSE-OSS/AES256 头；恢复预检调用 `headObject`，但只拒绝“存在且非 AES256”的头，`headObject` 缺失或读取失败时仅 warn 后继续，未把“无加密元数据”判为失败。
- 修复方向：生产 OSS 场景下将缺失 SSE 头视为预检失败（本地替身可跳过），读取失败时应 fail-closed，避免明文或旧对象通过预检。

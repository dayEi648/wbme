## 一、严重问题（8 项）

### ✅ S1【DEP】生产发布必然失败：恢复执行器探针路径错误
- 位置：`deploy/docker-compose.yml`（healthcheck）、`deploy/release.sh`（wait_ready）、`deploy/restore-drill.md`
- 问题：恢复执行器就绪探针真实路由为 `/recovery/readyz`（`apps/recovery-executor/src/recovery-control.controller.ts`，`@Controller('recovery')`），compose healthcheck 与 release.sh 均探测 `:3090/readyz` → 404 → 容器永久 unhealthy、发布第 5 步等待超时 fail。任何发布（含无迁移常规发布）必失败。
- 修复方案：
  1. compose healthcheck 探针路径改为 `/recovery/readyz`；
  2. release.sh 的 `wait_ready` 支持路径参数，恢复执行器使用 `/recovery/readyz`；
  3. `restore-drill.md` 前置检查同步修正。

### ✅ S2【DEP】备份/恢复在生产完全不可用：pg_dump 15 vs PostgreSQL 18
- 位置：`deploy/Dockerfile`（`postgresql-client-15`）、`deploy/docker-compose.yml`（`postgres:18-alpine`）
- 问题：pg_dump 15 拒绝导出比自身新的大版本服务器（`server version 18.x; pg_dump version 15.x`）→ 定时备份、立即备份、迁移前备份、恢复管道全部硬失败。
- 修复方案：
  1. runtime 镜像改用 PostgreSQL 18 客户端：推荐以 `postgres:18-alpine` 为 runtime 基础镜像（自带 pg_dump/pg_restore 18）再装 Node 环境；或 apt.postgresql.org（pgdg）源安装 `postgresql-client-18`；
  2. 备份处理器增加"客户端版本 ≥ 服务器版本"启动校验，防再次漂移。
- 实现：Dockerfile 采用阿里云 pgdg 源（`https://mirrors.aliyun.com/postgresql/repos/apt`，密钥 `/ACCC4CF8.asc`）安装 `postgresql-client-18`，经 postgresql-common alternatives 提供 `/usr/bin/pg_dump`，与 compose 的 `PG_DUMP_PATH=/usr/bin/pg_dump` 一致；backup.processor 的 `assertPgClientCompatible` 在每次真实备份执行前校验客户端主版本 ≥ 服务器主版本，不满足则备份失败并中止迁移。留待 ECS 构建时最终确认。

### ✅ S3【DEP】生产 OSS 存储链路断裂：RAM 角色声明与 AK/SK 实现矛盾
- 位置：`packages/files/src/oss-config.ts`（仅读 `OSS_ACCESS_KEY_ID/SECRET`）、`deploy/.env.production.example`、compose 未注入 OSS 凭证
- 问题：生产不填 AK/SK → `createOssClient` 返回 null → 静默回退 `LocalFileStorage`（根 `.agents/tmp-oss`），生产容器 `read_only: true` 且未挂载该目录 → EROFS 写入失败。图片上传、备份对象上传、恢复取备份全链不可用。与项目既定决策（ECS RAM 角色）矛盾。
- 修复方案：
  1. `oss-config.ts` 支持 ECS RAM 角色（阿里云实例元数据 `100.100.100.200` 取 STS 凭证并自动刷新，无 AK/SK 时启用）；
  2. 生产模式（`NODE_ENV=production`）下禁止静默回退 LocalFileStorage，缺凭证直接抛配置错误；
  3. compose 中 platform-core/asset/worker/recovery-executor 统一注入 `OSS_RAM_ROLE_NAME` 与五组 OSS 变量（bucket/region/prefix），worker 此前完全缺 OSS 环境变量；
  4. `createFileStorage` 全仓调用点适配 async。

### ✅ S4【PC】有迁移的发布与首次部署必然失败：迁移前备份钩子 401
- 位置：`apps/migration-runner/src/pre-migration-backup.hook.ts`（Bearer 令牌调用）、`apps/platform-core/src/modules/backstage/backup/backup.controller.ts`（SessionGuard + FunctionPermissionGuard）、`packages/server/src/session/session.guard.ts`（只认会话 Cookie）、`deploy/docker-compose.yml`（`PRE_MIGRATION_BACKUP_WAIT: "1"` 已启用）
- 问题：钩子用 `Authorization: Bearer` 调 `POST /api/v1/backups/immediate`，该端点只认会话 Cookie + `data_backup` 权限 → 401 → runner 中止迁移；全新库场景 platform-core 尚未启动 → 首次部署死锁。且迁移前平台服务 readyz 恒 503（含迁移版本检查），"先起平台服务等 healthy 再迁移"不可行。
- 修复方案：
  1. 新增 `/internal/v1/backups/immediate` 内部端点（InternalTokenGuard + 调用方白名单 `migration-runner`，保留备份互斥锁与"存在未完成恢复清单则拒绝"逻辑），钩子改调内部端点；
  2. `release.sh`：有发布基线（升级部署）时先 `up -d platform-core worker`，以 `healthz`（免迁移检查的进程探针）与 `wait_worker_healthy` 判定可用，再 `run --rm migration-runner`（备份→迁移），最后 `up -d` 全部；迁移完成后第 5 节仍以 readyz 复核；
  3. 空库豁免：钩子触发备份失败时经 `isFreshDatabase`（pg 直连 `DATABASE_URL` 查 5 个业务 schema 表数）判定：全新库（无业务表，无数据可备份）则跳过备份继续迁移，否则照常中止；查询失败保守视为非空库不豁免；
  4. 备份服务端使用分钟级自动幂等键（默认键 `internal:{caller}:{windowKey}`、指纹含 windowKey），避免同日重试 409 锁死；
  5. 补真实 HTTP 路径集成测试。

### ✅ S5【AS】asset 批次资料纠正接口必然 500
- 位置：`apps/asset/src/modules/inventory/inventory.service.ts`（`$queryRaw` 选择 `b.warehouse_id`）
- 问题：`asset.batches` 表不存在 `warehouse_id` 列（Prisma 模型与迁移均确认：批次只有 `warehouse_name/path` 快照；`warehouse_id` 仅存在于 `inventory_items`/`stock_in_items`）→ 任何纠正请求 PostgreSQL 42703 → 统一 500。T7-4 验收"纠正不绕过审批"对应 API 100% 不可用。
- 修复方案：
  1. 纠正 SQL 与读取结果类型中移除 `warehouse_id`；
  2. 并发一致性：兜底字段（供应商/品牌/单价/备注）一律取锁后 batchRow/sourceItem；来源条目锁前/锁后缺失时区分「批次仍在但归属被并发移动」（VALIDATION_FAILED 重试）与「批次消失」；
  3. 补 correctBatch 单测（正常纠正 + 无后续流水限制 + 占用限制 + 并发交错用例：拒绝仅允许 VALIDATION_FAILED、至少一笔成功、供应商修改必须保留）。

### ✅ S6【WEB】HR 部门管理"新建部门"必然 404
- 位置：`apps/web/src/pages/hr/HrPage.tsx`（`create` 未配置 endpoint）vs `apps/hr/src/modules/org/department.controller.ts`（`@Get('tree')` / `@Post()`）
- 问题：`ResourcePage` 默认用列表端点 `/departments/tree` 提交 POST → 404。asset 库位管理显式配置 `endpoint: '/warehouses'` 规避了同类问题。
- 修复方案：HrPage 部门 `create` 配置 `endpoint: '/departments'`；顺带检查其它未显式配置 endpoint 的 create 项（岗位/职称/其余 ResourcePage 实例）。

### ✅ S7【FIN】fin Excel 导入取消/超时传播不彻底：确认事务可在超时响应后提交
- 位置：`apps/fin/src/modules/excel/excel.controller.ts`（abortSignal）、`packages/server/src/request-timeout.interceptor.ts`（rxjs timeout 仅停响应）、`apps/fin/src/modules/excel/import.service.ts`（applyImport 尾部无检查点）
- 问题：路由级 150s 超时只停止监听响应，handler 继续执行；`applyImport` 在覆盖循环最后一次 `checkTimeout()` 之后、审计 createMany 与事务提交之间再无检查点，超时/取消在此窗口触发时，事务仍会继续完成并提交——违反 fin PRD §4"不能在超时响应后继续后台写入"。
- 修复方案：
  1. 取消信号源：controller 同时监听 `req.on('aborted')` 与 `res.on('close')` 生成 abortSignal；`makeImportTimeoutCheck` 接入 signal 检查；
  2. `applyImport` 全程补检查点（新增前/每批写入后/覆盖前/逐行更新内/删除重建明细前/审计前/审计后/事务返回前），触发即抛错 → 事务回滚 → finally 释放锁；
  3. worker 池：排队任务 splice + reject、执行中任务先 reject 再 terminate（不复挂至路由超时）、dispatch 跳过终止中 worker；
  4. 补真实 HTTP 集成测试（excel-cancel.integration.spec：调用前已取消、写入窗口内取消、上传中断、响应关闭四场景），断言事务回滚、无部分写入、无审计残留。

### ✅ S8【PC】批量注销可清空全部超级管理员（并发竞态）
- 位置：`apps/platform-core/src/modules/backstage/user-admin/user-lifecycle.service.ts`（无锁 count）vs `super-admin.service.ts`（`SELECT ... FOR UPDATE` 锁全部超管行）
- 问题：批量注销只锁批内目标行，再对全部超管做无锁 count。两个并发批次分别注销两名不同超管时双双通过 → 0 名可用超管，平台失去根管理员。
- 修复方案：
  1. `loadDeactivationTargets` 内可用超管计数改为 `SELECT id ... FOR UPDATE`（与 demote 一致），锁内重新计数；
  2. 并发注销同一用户经 lifecycleVersion 条件更新输出业务冲突（UNAUTHORIZED），避免无条件重写撞 task_uuid 唯一约束 500；
  3. 补并发集成测试（核心护栏为 remaining=1 断言）。

**✅ M2【PC】批量操作与导出接口全部零限流**
- 位置：user-admin.controller.ts、permission.controller.ts、announcement 批量删除、backup.controller.ts（立即备份/恢复确认）、operation-log/system-log/approval 导出端点；全仓 `RateLimit` 仅存在于认证类端点

- 修复方案：
  1. 批量操作类端点按用户/IP 加 `RateLimit`（scope 按端点语义），导出加每用户每小时导出次数上限；

  3. `RateLimitGuard` 注册进 `@Global` SharedModule 并导出（此前从未注册为 provider，Nest 11 对未注册守卫静默跳过，11 处限流与登录/激活/注册/密码/钉钉认证类端点限流全部未生效）；REDIS_CLIENT 由全局 RedisModule.forRoot 提供；

**✅ M3【PC】公告批量删除静默跳过不存在目标**
- 位置：`apps/platform-core/src/modules/backstage/content/announcement.service.ts`（updateMany、返回 `deleted: ids.length`）
- 问题：不存在/已软删目标被静默跳过，返回值按入参 ids 计数。违背主 PRD §2.6"整批不变更 + 逐项目标原因"。

**✅ M4【PC】恢复执行器停写确认缺失**

**✅ M5【PC】图片下载接口无业务授权/归属校验**

  4. 「业务引用授权」（下载者≠上传者共享场景）为 MVP 取舍，当前 web 无调用方；引入图片共享/展示场景时须补归属或业务引用校验。

**✅ M6【PC】`me()` 返回的 functionCodes 未按权限目录过滤**

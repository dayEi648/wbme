## 〇、总原则（所有修复必须遵守）

1. **严禁偷懒**：不得强行套用同一组件、不得强行做一样的页面、不得强行简化功能实现；每个页面/弹窗/表单按自身业务形态设计。
2. 导航按业务分组、一表一页、全站分页默认 20 条/页、删除一切开发笔记式描述文案、禁止让用户面对代码（JSON/ID 手输）。
3. **修复口径**：
   - 分类/库位/字典项属于配置类数据：被引用时**不整批拒绝**——删除前服务端返回每个目标仍被引用的情况、前端明确展示并要求确认，确认后物理删除；既有业务与历史记录按删除前名称快照原样展示。按主 PRD §2.6 修复。
   - 具体实现层面问题：优先遵循 PRD；实现与 PRD 不符 → 按 PRD 修复；PRD 内部矛盾或 PRD 非最优决策 → 向产品提问，结论同步回 PRD。
   - 功能需求层面：必须符合 PRD（如「不设个人记录汇集页」）。
4. 修复后必须同步 PRD / API 文档 / `docs/directory.md`（如结构变化），并按约定运行 `pnpm lint / typecheck / test / build`。

### 1. 列表分页契约不统一（`{items,total}` 与 `{data,pagination}` 并存）【M·PC】
- 位置：`announcement.service.ts:47`、`release-log.service.ts:33`、`backup.service.ts:62,72`、`approval-center.service.ts:61`，以及 **asset/hr/fin 大量列表接口**返回 `{items,total}`；已对齐契约的有 operation-log、system-log、permission-group 及部分 HR 包装接口（`{data,pagination}`）。
- 根因：早期实现未遵循主 PRD §9.5 统一契约，前端 `normalizeList` 双兼容掩盖了漂移。
- 影响：同一平台两种分页结构并存，违反统一契约；前端/第三方集成需分别适配。

### 2. 全局 30 秒请求超时拦截器截断 120 秒导出预算【M·PC】
- 位置：`packages/server/src/request-timeout.interceptor.ts:7`（`DEFAULT_REQUEST_TIMEOUT_MS=30_000`）+ 各服务 `main.ts`（全局注册）；共享 `runExport` 预算为 `EXPORT_TIMEOUT_MS=120_000`（`packages/server/src/export/workbook-export.ts`）。
- 根因：多数导出路由未挂 `@RequestTimeout`，rxjs 全局 30s 先于 120s 导出预算触发，且超时不取消底层任务。**例外**：fin Excel 路由已设 `EXCEL_ROUTE_TIMEOUT_MS=150_000`（`excel.controller.ts`），不受本问题影响。
- 影响：未豁免的导出超过 30 秒必然 503 截断（大行数上限很容易超过），PRD 允许的 120 秒导出时限形同虚设；超时后 handler 仍可能在写响应。
- 修复方向：导出/流式下载/备份恢复等长任务路由显式豁免或挂独立超时（主 PRD §9.6）；对照 fin Excel 已有豁免补齐 asset/hr/platform-core 等其余导出路由。

- 影响：02:00 定时备份执行期间用户点「立即备份」或超管确认恢复被拒需手动重试；backstage PRD §10 要求「保留各自任务记录并按创建时间串行执行」「停留在预检等待」。

### 8. 恢复执行器停写检查不统计 idle 连接【M·DEP】
- 位置：`recovery-executor.service.ts:411-418`（只统计 `state IN ('active','idle in transaction') AND xact_start IS NOT NULL`）。
- 影响：各业务服务连接池 idle 连接常驻不计入；检查通过后这些连接仍可随时发起新事务写入（TOCTOU 窗口），与「不能边恢复边接受旧连接写入」不符。

### 9. 恢复补回备份不校验对象大小/校验和/格式【M·DEP】
- 位置：`recovery-executor.service.ts:502-577`（只校验清单 JSON 形状与 dump.fc 存在）。
- 影响：损坏/截断的备份对象会被登记为可恢复备份，用户可能选择无法恢复的备份。

### 10. 恢复退出维护状态前不校验业务服务就绪【M·DEP】
- 位置：`recovery-executor.service.ts:596-625`（READINESS 只查 `base._prisma_migrations`/function_registry/超管存在；注释自认服务就绪交部署编排）。
- 影响：业务容器未就绪时维护标记已移除，流量打到未就绪栈；恢复「成功」但平台实际不可用。

### 11. 恢复全流程无 PostgreSQL 大版本兼容性校验【M·DEP】
- 位置：`recovery-executor.service.ts`（pgVersion 只存清单不比对；备份侧有 `assertPgClientCompatible`，恢复侧无）。
- 影响：跨大版本备份在 pg_restore 中途失败可能留下半恢复状态。

### 12. 恢复投递不可重放 + timeout_at 死字段【M·DEP】
- 位置：`packages/tasks/src/constants.ts:75-82`（不含 RESTORE_DELIVERY）、`outbox.ts:52-59`、`status-transitions.ts:113`（timeout_at 仅写入无任何读取）。
- 影响：执行器「已接收但未回写」间崩溃时投递任务永久卡 RUNNING（不重投不终态），需人工介入；「支持超时控制」未实现。
- 修复方向：
  1. timeout_at：按主 PRD §9.1「支持超时控制」补超时执行/终止逻辑（超时任务按策略终态化或重投）；
  2. 恢复投递可重放性：主 PRD §9.1 明确「数据库恢复在写入外部控制清单**前**可以按上述投递规则重新交付」——允许清单写入前重投，执行器对同 restoreUuid 幂等接受（acceptDelivery 已有幂等基础，补投递重试次数/退避与清单写入后的禁止重投判定）；清单写入后仍不重投（backstage PRD §10「恢复任务不自动重试」指清单写入后的执行阶段，二者不冲突）。

### 13. 备份执行租约 600s 与长时间备份冲突【M·DEP】
- 位置：`packages/tasks/src/constants.ts:52`（`TASK_RUNNING_LEASE_SECONDS=600`）+ `outbox.ts:52-59`（租约过期 RUNNING 备份按可重放重领）+ `backup.processor.ts`（无租约续期）。
- 影响：>10 分钟的备份执行中租约被调度器接管 → 同一 backupId 被重复 pg_dump/上传执行第二次（有缓解：BullMQ jobId 去重 + 覆盖语义，但 Worker 崩溃/Redis 丢作业场景真实发生）。

### 14. 发布脚本强制启动全部服务【M·DEP】
- 位置：`deploy/release.sh:113`（`docker compose up -d` 无差别启动）。
- 影响：运维主动停用的业务服务在每次发布后被强制拉起，违反主 PRD §1.3「停止状态业务服务不被强制启动」。

### 15. 生产无 HTTPS 配置 + COOKIE_SECURE 硬编码【M·DEP】
- 位置：`deploy/nginx.conf:7-11`（仅 listen 80）、`docker-compose.yml:157`（`COOKIE_SECURE: "true"` 硬编码）、`.env.production.example:22-24`（`PUBLIC_ORIGIN=http://127.0.0.1`）。
- 影响：按模板部署时浏览器在纯 HTTP 下拒绝保存 Secure 会话 Cookie，**登录功能不可用**；平台处于明文 HTTP，违背 §9.7/§9.14。

### 16. pg_dump/恢复对象整体读入内存【M·DEP】
- 位置：`backup.processor.ts:107`（`readFile(dumpPath)` 全量）+ `recovery-executor.service.ts:450-451`（`getObject()` 返回 Buffer）。
- 影响：大库备份在 worker 256m/执行器 128m 上限下可能 OOM（备份失败重试、恢复中断），应流式处理。

### 17. Worker 就绪探针不反映 PostgreSQL【M·DEP】
- 位置：`worker-runtime.service.ts:75-77`（`ready = redis.status==='ready'`，PG 仅启动时探测）。
- 影响：PG 运行期故障时 worker readyz 仍 200，编排层误判可用。

### 18. 恢复执行器就绪检查不校验 OSS 配置【M·DEP】
- 位置：`recovery-executor.service.ts:118-145`（只查 DATABASE_URL/REDIS_URL/恢复会话密钥/状态目录，无 OSS_BUCKET/REGION）。
- 影响：OSS 凭证缺失时就绪仍为 true，恢复到 RESTORING 阶段才失败。

### 19. 发布脚本核验缺口【M·DEP】
- 位置：`release.sh:34-43`（无 `docker compose config` 校验）、`:139-147`（无数据卷核验）、`:149-154`（公网端口只查 `:80` 存在，不验证 5432/6379/3090 未暴露）。
- 影响：§9.12/§9.14 要求的发布门禁缺失，配置错误与端口暴露无法在发布时拦截。

### 20. Worker 队列清理失败不写集中系统日志【M·DEP】
- 位置：`queue-maintenance.ts:35-43`（仅 console.error）。
- 影响：§9.1「清理失败记录系统日志」未落实。

# WBME 实现规划

> 版本：0.1（初稿）· 2026-08-08 · 状态：待两人评审
> 基线文档：主 PRD `docs/prds/prd.md` 及各子系统 PRD、`docs/database-design/`（81 张表）、`docs/dev-workflow.md`（协作与 CI/CD）
> 本文档只呈现当前事实与既定决策；全部架构决策已在 §6 确定。

---

## 0. 总览

- **目标**：按 PRD 实现 MVP 全功能——platform-core（base + backstage）、asset、hr、fin 四个后端部署单元、前端、Worker 与恢复执行器；ai / agent 本期不实现（主 PRD §1.3、fin PRD「本期无表模块」）。
- **推进原则**：契约先行、骨架先立、平台核心先行、业务模块按依赖打通后并行。
- **数据库**：81 张表设计已评审定稿（见 `docs/database-design/`），实现阶段直接落 Prisma 模型与迁移。
- **协作**：GitHub 单仓库 monorepo、直接推 main + CI 门禁、版本 = 发布 tag（见 `docs/dev-workflow.md`）。

## 3. 阶段与任务清单

> 任务编号：`T{阶段}-{序号}`。每个任务标注对应 PRD 章节；验收标准以"可运行 + 测试通过 + 文档同步"为共性要求（操作日志、错误码、API 文档随任务同步，不单独列任务）。

### 阶段 0：工程基座（无 PRD 直接对应，支撑全项目）

**目标**：monorepo 骨架可跑、CI 转绿、开发环境可一键启动。

- [ ] **T0-1 monorepo 初始化**：pnpm workspaces、根 `package.json`（聚合脚本 lint/typecheck/test/build，供 CI）、根 `.nvmrc`（Node 24 LTS）、统一 tsconfig 基座、目录结构（`apps/platform-core|asset|hr|fin|web|worker`、`packages/contracts|approval|logging|tasks`，共享包清单见 §6-2）。验收：`pnpm install`（镜像源）后聚合脚本可执行。
- [ ] **T0-2 共享包骨架**：`@wbme/contracts`（主 PRD §9.6 错误目录 MVP 业务域 `ACCOUNT/PERMISSION/APPROVAL/ASSET/INVENTORY/HR/FINANCE/EXPORT/BACKUP/INTEGRATION` 的错误码目录 + `BusinessException` 基类）、DTO 基类、枚举/字符串联合类型（与 Prisma enum 对齐）；`@wbme/approval` / `@wbme/logging` / `@wbme/tasks` 在本阶段建包结构与导出约定，实现随 T5-1/T4-1/T4-2 落地。验收：错误码域内唯一、HTTP 状态映射存在（测试校验）。
- [ ] **T0-3 NestJS 应用骨架 ×4**：platform-core / asset / hr / fin 各自 NestJS 应用可启动（空模块 + 路由命名空间 `/api/v1`），Worker 与恢复执行器占位工程。验收：四服务 + worker 本地可启动。
- [ ] **T0-4 统一请求处理链路**（主 PRD §9.6）：请求上下文中间件（requestId/traceId）、全局校验管道（DTO 白名单）、认证/授权守卫挂载点、单一全局异常过滤器（异常→统一错误结构 `error {type, domain, code, message, details, requestId}`，映射表见 §9.5/§9.6）、业务异常不追加系统日志的规则。验收：统一错误结构测试通过。
- [ ] **T0-5 健康探针**（主 PRD §13 健康检查）：各部署单元 `/healthz`、`/readyz`；platform-core 就绪检查覆盖 base+backstage 依赖；探针免登录仅返回最小状态。验收：compose 内 healthcheck 可用。
- [ ] **T0-6 开发环境 compose + Migration Runner**（主 PRD §9.9）：`docker compose up`（PostgreSQL + Redis + 四服务 + Worker），Migration Runner 按部署单元顺序执行迁移并校验 `_prisma_migrations` 隔离；迁移前自动创建"立即备份"的钩子（阶段 4 实现时接入）。验收：全新环境一条命令起全套。
- [ ] **T0-7 CI 生效**（dev-workflow §4）：聚合脚本就位后 GitHub Actions 转绿；配置分支保护"Require status checks"。验收：push main 后 CI 全绿。

**检查点 0**：四服务 + 前端骨架在 compose 内启动、CI 绿、两人均能 `docker compose up` 跑通。

### 阶段 1：数据库建模（对应 `docs/database-design/` 全部 + 主 PRD §9.9）

**目标**：81 张表落地，4 套迁移序列与只读视图脚本就位，种子数据可初始化。

- [ ] **T1-1 platform-core Prisma schema**：multi-file schema，`@@schema` 归属 base/backstage；81 张表中 base 5 张 + backstage 19 张；枚举、CHECK、部分唯一索引按表设计逐条落地。验收：`prisma migrate deploy` 在空库可执行；表设计文档与 schema 逐条核对无差异。
- [ ] **T1-2 asset / hr / fin Prisma schema ×3**：各自部署单元 schema 与迁移历史（asset 30 / hr 18 / fin 9）。验收：同 T1-1。
- [ ] **T1-3 迁移序列与 Runner 配置**（主 PRD §9.9）：四套迁移目录隔离、Migration Runner 按 `platform-core → asset/hr/fin` 顺序执行、启动时结构版本校验。验收：并发容器不互相干扰迁移。
- [ ] **T1-4 只读视图脚本**（主 PRD §3.3/§9.9）：操作日志 `UNION ALL` 联合视图（base/backstage/asset/hr/fin）、hr 职称视图（hr PRD §8）、backstage 站点角色只读视图；`CREATE OR REPLACE VIEW` 幂等脚本，Migration Runner 迁移后统一执行。验收：视图脚本可重复执行、字段与契约一致。
- [ ] **T1-5 种子与初始化数据**：第一个超级管理员种子账号（待激活，base PRD §2、主 PRD §3.1，部署参数提供姓名/手机号/性别）、权限目录初始注册表（systems/business_sections/functions，backstage PRD §1 权限清单）。验收：初始化命令一次性展示激活链接，不写日志。

**检查点 1**：四库可迁移、视图可查、种子可建；`docs/database-design/` 与 schema 核对完成。

### 阶段 2：base 认证与账号（base PRD 全部 + 主 PRD §9.7/§9.8）

**目标**：双通道登录、激活、会话、登录保护、门户、个人中心可用——全平台访问前提。

- [ ] **T2-1 钉钉 OAuth 集成**（base PRD §2）：官方网页扫码授权、授权码后端兑换、组织成员校验（本公司组织）、稳定唯一标识绑定依据、state/nonce 一次性校验、手机号规范化与自动同步（含冲突写安全日志）。验收：扫码登录/注册/换绑/重置全流程，组织不匹配拒绝。
- [ ] **T2-2 注册与激活**（base PRD §2）：管理员预创建待激活账号 → 一次性二维码/链接（凭证摘要存储、7 天可配）→ 激活会话（fragment 凭证、短时 Cookie）→ 确认姓名性别设密码 → 事务内绑定+手机号同步+状态转正常。验收：邀请重发即旧失效、双通道一次性、手机号唯一性部分索引生效。
- [ ] **T2-3 密码登录 + 登录保护**（base PRD §2/§4）：Argon2id 哈希、手机号+密码通道、账号锁（默认 10 次/10 分钟）与 IP 锁（默认 60 分钟窗口/120 次/锁 1 小时，参数系统设置可调）、锁定/解锁事件写安全日志、统一错误提示不泄露账号存在性。验收：锁表、解锁后恢复、并发限流。
- [ ] **T2-4 会话管理**（base PRD §3）：Redis 服务端会话 + HttpOnly/Secure/SameSite Cookie + CSRF；空闲/绝对双超时（含"记住我"延长）；`session_version` 递增踢全部会话；登录成功/提权后旋转会话标识；守卫按四版本（授权/目录/组织/树）校验。验收：改密后全部会话失效、撤权立即生效。
- [ ] **T2-5 密码修改/重置/换绑**（base PRD §2、backstage PRD §3 联动）：修改密码（旧会话全失效）、钉钉验证式重置、管理员发起重置（凭证一次性、双超管约束）、钉钉换绑（原子替换、手机号同步、安全日志全记录）。验收：重置完成前旧会话有效、完成后统一失效。
- [ ] **T2-6 统一门户**（base PRD §5）：登录后落地页，系统入口按权限推导（可见≠可进入，"即将上线"/不可用展示状态）、个人中心入口常显、系统公告入口（读当前 PUBLISHING 公告）、待办角标（按审批功能数据范围统计）。验收：无权限系统入口不可见、公告状态正确。
- [ ] **T2-7 个人中心**（base PRD §6）：身份查看（手机号只读）、修改姓名/性别（超管立即生效，员工走资料修改审批）、修改密码、岗位变更申请入口（单部门员工限定，复用 T6-5 岗位申请）、我的操作日志（T4-1 依赖）。验收：资料审批通过才生效、岗位申请校验通过。

**检查点 2**：登录/激活/会话/门户端到端可用；安全事件全部落库。

### 阶段 3：backstage 权限体系（主 PRD §3.1 + backstage PRD §1/§4/§6）

**目标**：功能权限目录、授权、权限组、守卫、用户管理、超管管理——全项目访问控制的根基。

- [ ] **T3-1 权限目录与启动对账**（主 PRD §3.1、backstage PRD §1）：共享包定义三层目录（systems/business_sections/functions，含 data_scope_options）；backstage 启动按稳定功能编码幂等对账，变更事务递增 `catalog_version`。验收：目录漂移被对账修复、版本递增。
- [ ] **T3-2 员工授权 CRUD**（主 PRD §3.1、backstage PRD §4）：单人多功能授权/修改权限（携带授权版本条件更新，冲突 409）、批量授权（增量、幂等、整批回滚）、批量撤销、数据范围三档；事务内递增 `users.permission_version` + 操作日志。验收：并发修改冲突保护、整批语义正确。
- [ ] **T3-3 权限组**（主 PRD §3.1、backstage PRD §4）：CRUD + 矩阵式编辑 + 组编辑全量替换明细；授予时展开为授权快照，组变更不影响已授权员工；移除功能不再可展开。验收：快照语义验证。
- [ ] **T3-4 守卫与数据范围**（主 PRD §3.1、base PRD §3）：认证+系统可用性+功能权限+数据范围守卫；部门含下级闭包、多部门并集、最宽范围生效；四版本缓存校验（授权/目录/组织/树）；"权限管理"两级委派与自我提权防护；超级管理员豁免业务规则除外。验收：越权返回 403/404、撤权即时生效。
- [ ] **T3-5 用户管理**（backstage PRD §3）：创建（待激活、无密码无绑定）、编辑（姓名/性别）、批量注销（软删除 + 会话失效 + 生命周期任务 + 待审批类型分派）、批量恢复（hr 前置就绪检查 + 恢复兼容性 + lifecycle_version 校验）、解锁、重新生成邀请、发起密码重置。验收：整批全有或全无、注销/恢复安全顺序正确。
- [ ] **T3-6 超级管理员管理**（主 PRD §3.1）：任命/降级（二次确认、最后超管保护、当前角色复核、事务内递增版本 + 审计）。验收：最后一名超管不可卸任。
- [ ] **T3-7 系统与业务结构管理**（backstage PRD §6）：系统产品状态（OPEN/COMING_SOON）、业务板块说明维护。验收：入口可见性与状态联动正确。

**检查点 3**：权限目录对账、授权、守卫、注销恢复端到端可用；超管保护生效。

### 阶段 4：平台基础设施（主 PRD §3.3、§9.1–§9.3 + backstage PRD §7–§11）

**目标**：日志、任务、设置、公告、备份、恢复、健康——平台级能力齐备，业务模块随事务接入。

- [ ] **T4-1 操作日志**（主 PRD §3.3）：各模块同构表 + 摘要模板接口 + 幂等唯一约束（operator_id+system+scope+key）+ 请求指纹/结果引用；导出成功才记成功日志；联合视图查询（系统/功能/操作者/部门/时间筛选、导出所有/已筛选）。验收：幂等重放不重复、业务回滚日志同步回滚。
- [ ] **T4-2 统一后台任务 + Outbox**（主 PRD §9.1）：background_tasks 事实表（PENDING_ENQUEUE→QUEUED→RUNNING→终态）、轻量 Outbox（事务内建任务、提交后投递）、BullMQ 稳定 jobId 去重、调度循环（跳过已锁行、租约扫描、失败终态 24h 汇总索引）、可重放任务安全重试、BullMQ 记录保留与清理。验收：崩溃恢复不重复副作用、任务表为唯一事实来源。
- [ ] **T4-3 错误日志聚合**（backstage PRD §8）：指纹生成（服务+commit+分类+稳定入口，排除高基数/敏感值）、五分钟时间桶、条件唯一索引 + 原子 UPSERT、处置状态单向流转（PENDING→HANDLED/IGNORED）、脱敏样本、详情与脱敏摘要导出。验收：并发聚合不重复、终态不可回退。
- [ ] **T4-4 安全日志**（backstage PRD §8）：登录/锁定/激活/邀请/密码/换绑/手机号同步/内部令牌校验失败等事件，结果/原因/IP/上下文，只追加。验收：事件范围与 PRD 清单一致、敏感值不落库。
- [ ] **T4-5 系统设置**（backstage PRD §7、主 PRD §1.4）：S-8 参数表 + 设置页 + Redis 变更广播；平台配置（会话/锁/默认窗口/导出上限/备份保留/图片保留/审批超时天数）；敏感参数加密；版本化常量不入表。验收：改参数即时生效、快照规则不追溯。
- [ ] **T4-6 更新日志与系统公告**（backstage PRD §9）：发布流程自动追加 release_logs（唯一发布标识防重）；公告 CRUD + 发布事务（同时最多一条 PUBLISHING 的条件唯一索引）+ 门户读取 + 从更新日志复制。验收：并发发布不产生两条正在展示。
- [ ] **T4-7 数据备份**（backstage PRD §10）：定时（每日 02:00 北京时间）/立即备份 → pg_dump 压缩格式 → OSS 私有 + 最小清单；保留天数清理（目录+对象+清单联动）；备份互斥；恢复前紧急备份。验收：备份记录/清单/对象一致、清理不遗漏。
- [ ] **T4-8 数据库恢复**（backstage PRD §10）：恢复执行器（ECS 持久化维护标记 + 恢复控制清单 + 控制会话）、停写排空、恢复后正向迁移（只执行备份后新迁移）、非终态任务标记取消、OSS 备份目录补回、恢复后校验（连接/迁移/超管存在）、Redis 清空重建。验收：恢复全流程维护状态正确、异常保持维护并人工介入。
- [ ] **T4-9 健康状态页**（backstage PRD §11）：服务存活/就绪/依赖状态；任务总览（当前数量/24h 失败数/最近失败时间，按模块+类型分组）；按权限跳转业务页或系统日志。验收：汇总不展示任务明细。

**检查点 4**：日志/任务/设置/备份/恢复/健康全部可用；业务模块可随事务接入日志与任务。

### 阶段 5：统一审批契约（主 PRD §3.2）

**目标**：共享审批内核定型，hr/asset/backstage 三类审批头全部接入。

- [ ] **T5-1 审批内核共享包**（主 PRD §3.2）：审批头/处理记录契约（application_no、状态机 DRAFT→PENDING→APPROVED/REJECTED/CANCELLED、version 条件更新、驳回必填原因、取消来源 USER/ACCOUNT_DEACTIVATED/OVERDUE）、幂等键支持、超时自动取消扫描（submitted_at + 设置天数）、"同一业务键最多一条待审批"条件唯一索引工具。验收：并发处理仅一个成功、其余 CONFLICT。
- [ ] **T5-2 审批中心 API 契约**（主 PRD §3.2）：待办/已处理/详情时间线/处理接口契约统一；审批人范围校验（批次对象部门快照覆盖、入库/库存变更仅公司档例外）；注销员工待审批处理规则（公司业务型继续、账号资料型自动取消）。验收：范围外记录不可见。

## 4. 并行与分工建议

| 组合 | 建议 |
| --- | --- |
| 主线（T0–T5 + T10） | 一人负责 platform-core 全链（工程基座、认证、权限、基础设施、审批契约、发布脚本） |
| 业务线 | 另一人从 T6（hr）或 T7（asset）入手（需等待 T3–T5 的共享包/契约接口稳定，可先并行开发 T6-1 组织、T6-4 节假日等相对独立部分） |
| 前端 | 与后端各系统并行推进（契约先行：DTO/错误码先定）；fin 的 Editable Cells 与 Excel 链路建议后置到后端 T8 稳定后 |
| 文档同步 | 每个任务完成时同步检查 PRD/API 文档/表设计（项目宪法：代码修改须同步检查文档） |

## 5. 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 权限体系设计复杂度高（四版本失效、数据范围闭包、跨服务视图） | 延期/安全漏洞 | 阶段 3 独立成段、验收标准先行；共享包优先；跨服务契约（hr 视图、注销生命周期）在 T1-4 视图脚本阶段就定字段 |
| 数据库迁移并发冲突（两人同时改 schema） | 迁移序列混乱 | dev-workflow §2 高冲突区协调；各自本地库、迁移随代码走；Migration Runner 统一执行 |
| 利润分析 Excel 往返（模板/样式/上限/并发）是全项目最复杂的单点 | 返工 | T8-4/T8-5 预留完整阶段；模板与样式常量绑定版本；固定快照测试 |
| 恢复流程（维护状态/停写/正向迁移）无法自动化测试 | 生产事故 | T10-3 部署后强制做一次恢复演练 |
| 前端契约漂移（多个后端并行） | 联调返工 | 后端契约（DTO/错误码/OpenAPI）先行评审，前端只消费生成文档 |

## 6. 既定决策

1. **monorepo 工具**：纯 pnpm workspaces（根锁文件 + `pnpm -r` 聚合脚本），不引入 turborepo 等构建编排。
2. **共享包边界**：独立 `@wbme` workspace 共享包——`@wbme/contracts`（错误码/DTO/枚举/权限目录定义）、`@wbme/approval`（统一审批内核）、`@wbme/logging`（操作日志模板/错误日志/安全日志的预定义受限语句接口）、`@wbme/tasks`（统一任务表的受限创建与状态条件更新）；asset/hr/fin 直接依赖，schema 归属约束不变（主 PRD §9.3/§9.1）。
3. **Node.js 版本**：24 LTS（Active LTS），写入根 `.nvmrc`，CI 与本地一致。
4. **前端推进策略**：与后端并行——后端 DTO/错误码/OpenAPI 契约先行，各系统前端随对应后端阶段同步推进。
5. **测试策略**：**全面单测**——Vitest 覆盖全部服务层逻辑（含错误目录、审批状态机、权限守卫、库存/额度一致性、Excel 模板校验）；UI 层以 Playwright E2E 为主；每个任务的验收均包含对应单测通过。
6. **文件存储**：OSS 预签名直传（限时/限大小/限路径）+ 后端校验解码后正式关联 + 临时对象 24h 清理（主 PRD §9.2），影响 T7-1 主图与 T4-7 备份上传链路。
